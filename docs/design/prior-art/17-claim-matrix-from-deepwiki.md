### NousResearch/hermes-agent
- **bound**: YES, the approval is bound to the exact request payload. The system uses a `request_id` and `digest` within the `ApprovalRequest` dataclass to ensure that an approval cannot be reused for a different call. The `consume_prepared_guard` function explicitly makes decisions single-use.     ## Explanation  When a human approves a risky tool call, the system ensures that this approval is specific to the exact request that was presented. This is achieved through several mechanisms:  ### Request Binding with Digest and ID The `ApprovalRequest` dataclass, defined in `hermes_cli/approval_transport.py`, includes a `request_id` and a `digest`.  The `request_id` is a unique identifier for each approval request, generated using `uuid.uuid4().hex`.  The `digest` is a SHA256 hash of the canonical JSON representation of the request's fields, including the `session_key`.  This `digest` ensures the integrity of the request payload. When a transport returns an `ApprovalDecision`, it must include the `request_id` and `request_digest` from the original `ApprovalRequest`, binding the decision to that specific request.   ### Single-Use Decisions The `consume_prepared_guard` function in `agent/terminal_approval_batch.py` explicitly states that a decision is "single-use, even for identical calls" by setting `slot.decision` to `None` after it's consumed.  This prevents the same approval from being implicitly reused for subsequent calls, even if their payloads appear identical.  ### Validation of Arguments The `validate_prepared_terminal` function in `agent/terminal_approval_batch.py` checks if the arguments of a terminal command have changed after approval preparation.  If the arguments (`args`) are not identical to the `slot.args` that were approved, the `slot.decision` is set to `None`, and a `RuntimeError` is raised, effectively denying the execution.  This ensures that an approval is strictly tied to the exact arguments presented at the time of approval.  ### Coalescing Identical Concurrent Approvals While approvals are single-use, the system does handle identical concurrent approvals by coalescing them. The `_await_gateway_decision` function in `tools/approval_gateway_wait.py` checks for existing pending approvals with the same command text and pattern keys.  If a leader approval exists, followers will adopt its decision for `session` or `always` choices, but a `once` approval only covers the leader, forcing followers to prompt for a fresh approval.  This mechanism prevents multiple identical prompts for the user while maintaining the single-use nature of "once" approvals.  ## Notes  The concept of "single-use" for approvals is critical for security, ensuring that a human's consent is specific to a particular action and its parameters. The `digest` in `ApprovalRequest` and the explicit nullification of `slot.decision` after use are key implementations of this principle. The coalescing of concurrent approvals is an optimization for user experience, but it respects the fundamental security constraint for single-use approvals.
