## 1. Scope and contract

**Job.** Make a decision a stranger can check without trusting the system that produced it, and say exactly how far that check reaches. Three artefacts carry it: the **ledger** (an append-only, tamper-evident record of what happened, with signed checkpoints), the **bundle** (one decision and everything needed to re-check it, packaged and signed), and the **verifier** (a standalone program that returns PASS, FAIL, INDETERMINATE or NOT_APPLICABLE per check, with reason codes and an explicit "what this does not prove").

**Inputs.** Typed values and trace events from M3, M4, M5, M13 and M7 (never their internals); evidence bodies and records from M1 and M2; the policy IR from M5 and the reconcile kernel configuration from M3 as data; the lifecycle transition table from M13; certificates from M4.

**Outputs.** (1) `ledger/`: C2SP tiles, checkpoints, anchors; (2) `dossier-<case>.tar`: the deterministic bundle, in audience tiers; (3) `verify.mjs` and two further verifier implementations; (4) the tamper corpus and its report; (5) erasure receipts; (6) the browser hash-recheck contract consumed by M10.

**Depends on.** M7 (ports `clock`, `ids`, `fs`, `StorePort` blob store, the trace schema, the single-writer append port, error classes), M8 (confidentiality labels, store partition rules, key custody boundary, `ReleaseBinding` contents and minting policy, `permission-matrix.json`), M5 (policy IR as data, decision record, reason codes), M4 (the `Evaluator` composition, certificate formats, normative L0 quote-check algorithm), M3 (reconcile kernel configuration), M2 (text-layer, locator units and layer format), M1 (evidence record, rights flags), M12 (`ExecutionContract` container), M13 (lifecycle, receipts, broker, approvals, nonce store), M6 (memory head).
**Depended on by.** M10 (viewer, CLI `verify`, MCP `verify_bundle`), M11 (tamper corpus is an evaluation artefact), M13 (receipts and the capability signer role), M12 (Meterless ledger head anchored here).

**Claim discipline.** The strongest sentence this module may publish is: "tamper-evident under assumptions A1 to A7 (section 10.4), checked by a verifier whose false-accept count over the published mutation set is reported with its scope". Never "tamper-proof", never a SLSA level, never "AI Act compliant". The documentation lint of spec 9a applies to every string the verifier prints.

## 3. Component 1: Canonical form, digests and strict parsing

### 3.1 Best references
R14 (JCS and vectors), R9 (the lesson that three SDKs drifted until null-versus-absent was written down, 13 §3.1), R7 (length-prefixed PAE; "MUST NOT re-parse the envelope after verification"), 13 §4.5 (our restricted profile). Evaluation limits: JCS vectors cover number serialisation and key ordering; they do not cover our profile's rejections (duplicate keys, floats, depth) and none of the vectors exercises a non-JavaScript runtime sorting by UTF-8 bytes instead of UTF-16 code units.

### 3.2 What they actually do
RFC 8785 sorts members by UTF-16 code units and serialises numbers per ECMAScript (13 §4.5, read from the RFC). Obsigna's reject corpus is a list of named cases, each mutating one field of a freshly signed base receipt and each naming the clause it guards (read in `malformed_vectors.json`). R7 requires the verifier to hand the application the exact payload bytes it verified.

### 3.3 Decision
**Adapt.** M7 owns the canonicaliser used by producers (spec 4). M9 owns an **independent verifier-local copy** with a strict byte-level parser, because `JSON.parse` silently accepts duplicate keys, converts large integers, accepts `-0` and loses the source form, and a verifier that shares the producer's parser shares its blind spots. Rejected alternative: reusing M7's module in the verifier (violates "shares no server code").

### 3.4 Implementation design

```ts
// Plumbline profile P1 of RFC 8785. All functions pure.
type Raw = Uint8Array;
declare function parseStrict(bytes: Raw, limits: Limits): Result<Json, ParseError>;
declare function jcs(v: Json): Raw;                       // RFC 8785 output for the profile subset
declare function rawDigest(bytes: Raw): RawHash;           // `sha256:<lowercase hex>` of the bytes as stored; equals `sha256sum`
declare function docDigest(domain: DigestDomain, v: Json): DocHash; // `jcs:<hex>` = sha256(domain || 0x0A || jcs(v))
type DigestDomain = `plumbline.${string}.v1`;              // a domain tag never contains 0x0A, so the join is unambiguous
interface Limits { maxDepth: 64; maxDocBytes: 16_777_216; maxMembers: 20_000; maxMemberBytes: 268_435_456; maxBundleBytes: 2_147_483_648; maxTarRatio: 20 }
```
Parser rules (all MUST-reject, each a vector): invalid UTF-8; a BOM; unescaped control characters; lone surrogate escapes; duplicate keys at any depth (compared after unescaping); numbers other than `-?(0|[1-9][0-9]{0,15})` in the safe-integer range, so no fractions, exponents, `-0` or leading zeros; trailing bytes; depth over 64. Optional members are absent, never `null`, unless the schema marks them required-nullable. Sort order is by UTF-16 code unit: implementations in languages that compare UTF-8 bytes must transcode first (a vector with keys U+FF5E and U+1F600 distinguishes them).

Three digest kinds, never mixed (INT-003). `RawHash` covers anything a stranger can recompute from a file: bundle members, evidence bodies, tar members, quote bytes. `DocHash` covers structured values that are logged or chained, so a digest of one document type can never be mistaken for another. `Commitment` (`com:<hex>`, component 13) covers any value above `public` or of low entropy. Ledger leaf, node and root hashes use the RFC 6962 prefixes (component 2); they are carried in fields named `leafHash` and `root` and compared only with recomputation, because no shared kind describes them (revision note, contradiction 1). A list of all digest sites and their kind is a table in the verifier specification and a lint over the producer.

Digest string form is `<kind>:<64 lowercase hex>` with kind `sha256`, `jcs` or `com`; a verifier parses the prefix and a field declared `RawHash` that carries `jcs:` is `V1.SCHEMA` FAIL, so a mix-up is a parse failure and not a silent mismatch. The in-toto `subject.digest.sha256` field is the one exception: it is bare hex because that format defines it. Base64 is RFC 4648 section 4 with padding, canonical encodings only; decoders reject non-canonical forms (the same rule as R1).

### 3.5 Tests
`T-CAN-01` published JCS vectors (R14) in CI against our canonicaliser, the verifier copy and `canonicalize`; `T-CAN-02` profile rejections, one vector per rule above plus digest-prefix confusion (`jcs:` in a `RawHash` field and the reverse), run in all three verifier implementations; `T-CAN-03` astral-plane key order vector; `T-CAN-04` property: `jcs(parseStrict(jcs(v))) == jcs(v)` over generated documents (fast-check); `T-CAN-05` golden digests of every schema document (shared with M7, the D-011 golden-hash test). Disproof: any implementation pair disagreeing on a parse verdict for a corpus document.

### 3.6 Risks and NOT VERIFIED
Whether cyberphone's vectors can be used in CI under their licence status (NOASSERTION) is not decided; they are downloaded at test time, never committed. ECMAScript number rules are irrelevant to us (integers only), which removes the main cross-language hazard by construction; money is a decimal string.

### 3.7 Build notes
First thing built; unblocks every other component. Vectors written before any implementation.

## 4. Component 2: Ledger core, history tree, tiles, leaves, streams

### 4.1 Best references
R1 (checkpoint, tiles, proof format), R2 (hasher and proof algorithms, vectors), R3 and R4 (production tile logs; POSIX layout), R16 (why a tree beats a chain; skeptical client), R20 (the negative example), 13 §4.2 pitfalls table. Evaluation limits: Tessera, Rekor v2 and Sunlight are operated for public logs with thousands of entries per second; none is evaluated for a single-tenant, single-writer audit log that must run from one command on a Windows laptop, and none carries per-stream sequence numbers.

### 4.2 What they actually do
Read in `rfc6962/rfc6962.go`: leaf hash is SHA-256 of `0x00 || leaf`, node hash uses prefix `0x01`, empty-tree root is SHA-256 of nothing. Read in `proof/verify.go`: `VerifyInclusion` requires `0 <= index < size`, checks the leaf hash length, **checks the proof length exactly** (`inner + border`, where `border = popcount(index >> inner)` and `inner` comes from `innerProofSize(index, size)`, whose body I did not read), and compares the recomputed root; `RootFromConsistencyProof` rejects `size1 == 0`, rejects an empty proof unless sizes are equal, and rejects a non-empty proof when sizes are equal. Read in R1 `tlog-tiles`: tiles hold 256 hashes (8,192 bytes), path `tile/<L>/<N>[.p/<W>]` with `N` in zero-padded three-digit groups prefixed `x` (example `x001/x234/067`), partial tiles for the right edge, entry bundles `tile/entries/<N>` as big-endian uint16 length-prefixed entries (so an entry is at most 65,535 bytes), checkpoint at `<prefix>/checkpoint`, and "MUST NOT serve redirect responses". Read in R1 `tlog-checkpoint`: the three-line note body (origin, decimal size, base64 root), extension lines "NOT RECOMMENDED", and "MUST NOT sign any checkpoint which is inconsistent with any checkpoint it previously signed".

### 4.3 Decision
**Adapt** the RFC 6962 hashing and the C2SP tile and checkpoint formats exactly, **own** the log writer, the leaf schema and the stream layer. Adopt-as-dependency is rejected: no maintained TypeScript tile library was verified, the Go libraries cannot be a judge-run dependency, and the hashing and proof algorithms are about 300 lines that we must understand anyway because the verifier re-implements them. Go libraries become CI oracles (differential tests). Rejected: a hash chain (cannot detect tail truncation or a forked history, R16); Merkle mountain ranges (less tooling; the leaf format and checkpoint fields stay independent of the tree so a switch stays possible, 13 §2.8).

### 4.4 Implementation design

**Log identity.** One log per tenant (INT-048): erasure, key rotation, disclosure and isolation are per tenant, and a tenant split is a known chain failure. Origin `<ns>/ledger/<deploymentId>/<tenantId>`, where `<ns>` is the project namespace constant (section 10.4, a decision for Prateek; interim value ends in `.invalid`, which cannot collide with a real domain) and `<tenantId>` is a `TenantId` (`tn_...`). The judge path runs exactly one tenant, `tn_default`, so it has one tree. R1 asks only for a schema-less URL-style name; reachability is not required.

**On-disk layout** (all paths relative to the tenant's ledger directory `ledger/<tenantId>/`; blob bodies live in the unified blob store behind M7's `StorePort`, addressed by `RawHash` and partitioned by confidentiality class, so confidentiality and erasure rules differ per partition and no ledger file ever holds content):
```
log.json                         origin, hash "sha256", tileHeight 8, schemaVersion, genesisLeafHash
LOCK                             exclusive-create file {pid, startedAt}; one writer per directory
wal/pending.jsonl                leaves accepted but not yet inside a published checkpoint (fsynced)
tile/<L>/<N>[.p/<W>]             Merkle tiles, immutable once full (R1)
tile/entries/<N>[.p/<W>]         entry bundles (R1)
checkpoint                       latest signed note, replaced atomically
checkpoints/<size>.note          every published checkpoint, immutable
anchors/<size>/{cosigs/*.note, rfc3161/*.tsr, ots/*.ots}   self-authenticating attachments (components 5, 6)
idx/streams.json                 derived: stream -> {nextSeq, headLeafHash}; rebuildable from entries
```

**Leaf record** (JCS bytes, at most 4,096 bytes, far below the 65,535 entry limit):
```ts
interface LeafV1 {
  v: 1;
  tenant: TenantId;                  // equals the tree's tenant; a leaf for another tenant is rejected (`LEDGER_STREAM_INVARIANT`)
  type: LeafType;                    // registry in section 5.4
  stream: StreamId;                  // "deploy" | "policy" | "memory" | `case:${string}` | `hold:${string}` | "erasure"
  seq: number;                       // gapless per stream, starts at 0
  prev: Hash | null;                 // RFC 6962 leaf hash of (stream, seq-1); null iff seq == 0
  at: Iso;                           // ctx.clock; producer-asserted, bounded only by anchors
  actor: { kind: "system" | "role" | "human" | "service"; id: string; keyId?: string };   // models write nothing, they propose, so `model` is not an actor kind
  subject: DocHash | Commitment;     // docDigest, or salted commitment when the thing is above `public`
  payload: RawHash | null;           // digest of the body in the blob store (erasable)
  attrs: { [k: string]: string | number | boolean | string[] };  // small, structural, no personal data
  idk: string;                       // idempotency key (component 3)
}
```
Rules. `attrs` may hold only identifiers, codes, counts and hashes; names, account numbers and free text never appear (the leaf is exposed by any inclusion proof). `subject` for any item whose confidentiality is above `public` is a salted `Commitment` (component 13), so a leaf digest of a low-entropy value cannot be guessed. M7's `LeafDraft` is a subset constructor of this record (any stream, the four actor kinds here). `prev` is the stream-local chain: removing a leaf from the middle of a stream breaks the next leaf's `prev`; removing the tail cannot be detected by `prev`, which is why checkpoints, a terminal marker (`case.closed` or `decision.final` followed only by the post-decision types) and the pinned earlier checkpoint exist.

**Tree operations** (pure, over tile reads):
```ts
declare function leafHash(leafBytes: Raw): Raw;                   // sha256(0x00 || bytes)
declare function nodeHash(l: Raw, r: Raw): Raw;                   // sha256(0x01 || l || r)
declare function rootAt(store: TileReader, size: number): Result<Raw, LedgerError>;
declare function inclusionProof(store: TileReader, index: number, size: number): Result<Raw[], LedgerError>;
declare function consistencyProof(store: TileReader, m: number, n: number): Result<Raw[], LedgerError>;
declare function verifyInclusion(index: number, size: number, leaf: Raw, proof: Raw[], root: Raw): boolean;   // exact proof length
declare function verifyConsistency(m: number, n: number, rootM: Raw, rootN: Raw, proof: Raw[]): boolean;     // m >= 1, rules as in R2
```
The proof algorithms are transcribed from RFC 9162 sections 2.1.3 and 2.1.4 and checked against the R2 vectors before use. Right-edge hashes that are not stored in a full tile are recomputed from the partial tile at each level. Stored full tiles are never rewritten.

**Append algorithm (single writer, owned by component 3).** Leaves are first written to `wal/pending.jsonl` and fsynced, which assigns the next global index and the stream `seq`. A flush writes the entry bundles and tiles for the new size to temporary names, renames them into place, computes the new root, obtains a signature (component 4), writes `checkpoints/<size>.note`, atomically replaces `checkpoint`, and truncates the WAL prefix. **Recovery** on start: acquire `LOCK` (a stale lock is taken over only if the recorded pid is not alive and the lock is older than a configured bound); read `checkpoint`; rebuild `idx/streams.json` by scanning entry bundles; any entry bundle or tile beyond the signed size is either confirmed against the WAL (and re-submitted for signing, which the signer accepts because it is a consistent extension) or, if torn, discarded back to the last complete entry. The WAL is the source of truth for unpublished leaves.

**Determinism.** The global index depends on the interleaving of concurrent cases and is therefore **not replay-stable**. Replay equality is defined over each stream's leaf sequence and its head leaf hash, never over global indices or the tree root (this corrects the way spec 4 words "final state hash" if the ledger index leaks into state; see Spec feedback F4).

### 4.5 Tests and acceptance
`T-LED-01` proofs against R2's inclusion and consistency data and a differential run against `transparency-dev/merkle` on random trees up to 70,000 leaves (crosses the 256-entry tile and level-1 boundaries); `T-LED-02` property: for random sizes m <= n, `verifyConsistency` accepts the generated proof and rejects every one-hash and one-byte mutation, and rejects proofs of wrong length; `T-LED-03` tile layout byte-equal to R1's path encoding for N up to 1,234,067 (`x001/x234/067`); `T-LED-04` crash drill at each of eight points in the append algorithm (after WAL, mid entry bundle, mid tile, before root, before signing, mid checkpoint write, before `checkpoint` replace, after replace): after restart the log verifies and no accepted leaf is lost or duplicated; `T-LED-05` torn tile write; `T-LED-06` two writer processes started on one directory: the second fails closed; `T-LED-07` stream gap, duplicate `seq` and `prev` mismatch are rejected by the writer (`LEDGER_STREAM_INVARIANT`, class `fatal`). Metric: append p50 and p99 latency with group commit, tile bytes per leaf, verification time for a 200-leaf bundle. Disproved if any crash point loses an accepted leaf, or if differential testing finds one proof the oracle rejects.

### 4.6 Risks and NOT VERIFIED
Directory `fsync` does not exist on Windows; durability of renames after power loss on NTFS is **NOT VERIFIED** for our write sequence, so the drill is run on the Windows development machine and its limit is stated. `innerProofSize` body not read. Tile retrieval over HTTP is not needed (the log is a directory), so the redirect rule of R1 is moot until a server exists.

### 4.7 Build notes
Hasher and proofs, then tile reader and writer, then WAL and recovery, then the stream index. Blocks components 3, 4, 6, 9.

## 5. Component 3: Append port, group commit and the trace-to-ledger projection

### 5.1 Best references
R3 (synchronous publication: the call returns when the entry is in a published checkpoint), R9 (daemon-held signing and out-of-process writing), 13 §4.2 (event types), 13 §4.3 and §4.4 (trace and cassette), FoundationDB and TigerBeetle style fault injection (13 §5), Temporal's history-based replay (13 §4.4). Evaluation limit: none of them specifies how an agent runtime's trace maps to audit leaves, and AUD-05 shows that fully synchronous publication per event couples every step to signing.

### 5.2 What they actually do
Tessera offers synchronous publication as a contract (13 §2.6, read from its page, not its code). R20 is the counterexample: a ledger with no ordering guarantee, written from many call sites. Temporal replays workflow code against recorded history and fails on divergence (13 §4.4).

### 5.3 Decision
**Own.** The port is ours because it must be idempotent under M7's crash-resume, must keep per-stream order deterministic under fan-out, and must split durability from publication. Alternative rejected: write every trace line as a leaf (too many leaves, trace content would sit in the log); write only a final summary (loses the "no effect without a leaf" invariant).

### 5.4 Implementation design

**Single-writer port (the contract M7 provides and M9 implements).**
```ts
interface LedgerPort {                       // exposed through ctx.ledger; the only writer path
  append(req: AppendRequest): Promise<Result<Appended, LedgerError>>;      // durable (WAL fsync) on resolve
  published(a: Appended): Promise<Result<Published, LedgerError>>;         // resolves when covered by a signed checkpoint
  streamHead(stream: StreamId): Promise<Result<{ seq: number; leafHash: Hash }, LedgerError>>;
}
interface AppendRequest { tenant: TenantId; stream: StreamId; type: LeafType; actor: Actor; subject: DocHash | Commitment; payload: RawHash | null; attrs: LeafV1["attrs"]; idk: string }   // one port instance per tenant tree
interface Appended { globalIndex: number; stream: StreamId; seq: number; leafHash: Hash }
interface Published { size: number; root: Hash; checkpointNote: string }
type LedgerError = { code: "SIGNER_UNAVAILABLE" | "SIGNER_REFUSED" | "IDEMPOTENCY_CONFLICT" | "STREAM_INVARIANT" | "STORAGE" | "LOCKED"; class: ErrorClass };
```
`idk = H(runSeed, node path, event ordinal)`. M7's `appendBefore(call, draft)` helper is built on `append` plus `published` and is what the broker uses before an irreversible effect (INT-018). A repeated `append` with an existing `idk` and byte-identical leaf returns the original `Appended` (crash-resume); the same `idk` with different bytes is `IDEMPOTENCY_CONFLICT`, a non-determinism signal (class `fatal`). `SIGNER_UNAVAILABLE` is class `transient` (retry within the budget, then escalate); `SIGNER_REFUSED` (the signer found an inconsistency) is `fatal`.

**Group commit.** A flush runs when 64 leaves are pending, when 250 ms have passed since the oldest pending leaf, on `decision.final`, or on an explicit `sync`. These numbers are starting values to be tuned by measurement. **Which leaves wait for publication:** `append` alone suffices for `evidence.fetched`, `stage.committed`, `trace.segment` and other internal leaves. The caller must `await published(...)` before (a) the broker acts on `approval.granted` or `capability.issued` (the broker may not act on an unlogged approval), (b) `action.intent`, (c) `decision.final`, and (d) building a bundle. Result leaves (`action.executed`, `action.confirmed`, `action.not_sent`, `action.reversed`) may lag behind the effect and are backfilled from the WAL, which recovery preserves in `walSeq` order; because `action.intent` and `capability.issued` were published before the broker acted, V8 "no `action.executed` without prior `action.intent` and `capability.issued`" holds by global index order. M13's `appendAsync` for the intent is not a permitted call. This is the answer to AUD-05: durability is cheap and per leaf, publication is per batch and mandatory only where an unpublished leaf would let an effect precede its record.

**Leaf type registry** (v1). Types marked W are write-ahead (the leaf precedes the effect), R are result leaves (the leaf follows a recorded effect).

**Trace projection.** The runtime trace (JSONL, one event per line, deterministic ids) has one schema, owned by M7 (INT-054): it carries `prevLineHash` (the local hash chain), `why_kind`, `decider`, `phase`, `agent`, `verb`, `budget`, `tenant` and `semconv_version`; this module consumes it and adds no fields. At each stage commit, M7 passes the segment (line range and head hash) and M9 writes `trace.segment`. A verifier given the bundle's `trace/run.trace.jsonl` re-derives the chain and compares the segment heads to the leaves. The invariant "no recorded effect without a leaf" is checked at stage commit by a linter (every effect line in the segment has a cassette entry and the segment leaf exists) and offline by V8; "no leaf without a recorded effect" holds for R-leaves by the same ordering rule (cassette line written first, leaf after). Model calls, tool calls and deterministic steps are covered by segments, not one leaf each; effects with external consequences have their own leaves.

**`why_kind` handling.** Every decision-bearing trace line has `why_kind` in `rule | computed | model_reported | human_reported` (spec 13, INT-002) and `decider` in `code | model | human`. Rules: `rule` lines carry `ruleId` and `factIds`; `computed` lines carry the id of a registered pure function and its input ids; `model_reported` lines carry `rationaleDigest` and the model id and are stored in the blob store. A structured human decision (approve or deny with a code from a closed list) is a `rule` reason with `ruleId "human.approval.<code>"` bound to the signed approval record; free text from a person is `human_reported`, stored, labelled untrusted and never counted. The decision record separates `reasons` (kinds `rule` and `computed`, the only ones the UI may render as the explanation) from `modelReported` (rendered under "model-reported rationale, not verified") and `humanReported` (rendered under "Approver's note, not an explanation"). `trace.segment` and `decision.*` leaves carry counts and codes by kind. The verifier recomputes `rule` and `computed` reasons in V6, binds `human.approval.*` reasons to their `approval.*` leaf instead (they are not policy rules; counted apart as `humanBound`), and reports an `explanationCoverage` figure; a decision whose reasons are only `model_reported` or `human_reported` yields `V6.NO_VERIFIABLE_REASON` (INDETERMINATE).

**Concurrency.** M7 serialises appends from fan-out branches in branch order (spec 4), so per-stream order is deterministic; different cases interleave freely. The port is the only writer; readers (CLI `verify`, bundle builder, console) open tiles read-only and never take `LOCK`.

### 5.5 Tests and acceptance
`T-PORT-01` replay a stored case twice: per-stream leaf sequences and head leaf hashes are identical; global indices may differ. `T-PORT-02` idempotent resume: kill the process after each append and restart; the final stream is identical to an uninterrupted run. `T-PORT-03` effect/leaf linter (a seeded run with one effect missing its leaf fails; a leaf with no cassette line fails). `T-PORT-04` write-ahead: kill the broker between `action.intent` and the target call; on resume the target is queried with the idempotency key before acting (M13 test, evidence from here). `T-PORT-05` signer down: `append` still succeeds, `published` fails with `SIGNER_UNAVAILABLE`, the broker refuses to act. `T-PORT-06` `why_kind` lint: a decision line lacking `why_kind`, or a `rule` line with no `ruleId`, fails the trace linter. Metrics: leaves per case, checkpoints per case, added wall time per stage (published in the per-phase report, F-BUDGET).

### 5.6 Risks and NOT VERIFIED
The group-commit constants are untested. Whether M7's substrate can hold `await published()` across a human interrupt is a substrate property (spec 4). The 4,096-byte leaf limit may be too small for some `attrs`; reasons are kept as codes to avoid it.

After component 2 and the signer stub of component 4; M7 contract tests use a fake writer first.

## 6. Component 4: Signer process, checkpoints, cadence and key rotation

### 6.1 Best references
R1 `tlog-checkpoint` and `tlog-cosignature` (what a signature covers; the monotonic-size rule for cosigners), R5 (a witness keeps only its latest verified checkpoint and persists atomically), R9 (out-of-process daemon holds the key; key-rotation receipts signed by the outgoing key), R16 Schneier and Kelsey (forward security), 13 §4.2 (declared cadence, from the checkpointed local log draft), R13 (Ed25519 edge cases). Evaluation limit: none of these addresses a signer that must also guard capability and decision signatures, and R9's daemon design was read through its README and tree listing, not its code.

### 6.2 What they actually do
Read in R1 `signed-note`: a signature line is an em dash, the key name, and base64 of a 4-byte key id followed by the signature; the recommended key id is the first four bytes of `SHA-256(name || 0x0A || type byte || public key)`; Ed25519 log signatures use type `0x01` and sign the note text; verifiers "MUST ignore signatures from unknown keys" and "MUST reject the note" if no known key verifies. Read in `tlog-cosignature`: an Ed25519 checkpoint cosignature (type `0x04`) signs `cosignature/v1\ntime <t>\n<origin>\n<size>\n<root>\n` plus extension lines, its key id uses type byte `0x04`, and "the Ed25519 signed message format doesn't commit to the cosigner name", so one key must serve one cosigner. A witness's cosignatures are monotonic in tree size.

### 6.3 Decision
**Own** the signer as a separate process with **role policies**, **adapt** the formats. The signer is not a dumb oracle: it behaves as a witness of its own writer. It stores the last checkpoint it signed (size and root) and signs a new one only when handed a valid consistency proof from that state (the exact request shape of the R1 `add-checkpoint` call), so a compromised writer process cannot obtain a signature over a forked history. Rejected: an in-process signer (a bug in the writer or runtime exposes the key and loses the consistency guard); an HSM or cloud KMS now (a documented extension point; not available to a judge).

### 6.4 Implementation design

**Process model.** `plumbline-signer` is started as a child process (stdio pipes; no network listener) by the ledger writer or, in a stronger deployment, as a service under a different OS user. It is the one signer process and the one key registry of the system (INT-017): it holds six key roles, keyed per tenant, and every other module's signing need is a client of it through M7's `SignerPort`; `KeyPort` (M13: inventory, rotation, data-key wrap) sits behind the signer as its storage and rotation interface and is not a second signing path. Per-role policies are specified here once and contributed by their owners. The honest statement of isolation: a separate process under the same OS user gives crash and bug isolation, not compromise isolation; compromise isolation needs a different user or container, which is the documented production posture. Keys are Ed25519, generated at first start, stored encrypted at rest with a passphrase from the environment or a prompt; private bytes never cross the pipe.

```ts
type KeyRole = "ledger" | "decision" | "capability" | "attestation" | "control" | "erasure";   // registry key: (tenant, role)
type SignRequest =
  | { tenant: TenantId; role: "ledger"; oldSize: number; consistency: Hash[]; checkpoint: string }            // the note body (3 lines)
  | { tenant: TenantId; role: "decision"; payloadType: string; payload: Raw; leafProof: InclusionEvidence }   // DSSE PAE input
  | { tenant: TenantId; role: "capability"; contract: Raw; approvalProofs: InclusionEvidence[] }              // JCS body of an ExecutionContract; one proof per approval leaf
  | { tenant: TenantId; role: "attestation" | "control"; payloadType: string; payload: Raw; leafProof?: InclusionEvidence }   // M8 C4 attestations, C14 kill state
  | { tenant: TenantId; role: "erasure"; receipt: Raw; requestProof: InclusionEvidence };                     // component 14
interface InclusionEvidence { leafBytes: Raw; index: number; proof: Hash[]; checkpoint: string }
type SignResponse = Result<{ sig: Raw; keyId: string }, "REFUSED_INCONSISTENT" | "REFUSED_NO_LEAF" | "REFUSED_POLICY" | "KEY_LOCKED">;
```
Role policies. **Ledger:** verify the request's consistency proof against the stored last-signed state, require `size >= last`, require the note body to be exactly origin, size, root with no extension lines, persist the new state atomically before returning the signature. **Decision:** the payload must be an in-toto Statement whose predicate names a `decision.final` leaf; the request carries that leaf and an inclusion proof to a checkpoint **the signer itself has already signed**; so a decision cannot be signed unless it is in the log. **Capability** (INT-016, INT-017): the signer signs exactly one object, an M12 `ExecutionContract` whose `scope.capabilities` is `["act/po.release"]` and whose `scope.release` is M8's `ReleaseBinding`, as a DSSE envelope with payload type `application/vnd.plumbline.release-capability+json` over the JCS body (the `plumbline/contract/v1` HMAC encoding is refused: `alg_not_allowed`). The policy is a **conjunction**: (a) each entry of `ReleaseBinding.approvals` carries an inclusion proof of its `approval.granted` leaf in a checkpoint the signer already signed, and `approvalSetHash` matches; (b) M8's check that each approval's WebAuthn assertion challenge equals `H(body without approvals)`, with distinct subjects; (c) `aud` equals `broker:<tenant>:<adapter>:<restoreEpoch>` for the current restore epoch, `exp - nbf <= 120 s`, and a 128-bit `nonce` the signer has not seen for this tenant; (d) M13's `G-FRESH` (fact-set, list and vendor-master versions current) was evaluated by the case manager before the request and is evaluated again by the broker at execution, because the signer cannot read the ERP and is not given that power (residual stated in M8 C19). Single use is consumed by M13's `NonceStore.consumeAndRecordIntent`, not by the signer. **Attestation and control:** M8's policies for attestations (C4) and the kill state (C14), enforced here as role-to-payload-type allowlists plus the proof rule where they name a leaf. **Erasure:** the request names an `erasure.requested` leaf (inclusion proof), and the receipt's `holdCheck` is re-derived by the eraser, not trusted (component 14). Roles never share a key and a payload type outside the role's allowlist is `REFUSED_POLICY`. This answers SEC-09 and the "same boundary as the ledger signer" sentence of spec 14a with a mechanism.

**Checkpoints.** Body is the three C2SP lines. Signed with the ledger key as an Ed25519 log signature (type `0x01`, key name equals the origin). Cosignatures from witnesses are added as further lines (component 5). Extension lines are never used, because they "are neither auditable ... nor signed in all signature algorithms" (R1).

**Cadence.** `ledger.cadence` (written at genesis and on change) declares `maxLeaves` (default 256) and `maxSeconds` (default 300). A checkpoint is also published after every `decision.final`. The verifier, given a clock reading (`--now`, default system time) and the newest time it can trust (a witness cosignature timestamp or a timestamp-authority time, never the `at` of a leaf), reports `V4.CADENCE_EXCEEDED` (INDETERMINATE) when the newest trusted time is older than the declared cadence plus the relying party's grace. A silent log is therefore a missed promise, not an absence.

**Key rotation as signed leaves.**
```ts
interface KeyRotated { role: KeyRole; oldKeyId: string; newKeyId: string; newPublicKey: string /* b64 */;
  effectiveFromSize: number; reason: "scheduled" | "suspected_compromise" | "ceremony";
  possession: string /* Sign_new("plumbline.key.rotate.v1" || oldKeyId || newPublicKey || effectiveFromSize) */ }
```
The `key.rotated` leaf is logged; the checkpoint that first covers it is signed by **both** old and new ledger keys (the C2SP format allows several signature lines for one name with different key ids); later checkpoints use the new key. A relying party holding the old key can follow the chain when its pins say `followRotations: true`; otherwise a checkpoint signed only by an unpinned key is `V3.CHECKPOINT_SIGNER_NOT_PINNED`. A stolen key cannot revoke itself credibly: `key.revoked` records the event, but recovery is an out-of-band re-pin and the relying party's `revokedKeyIds` list. Forward-secure ratcheting (Schneier and Kelsey) is not adopted; time-stamp anchors do the equivalent job at lower complexity (13 §2.5).

### 6.5 Tests and acceptance
`T-SIGN-01` consistent extension signed; a forked checkpoint of the same size, a smaller size and a wrong-origin note all refused. `T-SIGN-02` crash between "persist state" and "return signature": restart never signs a checkpoint inconsistent with a signature it may have emitted (state is written before the signature is released). `T-SIGN-03` decision role refuses a payload whose leaf is absent, whose proof targets a checkpoint the signer has not signed, or whose leaf belongs to another case. `T-SIGN-04` capability role refuses a repeated nonce, an approval without an inclusion proof, an `approvalSetHash` mismatch, a wrong `aud` or restore epoch, a lifetime over 120 s and any payload type outside its allowlist; `T-SIGN-07` a key of tenant A never signs a request naming tenant B, and each role's key refuses the other roles' payload types. `T-SIGN-05` Wycheproof Ed25519 vectors (R13) against the `node:crypto` verify path used by all six roles and by the verifier (**NOT VERIFIED** which edge cases, such as non-canonical S, Node accepts; the test decides, and the verifier adds its own canonical-S check if needed). `T-SIGN-06` rotation: pinned old key follows the chain; unpinned new key alone fails; a rotation leaf with a bad possession proof fails. Metric: signer round trip time (p50, p99), reported.

### 6.6 Risks and NOT VERIFIED
Passphrase handling on a judge machine (no secrets in the repo; the sample bundle uses a published throwaway key and says so in `nonClaims`). Windows key-file ACL enforcement unverified. The Node permission model flags for sandboxing the signer are **NOT VERIFIED** for the pinned Node line (the spec states the same for the extractor).

### 6.7 Build notes
Signer with only the ledger role first (needed for component 2 flush; build-order step 8a, with JCS, DSSE and the ledger core, before step 6), then decision, then the capability, attestation and control roles that M8 and M12 need at step 6 (the register's V5 correction), the erasure role with component 14.

## 7. Component 5: Witnessing and anchoring (stage 2)

### 7.1 Best references
R1 `tlog-witness`, `tlog-cosignature`, `tlog-policy`, `tlog-proof`; R5 (witness implementation and public network); R11 (RFC 3161, FreeTSA, `digitorus/timestamp` as oracle R22); R12 (OpenTimestamps); 13 §2.2, §2.9 and the pitfalls table. Evaluation limits: the public witness network states "Work in progress"; whether a third party can join as a log, and on what terms, is **NOT VERIFIED**; FreeTSA states no terms, rate limit or SLA; OpenTimestamps clients are unmaintained since 2023 and 2025, and calendar availability was not tested.

### 7.2 What they actually do
`tlog-witness` (read): the log POSTs `old <size>`, up to 63 consistency proof lines, a blank line and the checkpoint; the witness verifies log signatures for the origin, checks consistency with the one latest checkpoint it holds, persists, and returns a timestamped cosignature; 404 for unknown origin, 403 for a missing trusted signature. `tlog-policy` (read): a policy lists logs, named witnesses and `group` thresholds and exactly one `quorum` line (`quorum none` for no cosigning); the log vkey's name "MUST correspond to the log's origin"; duplicate keys are rejected; at least 32 logs, witnesses and groups should be supported. `tlog-proof` (read): a self-contained proof is `index`, the inclusion hashes, a blank line and a checkpoint with cosignatures; the verifier needs the leaf contents and a set of trusted keys. Read in OpenTimestamps `notary.py`: a Bitcoin attestation carries a block height; the commitment digest is the block header's merkle root, and `verify_against_blockheader` requires the caller to supply the header and raises if the digest differs. RFC 3161 (fetched): the token is CMS SignedData, the verifier must check the message imprint, the nonce when sent, the signing certificate identifier, and a critical `id-kp-timeStamping` extended key usage on the TSA certificate.

### 7.3 Decision
Stage 1 (committed scope): none of this is produced, but **the verifier core already parses and evaluates cosignatures and `tlog-policy` quorums** (they are pure Ed25519 checks), so stage 2 adds producers only. Stage 2, each item gated: (a) **witness-lite**, our implementation of the `add-checkpoint` protocol in a separate process with its own key, labelled `witnessIndependence: none` unless run by another operator or host (13 §4.2: a co-located witness gives no independence); (b) **RFC 3161** against at least two timestamp authorities of different operators; (c) **OpenTimestamps**. An item ships only with an offline verification test and the availability evidence below; otherwise it is dropped and the drop is recorded in the bundle's `nonClaims`. Public witness network: apply only after its admission process is read and verified; until then no claim. Rejected: a blockchain transaction per checkpoint (cost and disclosure for no gain over batched OpenTimestamps, 13 §6); committing the checkpoint hash to the public repository as a "timestamp" (commit times are author-asserted and not offline-verifiable; it may still be done as a convenience, never counted).

### 7.4 Implementation design

**What is stamped.** The SHA-256 of the checkpoint note body (the three lines, including the final newline). Anchors are **attachments**: self-authenticating files bound by hash to a checkpoint, stored under `anchors/<size>/` and packaged under `attachments/` in a bundle (component 6). They can be added or upgraded after the bundle is signed without changing its digest.

**Witness quorum evaluation** (in the verifier core, pure):
```ts
interface TlogPolicy { logs: VKey[]; witnesses: Map<string, VKey>; groups: Map<string, { k: number; members: string[] }>; quorum: string | "none" }
declare function parsePolicy(text: string): Result<TlogPolicy, PolicyError>;       // exact C2SP syntax, limits 32/32/32 at least
declare function quorumSatisfied(p: TlogPolicy, cosignedBy: Set<string>): boolean;  // recursive threshold
```
Cosignature verification builds the signed message from the checkpoint lines and the timestamp; timestamps in the future (relative to `--now`) are rejected; the newest cosignature timestamp feeds the cadence check.

**RFC 3161 job** (producer, asynchronous, never blocks append): after each published checkpoint, request a token from each configured TSA (SHA-256 imprint, `certReq` set, a random nonce), store the raw `.tsr`, write `anchor.recorded`. **Offline verification** (an optional zero-dependency module, `verify-anchors`, shipped as a separate file so that the core stays small): minimal DER reader; extract `TSTInfo`; require imprint equals the checkpoint-body digest, `genTime` parsed, nonce irrelevant offline; verify the CMS signature over the signed attributes (re-tagged as a DER SET, the classic pitfall) with `node:crypto`; check `messageDigest` attribute equals the digest of `TSTInfo`; check the signing certificate against the relying party's pinned TSA roots, require the critical timestamping EKU, and check certificate validity at `genTime`. Revocation is not checked offline and the report says so. Pins: `tsaTrust.rootsPem[]`.

**OpenTimestamps job.** Submit the same digest to calendars; the first proof is a pending attestation, upgraded after Bitcoin confirmation (hours). **Offline verification:** parse the proof (ops with the tags read in R12, attestation tags `0588960d73d71901` for Bitcoin and `83dfe30d2ef90c8e` for pending), apply the operations to the digest, and for a Bitcoin attestation require the relying party to supply the 80-byte block header for that height through pins (`bitcoin.headers`); compare the computed digest to the header's merkle root (byte-order as in R12) and check the header's proof-of-work against its `nBits`. The header must come from the relying party's own source: the verifier cannot know the chain. Without a header the result is INDETERMINATE (`V4.OTS_HEADER_NOT_SUPPLIED`); a pending attestation is INDETERMINATE (`V4.OTS_PENDING`); neither is PASS. Time reported is the header timestamp, which miners set loosely, so it is "not later than" and never an exact time.

**Gates for stage 2.**
- Witness-lite: the cosignature of a real run verifies in all three verifier implementations; a witness that was handed a forked checkpoint refuses (409 analogue); quorum edge cases from `tlog-policy` pass. Gate for any independence claim: a cosignature from a host under another operator.
- RFC 3161: tokens from two TSAs for 200 consecutive checkpoints with a success rate and latency distribution written to `eval/reports/anchors.md` (the number is recorded, not pre-judged); the offline verifier accepts them against the published certificate chain; the mutation set (imprint changed, signature bit flipped, wrong EKU, expired certificate, wrong root) is rejected. FreeTSA's published certificate hashes (R11) are pinned in test fixtures. If a TSA has no stated terms (FreeTSA), the report says so, and a second TSA is required.
- OpenTimestamps: one real proof, upgraded to a Bitcoin attestation, with a real header as a test fixture (public data), verifies offline; a flipped proof byte and a wrong header fail. If calendar access or upgrade fails during the build, OTS is dropped.

### 7.5 Tests and acceptance
`T-ANC-01` policy parser against the R1 example and its edge cases (duplicate key, unknown name in group, circular reference, missing quorum, non-ASCII names as opaque octets). `T-ANC-02` cosignature verification with generated witnesses: k-of-n, nested groups, one bad signature among good ones, timestamp in the future. `T-ANC-03` RFC 3161 differential: our verifier against `openssl ts -verify` (availability on the build machine **NOT VERIFIED**) and R22 on the same tokens. `T-ANC-04` OTS operations fuzzed (bounded op length 4096 and recursion depth as in R12). `T-ANC-05` anchor mutation cases are rows of the tamper corpus (component 12).

### 7.6 Risks and NOT VERIFIED
Everything about third-party availability and licensing; LGPL means we read the format but write the code ourselves; the OTS format has no specification file that I found, so the reader is derived from R12's source and must be tested against real proofs; how TSAs handle high request rates unknown.

### 7.7 Build notes
Policy parser and cosignature verification (stage 1 verifier work), then witness-lite, then RFC 3161, then OTS. Stage 2 cannot start before the stage 1 gate (tamper corpus with pins) passes.

## 8. Component 6: Bundle layout, manifest, deterministic tar, attachments

### 8.1 Best references
13 §4.1 (layout) and §4.6 (git object fan-out, CAR rejected), R7 and R8 (envelope), Sigstore bundle (13 §2.7: "everything required to verify, in one file"), sigstore/model-transparency (13 §3.9: manifest of file hashes in a DSSE statement), R9 (spec-clause naming), RO-Crate and PROV as projections (13 §3.7, §3.8). Evaluation limit: none of these describes member classes that are verifiable without being covered by the manifest (anchors), or tiered disclosure.

### 8.2 What they actually do
Sigstore bundles one file with verification material and content; model-transparency signs a manifest of file hashes inside a DSSE envelope with an in-toto statement (both 13, read from pages). R8 (read): each subject must carry `digest`; `predicateType` is required.

### 8.3 Decision
**Adapt.** A deterministic **tar** (ustar) of a directory; the manifest `bundle.json` is the authority and the DSSE statement's subject is its digest. Tar over zip: zip has a central directory and local headers that can disagree, which gives two parsers two answers; a plain tar read into memory and indexed has one reading. The verifier never extracts to disk (no path-traversal surface) except in evidence mode, where it only reads.

### 8.4 Implementation design


The verifier itself is **not** a member of the bundle; the manifest names only `verifierMinVersion` (AUD-02: a verifier shipped inside the bundle starts from code the bundle author chose).

**Manifest.**
```ts
interface Manifest {
  schema: "plumbline.bundle/v1"; caseId: string; decisionId: string; tenant: TenantId;
  tier: { audience: Audience; disclosure: Disclosure };   // the four tiers are (reviewer, full), (auditor, full), (auditor, redacted), (counterparty, notice); INT-008
  verifierMinVersion: string; asOf: Iso;
  members: { path: string; digest: RawHash; size: number; role: MemberRole; conf: Confidentiality; disclosure: "full" | "hash-only" | "withheld" | "erased"; mediaType: string }[];
  attachmentsDir: "attachments/";             // everything under it is self-authenticating, none of it is listed
  bindings: { memberPath: string; leafType: LeafType; field: "subject" | "payload" }[];   // which member must equal which leaf
  nonClaims: string[]; assumptions: string[];

```
`MemberRole` is a closed set: `manifest | envelope | decision | inputs | claims | certificates | policy | evidence-index | evidence-blob | evidence-stub | textlayer | spans | findings | layer-geo | raster | cassette | trace | ledger | tier-reveal | erasure-receipt | view | readme`; a role outside the set is `V0.MEMBER_SET` FAIL. Member `disclosure` carries the per-member content mode that the earlier `disclosurePolicy` field carried at bundle level, which `tier.disclosure` now replaces.

**Member roles and the binding graph.** The manifest, DSSE and ledger are tied together so that rewriting one layer needs rewriting the others, and the ledger layer needs the log key. Bindings (checked by V3): `policy/policy.bundle.json` equals the `policy.published` leaf subject; `decision/record.json` equals `decision.final`; `replay/cassette.manifest.json` equals `replay.cassette`; each `evidence/index.json` record commitment equals an `evidence.fetched` leaf subject; the trace segment heads equal `trace.segment` leaves; certificates equal `stage.committed` for stage `explain`. A producer or insider with the decision key but without the log key cannot make a consistent alternative bundle.

**Deterministic tar.** ustar; entries sorted by bytewise path order; regular files only; mode 0644; uid, gid 0; mtime 0; no PAX or GNU extensions; no directory, link or device entries; name at most 255 bytes through prefix and name; ASCII path characters `[a-z0-9._/-]` only, no empty or `.` or `..` segment, no leading slash or backslash, no case-insensitive duplicates, no Windows reserved names; checksum field validated; two zero blocks at the end; any unknown typeflag is a FAIL. Size limits from component 1 apply to declared sizes before reading and to actual bytes while reading; a gzip wrapper (for transport) is accepted only with an inflation ratio limit.

**Evidence modes at pack time.** `evidence/index.json` records, per item: `disposition` in `body | stub | stub-evidence-mode | erased`; `redistributable` flag (from M1 rights gate); for stubs, the raw-body `bodyHash` (a `RawHash`, public sources) or a `Commitment` (component 13); the **locator** in the shared `Locator` shape (`unit: "codepoint"`, `docSha`, `layerId`, `revision`, and for `textlayer` also `byteStart`/`byteEnd`) and its **resolver kind**, from the closed set the verifier implements: `bytes` (byte range of the raw body), `json-pointer`, `csv-cell`, `textlayer` (range in a page of the owned text layer, whose digest is `textLayerHash`). A parser-free locator is one of these four. A PDF's raw bytes cannot be resolved without a parser, but a rights-gated PDF reaches V5 through the `textlayer` resolver when the derived layer member ships (the `layer-only` viewer state); the source PDF need not (Spec feedback F13).

**Certificate vocabulary (XPL-07, INT-001).** M4 certificates carry a producer-side outcome `VALID | INVALID | INCONCLUSIVE` (`CertOutcome`) and a `vRef = { policyDigest, kernelDigest, vSpecHash, ledgerSnapshotDigest }`. The verifier's own results are `PASS | FAIL | INDETERMINATE | NOT_APPLICABLE` (`Verdict`); the two vocabularies share no word. The mapping is fixed: a certificate whose re-check agrees with its producer outcome is PASS (even when the outcome is INVALID or INCONCLUSIVE, the verifier PASSes the *check*, and reports the producer outcome as data); a re-check that disagrees is FAIL; one that exceeds the oracle budget is INDETERMINATE.

### 8.5 Tests and acceptance
`T-BUN-01` the same ledger and case yield a byte-identical tar on two machines (deterministic builder); `T-BUN-02` every path rule has a reject vector; `T-BUN-03` the binding graph: for each binding, changing the member (and re-hashing it into the manifest and re-signing with the decision key) fails V3; `T-BUN-04` attachments added after signing do not change `manifest` digest and verify; a corrupt attachment fails; `T-BUN-05` builder refuses to emit a bundle whose `published` checkpoint does not cover `decision.final`; `T-BUN-06` a derived member (`spans.json`, a raster) altered after signing fails V0 against its manifest digest; a tier that omits rasters lists them as `withheld` members, and the verifier's chain never reads them.

### 8.6 Risks and NOT VERIFIED
Bundle size for large corpora of evidence; tar handling differences between Python's `tarfile` and Go's `archive/tar` for malformed headers (the strict reader is our own in each language); the 255-byte path ceiling with fan-out paths is fine but unverified at scale.

### 8.7 Build notes
Builder after components 2, 3, 4 and 7; verifier work in parallel from the spec.

## 9. Component 7: DSSE envelope and the decision predicate

### 9.1 Best references
R7, R8, 13 §3.3 and §3.4 (SLSA-shaped predicate), R10 (receipt drafts: our predicate must not claim what they disclaim), R9 (domain-separated preimage, null versus absent). Evaluation limits: in-toto subjects are artefacts and this subject is a manifest; SLSA assurance levels are not claimed.

### 9.2 What they actually do
R7 (read): `payload` (base64), `payloadType`, `signatures[]` with `keyid` and `sig`; the signature covers PAE `"DSSEv1" SP LEN(type) SP type SP LEN(body) SP body`; **"Producers ... MAY add additional fields. Consumers MUST ignore unrecognized fields"**; either standard or URL-safe base64 is allowed; `keyid` may be unset; implementations MUST NOT re-parse the envelope after verification to obtain the payload. R8 (read): `subject[]` entries need `digest`; `predicateType` is a required TypeURI.

### 9.3 Decision
**Adopt the formats, constrain them.** Payload type `application/vnd.in-toto+json`. Our profile is stricter than DSSE: standard base64 only, canonical padding, unknown envelope fields ignored but reported, exactly one signature in a decision envelope (a second signature means a different envelope, not a longer one), `keyid` treated as a hint and never as trust. The predicate type is **our own URL**, never a borrowed domain: `<ns>/predicate/decision/v1` where `<ns>` is the namespace constant of section 10.4. The URL document (the predicate specification) is published with the verifier specification; the verifier compares the string exactly and rejects any other `predicateType` for a decision statement.

### 9.4 Implementation design
```ts

  _type: "https://in-toto.io/Statement/v1";
  subject: [{ name: "bundle.json"; digest: { sha256: string } }];
  predicateType: string;                // == PREDICATE_TYPE_V1
  predicate: {
    schema: "plumbline.decision/v1"; caseId: string; decisionId: string; tenant: TenantId; tier: Manifest["tier"];
    decision: { action: Action; autonomy: AutonomyLevel; approval: "none" | "pending" | "granted" | "denied" };
    externalParameters: { caseDigest: DocHash; asOf: Iso; requestedAction: string };
    internalParameters: { policyDigest: DocHash; kernelDigest: DocHash; vSpecHash: DocHash; runtimeCommit: string; models: { id: string; paramsDigest: DocHash }[]; budgetsDigest: DocHash; semconv: string };
    resolvedDependencies: { role: "evidence-index" | "cassette" | "trace" | "policy" | "schemas" | "prompts"; digest: { sha256: string } }[];
    ledger: { origin: string; checkpoint: { size: number; root: Hash }; stream: StreamId; firstSeq: number; lastSeq: number; streamHeadLeafHash: Hash; decisionFinalIndex: number };

```
Verification order (V2): decode the envelope with strict base64; check that `payloadType` is exact; build PAE from the **decoded bytes**; verify the signature against pinned keys; only then parse those same bytes with the strict parser and check that they equal their own canonical form; then check statement fields; then check `subject[0].digest.sha256` equals the digest of `bundle.json` as read from the tar. `nonClaims` are fixed strings drawn from spec 9a (examples: "sources are as retrieved by this system and not attested by the source", "model outputs are recorded, not proven correct", "approval timing is as logged", "the producer's policy is not judged right") and the verifier prints the producer's list but never relies on it.

### 9.5 Tests and acceptance
`T-ENV-01` PAE vectors including a payload type containing spaces and a payload containing the literal `DSSEv1`; `T-ENV-02` envelope malleability: URL-safe base64, missing padding, extra fields, two signatures, reordered members; each must produce the specified verdict; `T-ENV-03` predicate type string compared byte for byte, trailing slash and case variants rejected; `T-ENV-04` payload bytes not canonical but otherwise valid: V1 FAIL; `T-ENV-05` an off-the-shelf DSSE/in-toto parser (sigstore-js, R in 13 §2.7) can read the envelope (credibility check, not part of the verifier).

### 9.6 Risks and NOT VERIFIED
Predicate namespace is undecided (section 10.4). No existing tool understands our predicate; interoperability means "parses as an in-toto statement". Whether signing the manifest digest rather than a build artefact misleads in-toto tooling is untested.

### 9.7 Build notes
Envelope code is small; build with component 6 and the signer decision role.

## 10. Component 8: Trust model, pins, tri-state verdicts, reason codes, report

### 10.1 Best references
10.1.a: R10 (the EQR draft's PASS, FAIL, INDETERMINATE outcome and its sentence that a PASS receipt "is never itself permission to execute"; the noa draft's explicit non-claims), R1 `tlog-policy` and `tlog-proof` (a relying party's trust is a *policy file* of keys and a witness quorum, not something carried inside the proof), R16 (the skeptical client holding an earlier checkpoint), spec 9a, R9 (named clause per reject case). Evaluation limit: the drafts name outcomes but ship no verifier with reason codes; our code table is original work.

### 10.2 What they actually do
`tlog-proof` (read) states that the verifier "needs the public keys for origin lines it is willing to accept, as well as the public keys for some witnesses", and "which subsets of witnesses are considered strong enough, is determined by application policy". `tlog-policy` is exactly that policy language. The EQR draft (13 §3.1, read from the page) separates an outcome from authorisation.

### 10.3 Decision
**Adapt** `tlog-policy` as the log-trust half of our pins file and **own** the rest. Rejected: trust inside the bundle (AUD-02); a numeric score (non-actionable); a boolean (loses the distinction between "wrong" and "could not check").

### 10.4 Implementation design

**Results and aggregation.** Each check yields `PASS | FAIL | INDETERMINATE | NOT_APPLICABLE` plus a reason code. FAIL means the artefact contradicts itself or the pins (evidence of tampering or a producer bug). INDETERMINATE means a check in the chosen profile could not be completed because **an input the relying party could have supplied is missing** (pins, earlier checkpoint, evidence body, block header, reveals) or a declared budget ran out. Everything the verifier can never reach is not a verdict at all: it is an **assumption line** (the "not established" column of spec 9a). The bundle verdict is FAIL if any check FAILs; otherwise INDETERMINATE if any required check is INDETERMINATE; otherwise PASS. A check that is missing from the report counts as FAIL (`V0.CHECK_NOT_RUN`), and an uncaught exception ends the run with exit code 70 and no verdict, never PASS. Exit codes: 0 PASS, 1 FAIL, 2 INDETERMINATE, 64 usage error, 70 verifier error.

**Profiles.** `--profile full` (default): V0 to V8 required where inputs exist. `--profile integrity`: V0 to V4 only. A profile never turns a FAIL into anything else; it only chooses which INDETERMINATE conditions block PASS.

**Pins** (the relying party's file, never read from the bundle):
```ts
interface PinsV1 {
  schema: "plumbline.pins/v1";
  decisionSigners: { vkey: string; label: string }[];       // Ed25519, with key id; validity follows rotation leaves
  logPolicy: string;                                         // verbatim C2SP tlog-policy text (log vkey, witnesses, quorum)
  witnessIndependence: { [witnessName: string]: "none" | "same_owner_separate_host" | "third_party" };  // printed, never inferred
  followRotations: boolean; revokedKeyIds: string[];
  earlierCheckpoint?: string;                                // a signed note the relying party saw before
  requireWitnessQuorum: boolean;                             // default true iff logPolicy quorum != none
  tsaTrust?: { rootsPem: string[] }; bitcoin?: { headers: { height: number; hex: string }[] };
  requireAnchors?: ("rfc3161" | "ots")[];
  acceptedPolicyDigests?: DocHash[];                         // if present, V6.POLICY_BIND fails on any other
  cadenceGraceSeconds?: number;
}
```
Without `--pins`, the verifier evaluates every signature against the bundle's *suggested* keys so that accidental corruption is still caught, prints the key fingerprints, and sets the trust mode to `self_supplied`: V2 and V3 signature checks and anything that needs trust yield INDETERMINATE (`V2.TRUST_SELF_SUPPLIED`), and the bundle verdict cannot exceed INDETERMINATE. **Re-sign with a fresh key:** without pins the result is INDETERMINATE; **with** pins it is FAIL (`V2.SIGNER_NOT_PINNED`), because the pins say which keys are acceptable and this one is not. Spec 13 names only the first case; both are corpus rows (Spec feedback F2).

**Currency.** A bundle is a statement as of one checkpoint. The report always prints `currency: not shown after checkpoint <size>` unless the relying party supplies later entries (`--ledger-dir` or `--later <attachment>`), in which case the verifier checks consistency to the later checkpoint and scans the case stream for `decision.retracted`, `case.reopened` and `erasure.completed`; a retraction yields FAIL `V4.SUPERSEDED` for a profile flag `--require-current`, otherwise a report line. Spec 9a has no row for log completeness and currency (Spec feedback F15).

**Predicate namespace (decision for Prateek).** The predicate type URL and the checkpoint origin need a namespace we control. No domain or organisation is chosen yet. Interim constant `PLB_NS = "https://predicate.plumbline.invalid"` (RFC 2606 `.invalid`, cannot resolve or collide); the constant lives in one file, and both strings change together before the first public bundle exists. Changing it after publication means a new predicate version.

**Reason codes.** Stable ASCII `<checkId>.<REASON>`; registry `reason-codes.json` with fields `code`, `result` (FAIL or INDETERMINATE), `clause` (the spec clause it guards), `message` (fixed text), `mutations` (ids of corpus rows that exercise it). Two registry lints: every code is exercised by at least one corpus mutation, and every check has at least one mutation expected to fail it (a check that never fails is untested, the inert-control rule of spec 19).

A3 the pins were obtained from the producer or the log operator through a channel the attacker did not control. A4 the verifier code is the published code (digest compared out of band). A5 any witness or anchor claimed was operated independently of the producer, as labelled in the pins. A6 the producer's keys were not compromised before the earliest checkpoint or anchor the relying party holds. A7 the bundle is current only through the stated checkpoint.

### 10.5 Tests and acceptance
`T-TRUST-01` no pins: every sample bundle yields INDETERMINATE, never PASS, and the report prints the fingerprints; `T-TRUST-02` pins present, correct: PASS; `T-TRUST-03` pins present, fresh key: FAIL `V2.SIGNER_NOT_PINNED`; `T-TRUST-04` wrong log origin in pins; `T-TRUST-05` pins with revoked key; `T-TRUST-06` a deleted check row yields FAIL, not PASS; `T-TRUST-07` wording lint on every string in `reason-codes.json` and in report templates (forbidden: "proved", "by construction", "guaranteed", "tamper-proof" outside a sentence citing a 9a row); `T-TRUST-08` registry coverage lints above. The mapping table from checks to 9a rows needs a reviewer's agreement; it is part of the verifier specification and audited against the live spec.

### 10.7 Build notes

## 11. Component 9: Verifier core, V0 to V5

### 11.1 Best references
R2 (proof algorithms and their strict length rules), R1 (all note, checkpoint, cosignature, policy and proof rules), R7 (verify the exact bytes), R9 (reject corpus; independent SDKs), R16 (skeptical client), 13 §4.1 (level table), R18 (checking is cheaper than finding). Evaluation limit: none of these includes a verifier that checks claim quotes, tiered disclosure or evidence mode; R9's three SDKs share one author (13 §3.1), which is the correlated-failure problem spec 13 solves with a clean-room build.

### 11.2 What they actually do
`proof/verify.go` (read) is a pure function over hashes with exact length checks; `tlog-proof` (read) lists the verification steps: leaf hash, origin and log-key check, cosignatures against the policy, inclusion proof.

### 11.3 Decision
**Own**, zero dependencies beyond `node:` built-ins (`node:crypto`, `node:fs`, `node:path`, `node:process`; no `node:child_process`, no network modules). Single ES module produced by deterministic concatenation of source files (no bundler, no minification) so the published digest is of readable code. Shares no code with the producer. **Scope of the core (INT-051):** V0 to V4a, V5 for parser-free locators, and V6 to V8 through the recompute module (component 10), which is part of the `full` profile and loaded by the same entry point; V4b (anchors) is a separate file. Rejected: reusing the producer's tile reader; loading a JSON-schema library: V1 `SCHEMA` uses the **PSP restricted schema dialect** (M7 component 3), interpreted by a verifier-local interpreter of about 250 lines per language, differential-tested against the pinned validator and compared to golden schema hashes.

### 11.4 Implementation design

```ts
// Entry point (pure core + thin host). Host adapters supply bytes and clocks; the core never touches fs.
interface Host { readBundle(path: string): Result<Map<string, Raw>, IoError>; readEvidenceDir?(dir: string): Map<Hash, Raw>; now(): number; sha256(b: Raw): Raw; ed25519Verify(pub: Raw, msg: Raw, sig: Raw): boolean }
declare function verifyBundle(h: Host, opts: { pins?: PinsV1; profile: "full" | "integrity"; evidenceDir?: string; requireCurrent?: boolean; later?: Raw[] }): VerifyReport;
```
**Algorithm by level** (each step emits report rows; later steps whose inputs failed emit `INDETERMINATE` with reason `DEP_FAILED:<checkId>`).

*V0 container.* Read the tar into an in-memory index under the limits of component 1; apply the path rules; compare the file set to `bundle.json.members` exactly (extra or missing member FAIL), compare size then `rawDigest`; classify everything under `attachments/` (allowed types: `cosigs`, `rfc3161`, `ots`, `later`; an unknown name or type FAIL `V0.ATTACHMENTS`); check `schema` and `verifierMinVersion` against the running version. `bundle.json` itself is read raw before parsing so that V2 compares its digest.

*V1 form.* Strict-parse every JSON member and `entries.jsonl` lines; the stored bytes must equal `jcs(parse(bytes))` for members declared canonical (all but `README.txt`, the cassette body and evidence blobs); validate documents against embedded PSP schemas, including that every digest field carries the prefix of its declared kind (`RawHash`, `DocHash`, `Commitment`); for committed documents (component 13) check each presented reveal against its commitment (`V1.COMMITMENTS`).

*V2 envelope.* As specified in component 7 and the order given there. Key selection: pinned `decisionSigners` whose validity (from rotation leaves, after V3) contains the decision's ledger position; the `KEY_WINDOW` check is therefore evaluated after V3 and reported at level V2.

*V3 ledger membership.* Parse the checkpoint note: exactly three body lines then the blank line and signature lines; origin must equal `predicate.ledger.origin` and the pinned policy's log origin; verify signature lines whose key name and id match a known key (ignore unknown, require at least one valid known signature, reject if a known key's signature is invalid, as `signed-note` requires). For each leaf in `entries.jsonl`: require `tenant` to equal the tenant named by the origin and the manifest; compute `jcs(leaf)`, the leaf hash, and verify inclusion at its index against the checkpoint size and root with **exact proof length**; check stream rules over the leaves present: `seq` is consecutive from the lowest present value through the highest, `prev` equals the previous leaf's hash, the first `seq` is 0 (the full case stream is always bundled), the `decision.final` leaf is present at the index stated in the predicate, and `streamHeadLeafHash` equals the last leaf. Check each manifest binding (member digest or commitment equals the named leaf field).

*V4 extension and anchors.* `CONSISTENCY`: the bundle's `consistency.json` from the checkpoint covering `case.opened` to the bundle checkpoint; and, if `earlierCheckpoint` is pinned, a consistency proof from it (supplied via `--later` or as an attachment) with the exact C2SP rules (earlier size at least 1). `WITNESS_QUORUM`: evaluate the cosignatures in the checkpoint note and `attachments/cosigs` against `logPolicy`; unmet quorum with `requireWitnessQuorum` is INDETERMINATE (`V4.QUORUM_NOT_MET`) when no cosignature is invalid, FAIL when a cosignature from a known witness is invalid. `CADENCE`: as component 4. Anchors: `verify-anchors` as component 5; absent anchors are INDETERMINATE only if `requireAnchors` names them. `SUPERSESSION`: as section 10.4.

*V5 evidence.* For each evidence item cited by a claim: obtain the body (bundle blob, or in evidence mode a file in `--evidence-dir` whose `rawDigest` equals the recorded `bodyHash`; the verifier hashes every file in the directory once and indexes by digest, with a file-count and byte cap; a file with the right name and the wrong content never matches); if no body is available, `V5.EVIDENCE_BODY` is INDETERMINATE with reason `HASH_ONLY`, `ERASED`, `WITHHELD` or `EVIDENCE_NOT_SUPPLIED`. With a body, resolve the locator through the closed resolver set to bytes. For a `textlayer` locator the canonical unit is the **code point** (page-relative offsets `start`/`end` over the unnormalised visible layer, M2) and the locator also carries UTF-8 `byteStart`/`byteEnd` into the same page text (INT-004). The verifier needs no Unicode logic: it slices bytes `[byteStart, byteEnd)`, requires both ends to sit on code-point boundaries (a byte is a boundary unless its top two bits are `10`), requires the slice to equal the quoted bytes and its `RawHash` to equal the recorded `spanSha`, and requires the number of code-point-start bytes before `byteStart` to equal `start` and the count inside the slice to equal `end - start`; any disagreement is FAIL `V5.LOCATOR_UNIT_MISMATCH`. It then runs the **normative L0 quote check** (exact, normalised with index map, ordered ellipsis; `near`, `misattributed` and `absent` are FAIL or, for `near`, a reported warning per M4's table) as specified in M4's L0 document with its own vectors. Numeric and date consistency are recomputed from the quoted spans. `CITATION_COVERAGE`: every claim citation resolves to an evidence id present in the index and a span present in the claim ledger; no claim cites an erased or absent item without a disposition. Page text boundaries inside the layer member are those of M2's layer format (NOT VERIFIED until DI-01 publishes it) (Spec feedback F5).

### 11.5 Tests and acceptance
`T-VER-01` positive vectors: every sample bundle yields exactly the expected report (verdict and per-check results) from all implementations; `T-VER-02` the R2 inclusion and consistency data and the tile cases through the verifier's own implementation; `T-VER-03` the R1 examples (note, checkpoint, cosignature, policy, tlog-proof) parsed and verified, with signatures regenerated from our own keys; `T-VER-04` import hygiene: the verifier source contains no import outside the allowed `node:` set (static check) and runs with the network permission denied where the pinned Node supports it; `T-VER-05` hostile input budget: a 1 GiB sparse tar, a 10^6-member tar, depth 10^5 JSON and a million-hash proof all end in FAIL within a stated time and memory bound; `T-VER-06` clean directory run: copy the verifier and a bundle to an empty directory with no `node_modules` and run it; `T-VER-07` locator-unit vectors shared with M2 DI-01 (astral characters, combining marks, a page that starts mid-layer, a slice ending inside a multi-byte character, a byte offset consistent with a wrong code-point offset) give the specified verdict in all implementations. Metrics: verification wall time for the sample bundle (target stated after measurement), peak memory, lines of code (non-test), and number of distinct reason codes exercised.

### 11.6 Risks and NOT VERIFIED
Node's `crypto.verify` behaviour on Ed25519 edge cases (T-SIGN-05). Browser support for Ed25519 in WebCrypto is irrelevant to the CLI but relevant to component 15. A single-file module is large; the review burden is part of why the code is split by level before concatenation.

### 11.7 Build notes

## 12. Component 10: Recompute module, V6 to V8

### 12.1 Best references
R18 (certifying algorithms: the checker must be small enough to read), 08 §1.1 and §1.8 (what `V` is, certificate shapes), 09 §9 (SMT cross-check of the policy), spec 10 (policy IR, two interpreters), XPL-07 (cap certificate size), AUD-01 (the contradiction this resolves). Evaluation limit: nothing in the 2026 receipt cluster recomputes a rule outcome; 08 and 09 describe the algorithms but the IR is provisional pending bake-off 2.

### 12.2 What they actually do
08 §1.8 (read): a flip certificate is the edit set `R` plus `V(E\R') = v*` for every proper subset; a sufficiency certificate is a Merkle-committed table of all `2^|E\S|` verdicts when `|E\S| <= 20`, otherwise the hitting-set trace; the trust base is "the pinned policy function and canonicalisation". AUD-01: flip recomputation needs reconcile, not only the rule engine.

### 12.3 Decision
**Own**, as a **separately loadable module that belongs to the `full` profile** (`verify-recompute`, same zero-dependency rules; INT-051) that interprets data, never code from the bundle. The inputs are data: the **policy IR** (M5; PPIR is the bundle format, with feature programs, the total action order `release ≻ release_with_approval ≻ escalate ≻ hold ≻ reject` and `needs: ActionClass` atoms), the **permission matrix** (`permission-matrix.json`, M8, hashed into the policy bundle, so a counterparty-authored `VERIFIED` field cannot satisfy an atom the matrix forbids; INT-014), the **label aggregation configuration** (M4 C9), the **reconcile kernel configuration** (M3: authority tables, per-attribute cardinality, date-window and precedence rules, tie-breaks) and the **recorded link decisions** (link, possible, non-link with the judged label, never the fuzzy score; recorded per pair, each edge's `inputs` being exactly the two mentions' assertions, so edge locality holds; a `locality: "set"` edge is flagged and its flips printed as possibly over-reported; INT-036). `V(S)` is M4's composition `phase2 ∘ phase1` (INT-034), interpreted as data: `phase1` = M3 `fuse` after label aggregation after M5 `featurize`, `phase2` = M5 `evaluate`. Stage A (fuzzy link scoring) is excluded from `V`. A certificate states exactly which `V`: `vRef = { policyDigest, kernelDigest, vSpecHash, ledgerSnapshotDigest }`, where `vSpecHash` hashes the three halves' versions plus the projection and is printed in every certificate. Rejected: embedding the TypeScript engine in the verifier (not a second implementation, shares bugs, breaks "no server code"); evaluating fuzzy scoring (cross-language floating-point drift at thresholds).

### 12.4 Implementation design

**Requirements placed on M5 and M3** (they are conditions for V6 to V8 to exist; see Spec feedback F9):
- The IR is JSON with total, pure semantics; all arithmetic is integer or fixed-point decimal strings (BigInt in JS, `int` in Python, `math/big` in Go); no floats; deterministic iteration order; explicit rule precedence; derived-feature functions come from a closed registry (days between dates, ratio of decimals, set membership, window sums) each with vectors, and everything else is an `SOR` input.
- The reconcile kernel configuration is data, and the resolution function is specified in prose with vectors (authority tier order, recency, cardinality, `unresolved` repair semantics), small enough for three implementers.
- The evaluator emits a derivation trace in M4's `DerivationTrace` form (content ids `nd_...`; M5 maps its richer DAG onto it), which is also what makes flip recomputation tractable.
- Bake-off 2's decision rule includes "interpretable by a dependency-free evaluator in two languages (about 500 lines each, differential vectors)" as a **gating criterion**, not a tie-breaker (INT-050): a candidate that fails it cannot be the normative policy format of a bundle. If Cedar or OPA wins on expressiveness it is an authoring front-end or CI cross-check, with PPIR as the bundle format.

```ts
interface RecomputeInputs { ir: PolicyIR; matrix: PermissionMatrix; labelAgg: LabelAggConfig; kernel: KernelConfig; assertions: Assertion[]; links: LinkDecision[]; evidenceIds: Id<"ev">[]; asOf: Iso; recordedOutput: VOut }
type VOut = { allowedSet: Action[]; firedRules: string[]; recommended: Action; maxAutonomy: AutonomyLevel };   // the output of V(S); not the verifier's `Verdict`
declare function evaluate(inputs: RecomputeInputs, subset: ReadonlySet<Id<"ev">>): VOut;               // pure: V(S)
declare function checkFlipCert(c: FlipCert, inputs: RecomputeInputs, budget: Budget): CheckOutcome;    // R is a flip and subset-minimal
declare function checkSufficiencyCert(c: SuffCert, inputs: RecomputeInputs, budget: Budget): CheckOutcome;
```
*V6.* `POLICY_BIND`: the IR digest equals the `policy.published` leaf subject (V3 binding) and, if `acceptedPolicyDigests` is pinned, is a member of it; `FACTS_INPUT`: the inputs digest equals the stage leaf; `FEATURES` (V6a, INT-050): each feature value is recomputed from the recorded facts by its declarative `FeatureProgram` (including `permits(actionClass)` booleans looked up in the permission matrix), so the view the rules saw is checked, not assumed; `TRUST_MEET` (INT-013): each recorded `Fact.trust` equals the meet over its `supports` only, and `defeats` lists every conflicting assertion the fuse considered that did not win (a missing defeated parent is FAIL); `RULES`: `evaluate(all)` reproduces the `VOut` and the recorded action, and the action order in the IR is a total order; `WHY`: each `rule` reason's rule id is in `firedRules` and its fact ids are premises (a `human.approval.<code>` reason is instead bound to its `approval.*` leaf); each `computed` reason's function id and inputs recompute; `model_reported` and `human_reported` reasons are NOT_APPLICABLE and printed under their labels.

*V7.* `V_REF`: the certificate's `vRef` equals this bundle's digests; `FLIP`: confirm `V(E\R) != v*` and, for every proper subset `R'`, `V(E\R') == v*` (at most `2^|R|` evaluations, `|R| <= 16`); `SUFFICIENCY`: for a table certificate, recompute every entry's verdict and the Merkle root; for a trace certificate, replay the implicit-hitting-set trace with the oracle; `GAP`: re-evaluate the stated decision-relevant gap by substituting each admissible value for the unchecked source. A global **oracle budget** (default 2^18 evaluations) applies; exceeding it is INDETERMINATE `V7.BUDGET`, with the number evaluated printed, and never PASS. Certificates larger than the table cap are rejected as non-conforming in favour of the trace form (XPL-07).

*V8 ledger-history invariants* are **data**, evaluated over the case stream (and the `policy`, `hold` and `erasure` streams referenced by it): `requires_before(typeB, typeA, join)`, `at_most_once`, `terminal`, `no_after`, `distinct_actors(typeA, typeB)`, `path_in(transitionTable)`. The verifier has a built-in minimal set for its version; `policy/ledger-invariants.json` can **add** invariants and can never remove one. Minimal set: lifecycle path is valid under `lifecycle.json` (no skipped state); `action.intent` is preceded by `approval.granted` and `capability.issued` for the same `caseDigest`, in that global-index order, and `action.executed` by `action.intent` and `capability.issued`; the approver differs from the requester and from the vendor-master editor (identities are idp subject ids in `actor.id`); `capability.issued` nonce hash appears once; the policy digest was `policy.published` and `policy.approved` before `decision.final` by global index; no `erasure.completed` inside a `hold.placed` to `hold.released` interval for the same scope; nothing follows `case.closed` except the post-decision types.

### 12.5 Tests and acceptance
`T-REC-01` independent re-implementation: the recompute module in all three verifier implementations (the clean-room author builds V0 to V5 only; V6 to V8 get a second implementation, not a third) agree on every hero-case bundle; `T-REC-02` the verifier's `evaluate` equals the producer's engine on 10^5 generated cases (the producer's M5/M4 tests already compare against SMT and brute force); `T-REC-03` certificate mutations (remove an element of `R`, add a non-minimal element, change `vRef`, corrupt one table entry, wrong Merkle root) each fail; `T-REC-04` budget exhaustion returns INDETERMINATE and prints the count; `T-REC-05` redacted tier: V6 and V7 return INDETERMINATE `INPUT_WITHHELD` when any input is unrevealed; `T-REC-06` model-reported-only decision gives `V6.NO_VERIFIABLE_REASON`; `T-REC-07` a bundle whose matrix row is edited to let a counterparty-authored `VERIFIED` field satisfy a manifest item fails `V6.POLICY_BIND` (matrix digest) or `V6.RULES`, and a fused value whose `defeats` omits a considered conflicting assertion fails `V6.TRUST_MEET`. Metric: evaluation count and wall time per hero-case bundle (the ledger-size distribution of spec 9 acceptance is published beside it). Disproved if the verifier and the producer disagree on any generated case that is not already a recorded producer bug.

### 12.6 Risks and NOT VERIFIED
The IR and kernel specifications do not exist yet and bake-off 2 may adopt Cedar or OPA, in which case V6 needs a second implementation of that language's evaluator, which could make the zero-dependency, two-implementation design infeasible: the decision rule of bake-off 2 now includes "interpretable by a 500-line verifier-side evaluator" as a gating criterion (INT-050, Spec feedback F9). Realistic ledger sizes and flip counts are unknown (spec 22). Time-dependent features need `asOf` only, never the verifier's clock.

### 13.4 Implementation design
**Vectors, three sets.** (1) *Unit vectors* per primitive (JCS, parse rejections, PAE, note and checkpoint parsing, cosignature, policy, proofs, tar header cases, commitments, L0). (2) *Public conformance corpus*: base bundles and the public part of the tamper corpus with expected reports. Expected output of every vector is the report (verdict and per-check results, not message strings).

## 14. Component 12: Tamper corpus, fuzzing, false-accept reporting

### 14.1 Best references
13 §8 contribution 2, R10 (Alshammari and Bahsi), R9 (named-clause reject cases), R15 (fast-check, jazzer.js, Stryker), spec 13 and AUD-06, C2 of `02-research-contributions-and-grant-case.md`. ### 14.2 What they actually do
R9: one field mutated per case, each case names the spec clause it guards. R10 reports counts without a released corpus (as summarised in 13).

### 14.3 Decision
**Own** the generator and the catalogue; **reuse** fast-check for generation and shrinking, Stryker for mutation testing of the verifier source, and jazzer.js only if it runs on the build machine. Report exactly what the spec says: the false-accept rate **over the published mutation set**, never over all attacks.

### 14.4 Implementation design

**Mutation catalogue (data).** Each row:
```ts
interface Mutation { id: string; family: string; clause: string; target: string; op: string; params: Json;
  resign: "none" | "fresh-key" | "decision-key-no-log-key" | "log-key-compromised";
  expect: { noPins: { verdict: Verdict; mustFail: string[]; mayFail: string[] }; withPins: { verdict: Verdict; mustFail: string[]; mayFail: string[] } } }
```
Families (each a generator over every base bundle and, where per-member, over every member):
- **byte**: flip one bit at first, middle and last byte of each member; flip inside a hash string; flip inside a JSON key; change only whitespace (V1); change a trailing newline; change tar header fields.
- **ledger-truncation**: drop the last k entries (k = 1, 2, half) with the checkpoint unchanged; with a re-issued checkpoint signed by a fresh key; with the real log key (the compromised-key class, expected to be caught only by a pinned earlier checkpoint, a witness, an anchor, or the stream terminal rule; expected verdict for the no-earlier-pin row is PASS-by-design and is recorded as such in a **known-limits** table, not hidden).
- **swap**: replace an evidence blob by other bytes of equal size with the manifest updated; with a fresh-key re-sign; with the real decision key but no log key.
- **rule**: change the policy IR; change one reason code; change a certificate's `R`.
- **claims**: reorder, duplicate, remove, retype a claim; change a span id; cite an erased item.
- **locator**: code-point `start`/`end` shifted with bytes unchanged and the reverse; `byteStart` inside a multi-byte character; unit field missing or not `codepoint`; `spanSha` of another span; a `jcs:` digest where a `RawHash` is declared (each expected `V5.LOCATOR_UNIT_MISMATCH`, `V5.LOCATOR` or `V1.SCHEMA`).
- **checkpoint**: replace with an older valid checkpoint; a same-size different-root checkpoint; wrong origin; a fresh-key note; a cosigner removed or duplicated; a quorum-satisfying set built from the right names with wrong keys.
- **canon**: duplicate key; float; `-0`; leading zero; big integer; lone surrogate; BOM; key order; unicode escape variants; depth bomb.
- **path**: absolute, `..`, backslash, case-duplicate, symlink entry, reserved Windows name, 300-byte name, NUL in name, duplicate entry.
- **cassette**: edit a recorded response and not the cassette manifest; edit both and not the manifest; edit all three and not the ledger binding.
- **pins**: no pins; wrong pins; revoked key; pins from the bundle; expired rotation.
- **dsse**: payload swapped; payloadType changed; second signature appended; keyid mismatch; URL-safe base64; PAE-confusable type strings.
- **inclusion**: flip each proof hash; wrong index; too-long and too-short proofs; a valid proof for a leaf of another case; a leaf of the same case but another stream.
- **seq**: gap, duplicate, out of order, `prev` rewritten, stream splice from another case.
- **commit**: change a revealed value; swap a salt; reveal for the wrong field; commitment list shortened.
- **tier**: a redacted bundle declaring `{reviewer, full}`; counterparty notice presented as a dossier; `audience` and `disclosure` pairs outside the four allowed.
- **erasure**: forged receipt; erasure inside a hold; receipt for a digest that is still present; a tombstone whose receipt digest matches no `erasure.completed` leaf; a receipt whose `method` is outside the closed set.
- **capability** (V8): `action.intent` without a preceding `capability.issued`; a repeated nonce hash; `capability.issued` whose restore epoch differs from the latest `restore.epoch` leaf.
- **anchor**: imprint changed; TSA signature flipped; wrong EKU; certificate expired at `genTime`; OTS operation changed; header for another height.
- **recompute**: truth-table value changed with all digests recomputed and the log key unavailable (V3 binding fails); same with the log key (V6/V7 fail); lifecycle skipped state.
- **dos**: member count, inflation ratio, sparse tar, proof length, nesting.
- **benign** (must still PASS): re-pack with different tar ordering when the file set is equal (rejected by V0 sort rule by design: recorded as FAIL, so the benign class contains only **attachment additions**, README changes and `views/` regeneration); used to measure false rejects.

**Scale.** K base bundles (target 200 from the six recorded scenarios plus generated variants), about 60 members each; the byte family alone is tens of thousands of mutants; the whole set is generated from a seed and verified in CI in shards. The generator prints `seed + commit` on any failure (spec 4 simulation harness style).

**Oracles.** (1) *Expected-row oracle*: every mutant has expected rows as above. (2) *Covered-bytes oracle* for fuzzing: PASS is allowed only if every manifest-covered file is byte-identical to the base bundle's; anything else that PASSes is a false accept by definition. (3) *Differential oracle* across implementations. (4) *Liveness oracle*: no crash, no unhandled exception, completion within the time and memory bound.

**Structure-aware fuzzing.** Mutations at the structural layer: JSON tree edits (delete, duplicate, retype, swap sibling fields), tar header field edits, Merkle proof edits, DSSE field edits, tier field edits; byte-level fuzzing only as a complement. fast-check drives generation; jazzer.js coverage guidance is used if it runs on the build machine (**NOT VERIFIED**); otherwise the structure-aware generator with a coverage report from Node's built-in coverage tooling.

**Mutation testing of the verifier itself.** Stryker (or a hand-written mutation operator set if it does not fit) mutates the verifier source; the corpus must kill each mutant of a check body. Survivors are listed; each is either an equivalent mutant (documented) or a missing corpus row (added). Required: the inert verifier (always PASS) and the verifier with any single check disabled fail the corpus.

**Reporting.** Per family and overall: mutants N, false accepts (count), false rejects among benign, right-reason rate (all `mustFail` checks failed), wrong-reason rejections (rejected only by an unexpected check, a latent hole), disagreement count across implementations, fuzz executions and coverage. With zero events the report prints the 3/n upper bound at 95% (rule of three) and the exact Clopper-Pearson bound, and the sentence "over the published mutation set of N mutants; not a bound over all possible attacks". The **known-limits table** lists attacks the design does not detect in a given mode (for example, rewriting by a log-key holder with no earlier pin, witness, or anchor held by the relying party), with the mode that does detect them.

### 14.5 Tests and acceptance
`T-TAM-01` every check id and reason code is the `mustFail` of at least one row; `T-TAM-02` the inert-verifier and check-disabled verifiers fail; `T-TAM-03` zero false accepts on the public set for A, B and C (C on V0 to V5 rows only); `T-TAM-04` fresh-key re-sign rows: no pins gives INDETERMINATE, pins give FAIL; `T-TAM-05` held-out seed run before any public claim; `T-TAM-06` fuzz run of fixed duration with zero crashes and zero covered-bytes violations. Disproved if any false accept appears; each is a P0 against the verifier or the specification.

## 15. Component 13: Audience tiers and per-field salted commitments

### 15.1 Best references
R17 (RFC 9901: per-claim salt, digest over the disclosure, 128-bit minimum salt, decoy digests), 13 §4.2 pitfalls ("digests of low-entropy text can be guessed; use salted commitments"), R10 (Veridic redaction receipts), spec 13 (three tiers, table of surviving levels, "proof-preserving" withheld), R19 (tipping-off, Art. 86; LAWYER). Evaluation limit: RFC 9901 defines a JWT mechanism and says nothing about Merkle structures, multi-document bundles or a verifier recomputing a policy over revealed fields.

### 15.2 What they actually do
RFC 9901 (fetched): each undisclosed claim is replaced in the signed payload by the digest of an array `[salt, name, value]`; the holder reveals chosen disclosures; the verifier recomputes digests; decoy digests hide the number of claims; "unlinkability" requires fresh salts per presentation.

### 15.3 Decision
**Adapt.** One dossier, one signature, many views: sensitive documents in the dossier exist in **committed form**, and every tier is a different set of reveals attached to the same signed artefacts. Per-field granularity is by commitment list, not by Merkle tree (a list is simpler to implement three times; the number of fields is small). Rejected: separate signed bundles per tier (would multiply signatures, and a redacted bundle's signature would not cover what the full bundle covers); redaction by deletion without commitments (breaks digests).

### 15.4 Implementation design

**Committed document.**
```ts
interface CommittedDoc { schema: "plumbline.committed/v1"; docId: string; fields: { path: string; commit: Commitment }[] /* sorted by path */; decoys?: Commitment[] }
// commit = "com:" + hex sha256( "plumbline.field.v1" 0x0A || len(path) || path || salt(32 random bytes) || jcs(value) )
interface Reveal { path: string; salt: string /* b64 */; value: Json }           // shipped in decision/reveals/<docId>.json, per tier
```
The signed manifest covers the `CommittedDoc`. The reveals file is listed in the manifest as role `tier-reveal` with disclosure level, but its *content* is validated by commitments, so a tier can ship a subset without changing the signed bytes (the manifest records `disclosure: "partial"` for the member and the digest of the full reveals file, which the verifier does not need to match: a partial reveal is valid iff every revealed field matches a commitment). Salts are 256 random bits (RFC 9901 recommends at least 128). Salts derive from `HMAC(caseSecret, docId || path)` so a case can be re-bundled deterministically; the case secret is a confidential value in the `internal-sensitive` partition of the blob store, destroyed at erasure (component 14).

**Which fields are committed.** Any value whose confidentiality is above `public`, `personal` ones always: vendor names, bank account and identifiers, amounts, owner names, internal reference ids; structural fields (rule ids, codes, action, dates of checkpoints) stay in the clear, which is what lets V3 and V8 run on every tier. `evidence.fetched` leaf `subject` uses the same commitment form for non-public evidence. Public-source evidence keeps raw `bodyHash` so a stranger can match a downloaded file (evidence mode). Decoy commitments are optional per tier (a count-hiding option for the auditor tier).

**Tiers** are pairs `(audience, disclosure)` with `Audience = reviewer | auditor | counterparty` and `Disclosure = full | redacted | notice` (INT-008); four pairs exist.
- *(reviewer, full)* and *(auditor, full)*: all reveals, all bodies the rights gate allows. Identical content; the difference is who receives it and the access control around it.
- *(auditor, redacted)*: structure, commitments, selected reveals, bodies withheld by label.
- *(counterparty, notice)*: **not a dossier.** A signed `notice` document: case reference, outcome class, a reason code from the counterparty-safe set (a deliberately coarse table owned by M5/M10 and reviewed by a lawyer; the mapping must not make the code a function of the hidden cause, or the notice tips off), date, plus `bindsTo` (a `Commitment`, `sha256("plumbline.notice.bind.v1" 0x0A || salt || manifestDigest)`) committing to the full dossier without revealing it, and optionally the inclusion proof of a `notice.issued` leaf. In a later dispute or appeal, the salt and dossier can be revealed to an arbiter to show the binding. Delivery of the notice to a counterparty is outside the first release and is a LAWYER item; the reviewer-side preview with a leakage test is M10's deliverable (INT-055). No listing, source or rule detail, no sanctions language, and no distinguishable difference in size or timing between outcomes beyond what policy permits (a note for M10: padding is not designed).

**Which verifier levels survive each tier** (the table spec 13 requires; "proof-preserving" is not claimed beyond it):

| Level | (reviewer or auditor, full) | (auditor, redacted) | (counterparty, notice) |
|---|---|---|---|
| V0 member set and digests | PASS | PASS (withheld members are listed with digests) | PASS on the notice file only |
| V1 canonical form, commitments | PASS | PASS for revealed fields; unrevealed fields are not checked | PASS on the notice |
| V2 envelope and signature | PASS with pins | PASS with pins | signature on the notice with pins; no dossier statement |
| V3 ledger membership and bindings | PASS | PASS (leaves are structural; subjects are commitments) | optional, `notice.issued` leaf only |
| V4 consistency, witnesses, anchors, currency | PASS where supplied | same | optional |
| V5 quotes and evidence | PASS where bodies present or supplied | INDETERMINATE (`WITHHELD`) unless the span and body are revealed | NOT_APPLICABLE |
| V6 rule recompute | PASS | INDETERMINATE (`INPUT_WITHHELD`) unless every input of the recompute is revealed | NOT_APPLICABLE |
| V7 counterfactual and certificates | PASS | INDETERMINATE | NOT_APPLICABLE |
| V8 history invariants | PASS | PASS (structural leaves) | NOT_APPLICABLE |

**Linkability and leakage.** Presentations of the same dossier to different recipients share the signed commitment list, so recipients can collude to compare reveals; per-recipient re-commitment would break the single signature and is a stated limit. The count of fields leaks (decoys optional). The leaf structure leaks event counts and timing to anyone holding proofs.

### 15.5 Tests and acceptance
`T-TIER-01` no-leak test per tier: a scanner searches every byte of the tier's bundle for the plaintext and the raw sha256 of every confidential value of the test case (the guessable-digest check); `T-TIER-02` reveal tampering rows (component 12); `T-TIER-03` the survival table above is a generated test: for each tier and level the expected result is asserted; `T-TIER-04` dictionary attack: with the redacted bundle, brute force over the 10^6 most plausible bank-account numbers and a name list fails to find a commitment match (salts defeat it) while the same attack on an unsalted variant succeeds (positive control); `T-TIER-05` counterparty notice reason codes: a test that the code distribution is identical (same code) across hold causes of the hero set, run with M5. Legal acceptability of every tier: **LAWYER**; the technical scheme stands without it.

### 15.6 Risks and NOT VERIFIED
The notice mapping is a legal question; field-count and timing side channels; whether salts derived from a case secret create a single point of failure at erasure (intended) and at backup. Dedicated selective-disclosure signature schemes (BBS) were not studied; the commitment list gives selective disclosure but not unlinkability.

### 15.7 Build notes
Commitment library with component 1; committed documents are used from the first bundle (the plain form is not built, so recompute always reads through reveals and the redacted path is exercised from day one).

## 16. Component 14: Erasure, retention and legal hold

### 16.1 Best references
R19 (Art. 12 recording, Art. 26(6) "at least six months" retention for deployers' logs, GDPR Art. 17/22, Art. 86 and tipping-off), R10 (Veridic redaction receipts), 13 §4.2 pitfalls ("an erased body leaves a hash plus an `erased` receipt"), AUD-10, R17. Evaluation limit: none of these specifies an erasure protocol for a content-addressed store behind a Merkle log, or the interaction between legal hold and erasure; all legal readings are secondary and LAWYER.

### 16.2 What they actually do
The drafts name redaction receipts without a verification algorithm (13 §3.1, from pages). 15 §5.2 (read) notes the tension: hash-only traces help minimisation but may not allow reconstruction, and no retention schedule exists in the spec.

### 16.3 Decision
**Own.** Principles: the **ledger never holds content** (digests, codes, commitments), so erasure never edits the log; bodies, salts, case secrets and cassette bodies live in the one blob store behind M7's `StorePort` (addressed by `RawHash`, partitioned by confidentiality class: `public`, `case-visible`, `internal-sensitive`) and are the erasable layer; this service is the **only deleter** of that store, and M1's `erase` and M13's data-key destruction both call it (INT-043); erasure **destroys the salts**, which turns the remaining salted commitments into unguessable digests (a technical mitigation; whether such digests remain personal data is LAWYER); every erasure and every hold is itself a logged, signed event; retention is configuration, not code. Rejected: deleting leaves or rewriting tiles (destroys tamper-evidence). Crypto-erasure (destroy the per-object data key, so backups are covered) is a second `method` of the same protocol, used when M13's `KeyPort` data keys exist for the object's partition; the judge path ships `delete+salt-destroy` (section 16.6).

### 16.4 Implementation design
**Configuration** (`retention.json`, published as `retention.policy.published`): per object class (`evidence-body`, `cassette-body`, `trace-content`, `reveals`, `case-secret`, `bundle`) a `keepForDays`, a `trigger` (`case_closed`, `decision_final`, `fetched`), and `action` (`erase`, `review`). Spec 18 and R19 give no default; the default shipped is a parameter stated as "not legal advice; six months is the Art. 26(6) floor for deployers' automatically generated logs, as read in 15", and no claim of compliance is made.

**Protocol.**
```ts
interface ErasureRequest { scope: { caseId?: string; digests: Hash[] }; basis: "retention_expiry" | "subject_request" | "policy" | "operator"; requestedBy: Actor }
interface ErasureReceipt { requestLeaf: DocHash; erased: { digest: Hash; kind: "body" | "salt" | "cassette-line" | "trace-content" | "reveal" }[]; store: string; partition: Confidentiality;
  method: "delete+salt-destroy" | "crypto_erase" | "tombstone"; at: Iso; holdCheck: { holds: string[]; clear: true }; storeSignature: string }
interface Tombstone { schema: "plumbline.tombstone/v1"; digest: RawHash; partition: Confidentiality; erasedAt: Iso; receiptDigest: DocHash; method: ErasureReceipt["method"] }   // lives at the blob's address in the store
```
`method` meanings: `delete+salt-destroy` removes the bytes and the salts that made the commitments guessable; `crypto_erase` destroys the data key of the object, so every copy including backups is unreadable; `tombstone` records an erasure already carried out by another mechanism (for example an upstream source withdrawal) without claiming deletion here. Every method leaves a `Tombstone` at the blob's address, and the store's read of that address returns the error `erased` carrying `receiptDigest`, never an empty body.
1. Append `erasure.requested` and await publication. 2. The eraser (a function of the blob-store service, with its own signing key under the signer's role policy `erasure`) reads the `hold` streams: if any `hold.placed` without a later `hold.released` covers a scope member, it refuses (`ERASURE_UNDER_HOLD`) and logs nothing further. 3. Apply the method; overwrite is not claimed (filesystem and backups are out of reach unless `crypto_erase`; the receipt states `method`). 4. Write the tombstones, then append `erasure.completed` carrying the receipt digest (the only leaf for an erasure receipt); the receipt is a bundle member (`erasure/receipts/`). 5. Rebuilt bundles for the case show `disposition: "erased"` for those items with a pointer to the receipt. Named downstream states, never silence: replay raises `CassetteMiss{reason: erased}`, V5 is `INDETERMINATE V5.ERASED`, M6 validity and retraction are `unevaluable`, and M5 replay of that decision is `INDETERMINATE`.

**Verifier behaviour.** `E.RECEIPT` verifies the receipt's signature against the `erasure` store key pinned in `pins` (or suggested), that its `requestLeaf` is a leaf in the case log, that the erased digests match the ones in `evidence/index.json`, and that no hold covered the scope at the time (by global index order, V8). V5 for erased items is INDETERMINATE `V5.ERASED`, never FAIL and never PASS, and the report lists them in "not established". Hold: `hold.placed` and `hold.released` leaves in stream `hold:<scope>`; erasure under hold is a V8 FAIL after the fact (`V8.HOLD_ERASURE`), so a producer that erased anyway is detected from the log.

**Reconstruction per event class (Art. 12 tension).** Bodies of model prompts and responses, tool calls and source fetches are retained in the blob store for the retention period (case-visible or internal-sensitive, erasable), while exported traces and bundles are hash-only by default; the bundle's tier and its members' `disclosure` values say which. So reconstruction is possible inside the retention window by an authorised reader and impossible afterwards, which is the stated trade-off.

**M6 interaction.** Episodes are immutable in meaning (spec 11), not in storage: erasure turns an episode body into a tombstone while the episode's id, digest and trust label remain; precedents derived from an erased case keep `derivedFrom` ids and a `source_erased` flag, and retrieval treats them as counter-only (Spec feedback F16); validity and retraction recomputation over an erased snapshot are `unevaluable` (M6).

### 16.5 Tests and acceptance
`T-ERA-01` erase evidence X from a PASS bundle's case, rebuild: V0 to V4 and V8 PASS, V5 INDETERMINATE for claims citing X, `E.RECEIPT` PASS; `T-ERA-02` after erasure no byte anywhere in the case's tiers, bundle or logs contains X or any recoverable form (scanner), and the commitment of X no longer verifies against any candidate value without the salt (positive control: before erasure with the salt it does); `T-ERA-03` hold placed then erasure request: refused and logged; hold released then request: succeeds; `T-ERA-04` a forged receipt, a receipt for a digest still present, a receipt predating the hold: each fails; `T-ERA-05` retention sweeper proposes erasures only after the configured age and never without a leaf; `T-ERA-06` M6: a precedent whose source is erased stays retrievable as counter-only and cannot enable autonomy above AL1; `T-ERA-07` every method leaves a tombstone, the store returns `erased` with the receipt digest on read, and a replay that needs the body stops with `CassetteMiss{reason: erased}`. Disproved if any plaintext or unsalted digest of an erased item survives in an artefact the system produced.

### 16.6 Risks and NOT VERIFIED
Backups and filesystem remnants (`crypto_erase` covers them only where M13's per-object data keys exist; `delete+salt-destroy` does not); whether commitments after salt destruction are still personal data (LAWYER); whether Windows file deletion leaves recoverable remnants (not claimed); the default retention period.

### 16.7 Build notes
After components 2, 3 and 13; the `StorePort` contract (partitions, tombstone read error) agreed with M7 and M8 first.

## 17. Component 15: Verifier distribution and the browser hash-recheck contract

### 17.1 Best references
13 §4.2 pitfalls ("verifier digest in README ... trust bootstrap out of band"), R9 (web verifier next to CLIs, per tree listing), spec 13 ("published out of band, not only inside the bundle"), spec 14 (evidence viewer chip), Sigstore/GitHub artifact attestations for release signing (13 §2.7 for Rekor's intended use; availability for this account **NOT VERIFIED**). Evaluation limit: a digest in the same repository as the sample bundles is in the same trust domain as the bundles.

### 17.2 Decision
**Own** the distribution rules and the viewer contract. Rejected: `npx plumbline-verify` or any package manager distribution (version drift, a registry in the trust path); shipping the verifier inside the bundle (AUD-02).

### 17.3 Implementation design

**Release artefacts.** `verify.mjs` (A), `plumbline_verify.py` (B), the clean-room binary or source (C), the optional modules (`verify-recompute.mjs`, `verify-anchors.mjs`), the normative specification, the vectors, `SHA256SUMS`. A build script produces them from a tagged commit by deterministic concatenation; a second script rebuilds and compares digests (reproducibility check, `T-DIST-01`). The verifier prints `selfDigest`, computed from its own file bytes, in every report.

**Out-of-band means at least two channels the bundle author does not control alone:** (1) the repository README and release notes; (2) the submission text and the final slide of the deck; (3) the annotated git tag; (4) optionally a Sigstore signature and a public log entry for the release artefact (the intended use of the public Rekor instance, unlike decisions). A reader is told how to check: `sha256sum` of the downloaded file against the published value, performed before first use. This is stated as assumption A4 in every report.

**Browser hash-recheck contract (shared with M10).** The console shows a chip per claim. `chipState` returns a **named state**, never a colour; M10 owns colour and icon, and every state carries text and an icon (M2's set, which M10 adopts, INT-052): `verified exact`, `verified (OCR, min conf n)`, `layer-only (source not shipped)`, `relocated`, `hash mismatch (source|layer|span)`, `extractor disagree`, `hidden-text finding on page`, `quote absent`, `not checked`, `unavailable`. This module defines which verification outcomes may produce `verified exact` and `verified (OCR...)`: only those below. Hashes matching with an INDETERMINATE verifier result is `not checked` with the reason line; any mismatch or FAIL is a `hash mismatch` or `quote absent` state. A rights-gated PDF whose source is absent but whose layer ships is `layer-only`: step (2) is skipped, steps (3) to (5) run.
```ts
interface ViewerCheckInput {            // what M10 must hold for one citation
  manifestBytes: Uint8Array;            // bundle.json as served to this browser
  indexEntry: { evidenceId: string; bodyHash: RawHash | Commitment; textLayerHash: RawHash; resolver: ResolverKind };
  span: { page: number; start: number; end: number; byteStart: number; byteEnd: number; spanSha: RawHash; quote: string };   // code-point and UTF-8 byte offsets; quote as recorded
  docBytes?: Uint8Array; textLayerBytes: Uint8Array;          // as fetched by this browser; docBytes absent in layer-only
  report: VerifyReport;                                       // the bundle's recorded report, from a server-side run of the standalone verifier
}
declare function chipState(i: ViewerCheckInput, cryptoSha256: (b: Uint8Array) => Promise<Uint8Array>): Promise<ChipState>;   // ChipState: M2's ten, defined in DI-14
```
Steps, all in the browser with `crypto.subtle.digest("SHA-256")`: (1) hash `manifestBytes` and require equality with `report.input.manifestDigest` (the bytes shown are the bytes verified; closes the verify-then-swap gap); (2) hash `docBytes` and require `bodyHash` (or, for a non-public item, the commitment recomputed from the revealed salt and value); (3) hash `textLayerBytes` and require `textLayerHash`; (4) slice the page text `[byteStart, byteEnd)`, require both ends on code-point boundaries and equality with `span.quote` and `spanSha`, and require the code-point count before `byteStart` to equal `start` (the same cross-check as V5; a disagreement is `hash mismatch (span)`); where the recorded L0 status is not `exact` the browser does **not** reimplement normalisation and shows `not checked` with the verifier's per-claim row; (5) require `report.checks["V5.QUOTE:<claimId>"] == PASS` and `report.verdict != FAIL`. The state is `verified exact` only if all five hold. The member digests of `evidence/index.json`, the blob and the text layer must also equal the manifest's member digests (hashed by the browser).

**Two results, never one green.** The page runs the verifier **core** (V0 to V4a and parser-free V5) in a worker over the bytes it holds and reports two results: its own recomputation and the bundle's recorded verifier report from the server-side `verify --json` run (a separate OS process, so the report reflects the same program a stranger would run). If the two differ in any check result, the chip is an alert state (`unavailable` with reason "page and recorded verifier disagree"), never `verified`. The worker's host adapter supplies SHA-256 from WebCrypto; Ed25519 verification in the page is **NOT VERIFIED** across target browsers, so signature checks run in the page only if a verified path exists and are otherwise INDETERMINATE there (the recorded report carries them); with no pins in the report, the chip text reads "hashes match; signer not authenticated (self-supplied trust)". Mapping bytes to DOM highlight positions uses `TextDecoder` over the prefix to obtain a UTF-16 index; offsets in the data stay as recorded.

### 17.4 Tests and acceptance
`T-DIST-01` rebuild from tag reproduces the published digests; `T-DIST-02` an altered verifier file is detected by `sha256sum` and the report's `selfDigest` differs; `T-DIST-03` browser contract: Playwright drives the console on the sample bundle (`verified exact`), on each tamper row relevant to the viewer (the specified mismatch or alert state), on a swapped blob served after verification (`hash mismatch`), on a bundle whose recorded report is edited to disagree with the page's recomputation (alert state), on a layer-only item, and on a bundle without pins (hashes-match text); `T-DIST-04` the chip is never `verified` when the report verdict is FAIL or the page and recorded results differ; `T-DIST-05` accessibility: chip state announced by text, keyboard reachable.

### 17.5 Risks and NOT VERIFIED
Release-signing availability; the viewer's reliance on a server-side verifier run for tier decisions; WebCrypto Ed25519 support not needed for the contract as defined.

### 17.6 Build notes
Contract types agreed with M10 before the viewer is built; the build and reproducibility scripts follow the first verifier release.

## 20. Spec feedback

F1. **Spec 13 puts V4 in the zero-dependency core, but RFC 3161 and OpenTimestamps verification need DER/CMS parsing and Bitcoin header handling.** Proposal: V4a (consistency, witness quorum, cadence) stays in the core; V4b (anchors) is a separate zero-dependency file. The "core" statement in spec 13 should say so. *Resolved by INT-051.*
F2. **Re-sign with a fresh key: spec 13 says "expected INDETERMINATE".** That is right only without relying-party pins. With pins it is FAIL (`V2.SIGNER_NOT_PINNED`). Spec and corpus must carry both rows. *Resolved by INT-053.*
F3. **Shared-type comment on `Hash` says "hex digest of JCS-canonical bytes"; evidence bodies and bundle members are raw bytes.** Three kinds now exist (`RawHash`, `DocHash`, `Commitment`); `Evidence.bodyHash` of a non-public body is a `Commitment`. *Resolved by INT-003.*
F4. **Replay equality (spec 4) cannot include global ledger indices or the tree root,** which depend on the interleaving of concurrent cases. Define it over per-stream leaf sequences and head leaf hashes. *Resolved by INT-053.*
F5. **Spec 7 does not fix the unit of locator offsets.** The canonical unit is the code point (page-relative, unnormalised layer, M2); `textlayer` locators also carry UTF-8 `byteStart`/`byteEnd` that the verifier cross-checks, plus a closed set of resolver kinds. The rights-gated path depends on locators that need no parser (spec 13 evidence mode). *Resolved by INT-004* (this item originally proposed UTF-8 bytes as the only unit; M2's code points won).
F6. **13 §4.2 of the prior art makes `ledger.append()` resolve only when covered by a checkpoint (AUD-05).** Replaced by `append` (durable) plus `published` (required before effects, decisions and bundles). *Resolved by INT-018.*
F7. **Spec 14a leaves the capability key "behind the same boundary as the ledger signer, or its exposure is stated".** This blueprint takes the first branch with a mechanism (role policy requiring inclusion proofs of the `approval.granted` leaves, over M12's `ExecutionContract`). *Resolved by INT-017 and INT-016.*
F8. **Predicate type URL and checkpoint origin need a namespace Prateek controls.** Interim `.invalid` value; decide before the first public bundle. *Open (register decision D1).*
F9. **V6 to V8 are possible only if the policy IR and the reconcile kernel are small data languages.** Bake-off 2's decision rule includes "interpretable by a verifier-side evaluator of about 500 lines" as a gating criterion; if Cedar or OPA wins it is a front-end or cross-check and PPIR stays the bundle format. Certificate vocabulary mapping (XPL-07) is fixed in section 8.4. *Resolved by INT-050* (the "three languages" in the original wording became two for the policy evaluator; the verifier itself still has three implementations of V0 to V5).
F10. **Spec 13 "counterparty (reason code only, no list or source detail)" is a signed notice, not a bundle.** The tier table in component 13 is the replacement for the sentence "a table states which verifier levels survive each tier". *Resolved by INT-055.*
F11. **"Published out of band, not only inside the bundle"** needs at least two channels independent of the repository that hosts the sample bundles; the README alone is the same trust domain. *Open (register decision D1).*
F12. **Cassette in the bundle:** the manifest and the cassette body have different confidentiality (model prompts and responses); tiering applies to the body, the manifest carries Merkle roots over line digests (effect layer and transport layer) so partial reveal is possible. *Resolved by INT-042.*
F13. **Rights-gated PDF evidence cannot reach V5 offline in evidence mode** (text extraction is parser code the zero-dependency verifier does not carry). Only sources with parser-free locators (raw byte ranges, JSON pointer, CSV cell, text-layer range) can PASS; a PDF reaches V5 through its shipped layer. *Resolved by INT-051.*
F14. **Spec 4 says every decision carries `why`; spec 13 adds `why_kind`.** The trace linter must also require `ruleId` for `rule` lines and a registered function id for `computed` lines. *Resolved by INT-054.*
F15. **Spec 9a has no row for log completeness and currency** (a bundle is a statement as of one checkpoint; later retraction, reopening or erasure are invisible to it). Add: established = consistency from a held checkpoint to a stated checkpoint; not established = nothing after it. *Resolved by INT-053 and register section 4.*
F16. **Spec 11 "episodes are immutable" and M9 erasure:** immutability must mean meaning and digest, not stored bytes; tombstones with `source_erased` and counter-only retrieval. *Resolved by INT-040.*
F17. **Spec 20 step 8 lists "two implementations pass shared vectors" as the gate for the verifier core.** The normative specification and the held-out corpus are prerequisites and should be named in the gate. *Resolved by register section 5 (V5, V6): step 8a, scoped to V0 to V4a and parser-free V5.*

## 21. What this blueprint does not cover

- The policy IR, the reconcile kernel, the L0 quote-check algorithm and the certificate generators: they are M5, M3 and M4 deliverables; this module states what it needs from them (component 10, interfaces table).
- Signing-key hardware (HSM, TPM, cloud KMS), a per-tenant key hierarchy beyond the per-tenant registry in the signer, and the data-key design behind `crypto_erase` (M13's `KeyPort`): extension points only here.
- A public witness network membership, a third-party operator for witnesses, and any independence claim: unverified; no claim until a cosignature from another operator exists.
- Legal acceptability of any tier, the retention default, tipping-off wording, GDPR treatment of salted commitments: LAWYER.
- Post-quantum signatures: C2SP specifies ML-DSA-44 cosignature types; Ed25519 is used here for tool availability and verifier size; a migration path exists in the key-rotation leaves but is not designed.
- Full replay (`V9`, re-running pinned code over the cassette): a product command owned by M7 and M11, not part of the offline verifier.
- Network services: no log server, no tile HTTP serving, no monitor daemon; a monitor is a verifier run on a schedule and is not designed here.
- Performance at scale (thousands of cases per day), capacity planning for tiles and WAL, and ledger sharding.
- The visual design of the verdict display and the "what this does not prove" panel (M10).
- Anything about the contents of evidence being true, the policy being right, or an outcome being good: spec 9a states these are outside every check in this module.
