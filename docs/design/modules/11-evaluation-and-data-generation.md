## 1. Scope and contract

**Job.** M11 is the only module whose purpose is to find out whether the other twelve are any good. It owns (a) the synthetic world and everything generated from it, (b) the gold labels and the annotation protocol, (c) the external anchors that keep the evaluation from grading the system on its own assumptions, (d) the benchmark suites, their scorers and the metric library, (e) the statistics, pre-registration and ablation machinery, (f) the harness self-tests, baseline integrations and the evaluation-toolchain tier, (g) cost accounting and the generated reports, including the not-covered list, the engine-usage map and the claim-to-evidence map.

**Inputs.** A seed and a regime grid (generator); the silo contract file and connector schemas published by M1 (read as data, INT-046); the Plumbline-Inject family registry, tiers and oracle definitions published by M8 (INT-026); a system-under-test (SUT) exposed through the stage entry points of F-STAGES (`plumbline reconcile | explain | decide`, `verify`, `eval-run`), the M7 trace, cassettes and state hashes; pinned baseline tools (E20, E21); human annotations (E7).

**Outputs.** Case files split into `public/` (what a SUT may read) and `private/` (latent world, gold, regime parameters); `MetricResult`s with intervals; `eval/reports/<run-id>/report.{json,md}`; the generated `docs/submission/engine-usage-map.md`; `docs/submission/claims.json` verdicts; `data/README.md` inputs (F-DATAREADME).

**Depends on.** M7 (trace, state hash, budgets, cassettes; the generator deliberately does not, see E1), M1 (silo contract, a data file), M8 (attack families, tiers, oracle definitions), M9 (bundles for the tamper corpus), the stage entry points of M3, M4, M5, M6, M10 (CLI), M12 (engine switches and the C9 scenario set), M14 (role registry and hypothesis text for `ArmSpec` and `Prereg`). **Depended on by.** M5 (selective-release validation draws), M3 (bake-off 3 gold set), M2 (bake-off 4 corpus), M12 (engine ablation oracle), the submission kit (step 16).

**Position in the dependency rules.** M11 tests all; nothing imports M11. Where M11 needs a hook (an engine switch, a stage entry point, a seed-controlled run) it asks the owning module through the interfaces table, never by reading internals.

**Honesty frame.** Everything M11 produces is evidence about the SUT on *our* synthetic distribution plus the external anchors. It never yields a real-world error rate. Every report states that.

# E1. World model and generator core

**Best references.** R8 (what not to do), R9 (controllable synthetic truth discovery), 15 §6 (ten domain requirements), 07 §2 (source dependence). **What they do.** `binary_vectors` samples agreement indicators from per-field m and u probabilities (read: parameters `m=[0.9]*8, u=[0.1]*8`); the matcher then recovers the same parameters. DAFNA-EA's generator controls coverage and conflict distribution but has no notion of an authority table (README). **Decision: own.** Neither models a vendor world; the circularity lesson (GRT-01) is the design driver.

**Design.**

1. **Two stages, truth first.** A `World` is sampled with no reference to any authority table, trust level or system threshold. Observations are then produced by an *observation process* that holds each source's latent reliability. The system's authority tiers (a pack table) are never an input to the generator. Tier misalignment is a regime, not an accident.

```ts
interface World {
  seed: string; spec: Hash;                               // generator-spec version hash
  orgs: LatentOrg[];                                      // legal name history, aliases, jurisdiction, legal form, status timeline
  persons: LatentPerson[];                                // synthetic only
  ownership: OwnershipEdge[];                             // holder -> owned, pct, from, to, kind: "shares"|"nominee"|"trust"|"control"
  accounts: BankAccount[]; employees: Employee[]; addresses: Address[];
  contracts: Contract[]; invoices: Invoice[]; payments: Payment[];
  listTimeline: ListVersion[];                            // sanctions-style list versions with add/remove events (E2)
  events: WorldEvent[];                                   // bank-detail changes, mergers, renames, dissolutions, designations
  changeRequests: ChangeRequest[];                        // change_request_id, request_origin (shared WriteOrigin), editor_sub, last-write time, contact-point provenance (INT-024)
}
interface Source {                                        // latent; the SUT never sees these numbers
  id: string; kind: "internal"|"registry"|"aggregator"|"document"|"web";
  attrs: Record<string, { errorRate: number; staleLagDays: Dist; missingRate: number; formatNoise: number }>;
  copyOf?: { source: string; copyRate: number; lagDays: Dist };
  authorship: Authorship;                                 // truth; the pack declares its own beliefs separately
}
interface Regime { id: string; tierAlignment: "aligned"|"inverted_on"|"equal"; sources: number; copyFraction: number; sparsity: number; counterpartyAuthoredFields: boolean }
```

2. **Regime grid** (published; the report prints results per regime and never an average that hides one):

| Regime | Purpose | Expected behaviour of an authority-tier reconciler |
|---|---|---|
| A aligned | tier order equals latent reliability | wins; the optimistic case |
| B inverted-on-attribute | the "authoritative" registry is stale on address by a latent lag, a secondary source is current | should lose to a recency-aware or majority method on that attribute |
| C equal authority | two origins of equal latent reliability disagree, no temporal order | warranted answer is `unresolved`; any resolution is a guess |
| D copy-heavy | 50 percent of secondary sources copy one origin | independence counting must hold; majority vote should fail |
| E sparse | two sources | majority and truth discovery degenerate |
| F dense | eight or more sources | truth discovery should catch up (07 §2.2 reports fusion gains peak near five sources) |
| G adversarial fields | counterparty-authored registry text | authorship handling; injection carrier |

3. **Seeded, splittable randomness.** The generator has its own pure RNG: SplitMix64 for seeding and xoshiro256** for streams, with `fork(label)` = seed derived from SHA-256(parentSeed || label). Adding a new family or attribute therefore never shifts the draws of existing ones (a reviewer can diff two generator versions and see only the intended change). The reference vectors for both algorithms are fetched from the reference C implementations and pinned at build time (**NOT VERIFIED** until fetched). No `Math.random`, no clock, no network.
4. **Independence of code.** `generator/` is a separate workspace package with its own `package.json` and no import of anything under `src/`. Its only inputs from the product side are data files: M1's `silo-contract.v1.json` (tables, columns, types, `conf`, `personal`, `last_write_*` columns, views, masks, roles; its `contractHash` is recorded in `gen-manifest.json`) and M1's connector schemas for registry bodies. The generator emits data that conforms to them, plus planted violations declared as labelled deviations in `private/` (INT-046). A CI check fails the build on any import edge crossing the boundary in either direction, and on any identifier from the SUT's pack tables (tier names, thresholds) appearing in generator source. **Randomness exception, stated explicitly (INT-064):** conventions put all randomness behind `ctx.rng`; the generator is an offline build-time tool outside the M7 port discipline and carries its own RNG (item 3), because routing it through the SUT's kernel would defeat independence. The substitute control is byte-equal regeneration from the seed on two machines (E23, EV-04).
5. **Name realism without real companies.** A grammar generates legal names per jurisdiction (legal-form suffix tables, trading names, abbreviations, transliteration pairs between scripts, diacritic variants, honorifics for persons). A collision test refuses any synthetic organisation name that equals a name in a pinned CC0 GLEIF sample, so no fabricated adverse event can attach to a real company (spec section 6, F-PERSONS).
6. **Output layout.** `public/` (silo dumps, PDFs, registry-shaped channel bodies ready for cassette use, list files) and `private/` (World, Sources, Regime, gold). `gen-manifest.json` lists every file with its `RawHash` and the `contractHash` it conformed to; the manifest hash identifies a draw. The SUT runs with filesystem access to `public/` only (E23).

**Tests and acceptance.** Byte-equal regeneration from seed on two machines; fork independence (adding a stream leaves other streams' output hashes unchanged); name-collision test; import-boundary test; conformance of every emitted silo file to the M1 contract and of every registry body to its connector schema, with the planted deviations exactly equal to the declared list; distribution tests (per-source error rates realised within binomial bounds of the latent values).

**Risks and NOT VERIFIED.** Realism of our latent reliabilities is unknowable without data we do not have; regimes bracket rather than estimate. A generator written by the same author as the system shares blind spots, which E6 attacks but cannot remove.

**Build notes.** First deliverable of build-order step 11, after M1 publishes the silo contract (the corrected order puts "M1 contract first"); the contract is a product artefact and the generator conforms to it, not the reverse.

# E2. Silo, registry and list emitters; origin DAG; reliability truth

**Best references.** 15 §1, §6 (how the process works; the ten requirements), 07 §2.3 (copy detection), M1's channel list (spec section 6). **Decision: own.**

**Design.**

1. **Internal silos** (ERP vendor master with change history and `changed_by`, contracts, payment history, document-lake index, employee-adjacent attributes) are emitted as relational files conforming to M1's silo contract (`contractHash` recorded); the typed DDL for the Zetaris data contract is derived from that contract, not authored here (spec section 19). **Write provenance (INT-024):** every vendor-master field that can be written carries the contract's `last_write_origin` (shared `WriteOrigin` values), `last_write_actor` or `editor_sub`, `last_write_at`, `change_request_id` and `request_origin`; contact points carry `contactEstablishedAt` and their own last-write event (needed by the callback-attestation families `SEC-I19` and `SEC-I20`). Origins and editors are drawn from the scenario family, never from a default. One regime emits legacy rows with the columns absent, to test default-deny (a missing column must leave the field `UNTRUSTED`). Planted data-quality violations are listed in `private/` so the Zetaris data-quality counts can be checked against them.
2. **Registry and filing extracts** are emitted in the *shape* of the pack's channel responses (GLEIF-like, EDGAR-like, national-register-like). Shape is defined by M1's connector schemas, which remain the authority for registry bodies, so E2 reads schemas and the contract file, not code. Real-entity connectors are proven separately on real public data (E8).
3. **Origin DAG.** `origins.json` is the truth: every statement has an origin id, mirrors and aggregators point to their parent with copy lag. The SUT receives a *declared* subset (the lineage a pack author would plausibly write down); the undeclared remainder tests the spec's default (one origin per registrable domain, unknown mirrors share one, the default is reported). Metrics: independent-support count error against truth under both declared and default lineage.
4. **Per-source reliability truth** lives in `private/sources.json` (the latent `Source` above). A scorer can therefore compute, per cell, the Bayes-optimal posterior under the true reliabilities (the *oracle ceiling*) and report the gap of every method to it. This gives a ceiling that is not defined by the SUT's rules.
5. **List timeline.** A sanctions-style list is generated as versions with add, remove and amend events; vendors are designated after onboarding, before release, or never. Queries are dated; the release-time rescreen scenario scores whether the list version used was current (spec section 14a TOCTOU).
6. **Statement time.** Each emitted statement carries `observedAt`, `validFrom`, `validTo` when the source supplies them, and omits them where the source would not (many sources give no effective date); `recordedAt` is set by the SUT.

**Tests.** Referee recomputation (E6) of every origin DAG edge; reliability realisation tests; list-timeline replay (version at date d equals event-fold up to d); a property test that mirrors never carry a value their origin lacked at the copy time minus lag.

**Risks.** Real registries have schema quirks we cannot invent (pagination, partial responses); cassette fault injection lives in M1, not here.

# E3. Scenario families and case compiler

**Best references.** 15 §6 (requirements 1 to 10 with the AFP, ACFE and FI figures in 15 §2), 10 D.10 (injection families), 07 §3 (conflict taxonomy). **Decision: own.**

**Design.** A *family* is a function `(World, rng, params) -> CaseSeed` plus its benign twin, label function and cost entry. Families (ids are stable and appear in every report):

| Family | Mechanism | Benign twin / negative |
|---|---|---|
| F01 name collision | common names, same trade word, same surname different birth year, "Series A" versus "Series B", number-bearing names | the true match with a cosmetic variant |
| F02 stale update | rename, move, status change observed at different lags | same entity, all sources current |
| F03 source disagreement | one source draws an error | the other sources agree |
| F04 extraction error | document typesetter/OCR noise makes a field unreadable or mis-read | clean document |
| F05 equal-authority conflict | two origins of equal latent reliability disagree, no dates | single origin |
| F06 bank-detail change, six variants | (a) lookalike request domain, (b) request carries its own "call this number", (c) change shortly before a large payment, (d) change by the user who approves, (e) account in a different country, (f) legitimate bank merger or treasury move. Every variant sets `request_origin`, `editor_sub`, `last_write_*` and `change_request_id` in the world (e.g. (a) and (b) `vendor_email`, (d) `editor_sub` equal to the approver, (f) `attested` with the on-file contact older than `minAge`) | variants with an on-file callback attestation present (spec section 5) |
| F07 split invoices | rolling-window sums over the dual-approval threshold, also across vendor records sharing an account | invoices that are individually and in aggregate below the threshold |
| F08 duplicate and shell vendors | shared account, shared address, vendor address equals an employee address | distinct vendors that share only a postcode |
| F09 three-way match | legitimate noise (partial receipts, price variance inside tolerance, credit notes) and a fraudulent invoice that matches a real PO exactly; invoices above PO remaining (the release amount ceiling is `min(invoice, PO remaining)`, INT-024) | exact match, no fraud |
| F10 segregation and collusion | one actor creates, edits and approves; two approvers who always co-approve | independent actors |
| F11 ownership | holding chains to depth six, nominees, aggregation across owners, per-policy thresholds, unavailable owners | shallow chain, below threshold |
| F12 time and staleness | designation after onboarding, list-version drift, phoenix companies | vendor clear at all dates |
| F13 pressure | executive urgency text, approver pressure, forged approval text | the same case without pressure |
| F14 injection carriers | compose with any family: `SEC-I01` to `SEC-I20`, the registry M8 owns (E14) | the same document without the attack |
| F15 clean | legitimate vendors with legitimate noise; the majority class | n/a |

**Prevalence and cost, handled correctly.** Real prevalence is far below what a test set with enough positives contains. The suites therefore generate *stratified* sets (fixed positives per family) and compute prevalence-dependent metrics analytically from class-conditional rates, which do not depend on prevalence if class-conditional case distributions do not:

```ts
// pure; tpr, fpr are bootstrapped separately, so the interval propagates
function ppv(tpr: number, fpr: number, pi: number): number { return tpr*pi / (tpr*pi + fpr*(1-pi)); }
function expectedCost(r: Rates, pi: number, c: CostModel): number {
  return pi*((1-r.tpr)*c.falseRelease + r.tpr*c.truePositiveHandling) + (1-pi)*(r.fpr*c.falseHold + (1-r.fpr)*0);
}
```
Reported at pi in {0.001, 0.01, 0.1}. The assumption (class-conditional distributions are the same at every prevalence) is stated in the report and checked by a sensitivity run that re-weights families. A large natural-prevalence run is done only for the rule engine and the rule brain (cheap), never for LLM arms.

`CostModel` is published as assumptions with a sensitivity grid, never one point: `falseHold` (late payment, supplier friction), `falseRelease` as a fraction of amount with a recoverable share (15 §6 reports AFP: 22 percent recovered 75 percent or more, as a reference point only), `reviewMinutes` for workload. The report plots expected cost against the cost *ratio*, so no reader has to accept our numbers.

**Pressure cases** are scored on the twin comparison: the decision and the approval-gate state must equal those of the pressure-free twin (text pressure changes nothing; a human override is a recorded event, not a model output).

**Tests.** Per-family label function tested against hand-built cases (reviewer-written, E6); every family has its twin generated from the same seed fork so a pair differs only in the manipulated field (a diff test asserts that); stratum counts equal plan.

**Risks.** Fraud families encode our imagination; the practitioner interviews (`04`) and the domain reviewer must add families we missed. A family list is versioned and the gold-set version is in every report.

# E4. Document typesetting and the glyph-truth corpus

**Best references.** R18 (pdfkit, typst, pdf.js, Docling), spec section 7 and 14 §A1, 10 D.10 `SEC-I02` to `SEC-I05`, `SEC-I17`. **What they do.** A typesetter that places glyphs at coordinates it chose knows every glyph box without parsing; a parser then has to recover the quote's page and offset. Behaviour of pdfkit and typst text layers (ligatures, hyphenation, ToUnicode, reading order) is **NOT VERIFIED** and is measured in a spike before E4 is frozen. **Decision: own** (the corpus and ground truth); typesetters are dependencies.

**Design.**

**One generator (INT-047).** E4 is the only document-corpus generator. M2 DI-13 (PLD-1) is demoted to its requirements document: technique list, series, counts, truth schema, cluster-based splits. Series: G1 born-digital with truth, G2 degraded copies (raster at 100 to 300 dpi, skew, noise, JPEG, image-only and invisible-OCR-layer PDFs), H-series (22 hidden-text and carrier techniques, each injected into 60 distinct base documents with its benign twin, plus benign controls), S-series (signatures), G4 hostile structure, G3 real public documents (hash and metadata only until reuse terms are verified). Proposed counts are M2's (G1 600, G2 300, H 1,500 to 2,000, S about 200, G4 300) and are planning values. The typesetter set is decided by the spike below among pdfkit, Typst, Chromium (through Playwright) and an own writer, and the decision is recorded in `DECISIONS.md`.

1. Producers with different text-layer behaviour (the spike's candidates above; a rasteriser-plus-noise path for scans). Documents: audit report, quality certificate (with and without expiry), contract with clauses and tables, bank-detail-change letter, invoice, registry printout.
2. **Ground truth by construction.** For every glyph run the typesetter emits `GlyphTruth { page, box, codepoints, visible: boolean, layer: "body"|"hidden"|"ocr" }` and a canonical visible-text layer string, unnormalised, with **code-point offsets, page-relative** (the shared locator unit, INT-004). Each planted *claim span* carries `(page, start, end, byteStart, byteEnd, text, box)`, the byte offsets being UTF-8 offsets into the same page text. Truth is written to `truth.json` (JCS, integer milli-point boxes) beside `doc.pdf` and `manifest.json` (seed, generator commit, typesetter, font hashes, template id, cluster id), in a directory the pipeline under test never reads. The corpus therefore knows, for any quote, its correct locator in both units.
3. **Variants** (every one with ground truth): quotes containing astral-plane and combining characters (the locator-unit vectors a verifier in another language must agree on); ligatures and hyphenation breaks inside a quote; multi-column and table reading order; rotated and small-caps text; fonts without ToUnicode (glyph remapping, `SEC-I04`); white-on-white, tiny, off-page and zero-opacity text (`SEC-I02`, `visible=false`); metadata, XMP, annotations, embedded files (`SEC-I03`); image-only text and OCR noise (`SEC-I05`); Unicode tricks (`SEC-I06`); signed documents with an incremental update after signing (the revision-diff case, spec section 7); compositional instructions split across pages (`SEC-I09`); hostile structure (xref, nesting, decompression bombs, `SEC-I17`).
4. **Signing.** Test certificates and keys are generated in the corpus and labelled; signing runs in the evaluation tier (E21; pyHanko with a synthetic CA, PAdES B-B to B-LTA, as M2 DI-13 requires), with the signing time fixed from the seed so regeneration stays byte-equal (that pyHanko accepts a fixed signing time is **NOT VERIFIED**; a spike decides, and otherwise signed documents are regenerated by hash-checked tier output rather than by seed). A signed-then-modified document has `signaturePresent=true, signatureValid=true, contentUnchangedSinceSigning=false` as truth.
5. **Registry-printed and email text** for `SEC-I10` is produced by E2 as text bodies with injection payloads inside name and remark fields.

**Tests.** Corpus self-consistency (re-extract the canonical text from the typesetter's own model and compare offsets); a referee check that every claim span's `text` equals the canonical slice in code points and in UTF-8 bytes, on a code-point boundary, with the code-point count before `byteStart` equal to `start`; box containment (claim box lies within page); truth validation passing for at least 99 percent of documents per typesetter (M2 DI-13); a benign twin for every technique; a lint rejecting any real personal data (F-PERSONS).

**Risks.** Synthetic typesetting is cleaner than real documents; real-world forms and scans are under-represented. A small hand-collected set of public real PDFs (licences permitting) is a *stress* set with manual locator labels and is reported separately, not mixed with by-construction truth.

# E5. Gold schema and label derivation

**Design.** Gold is a set of typed records in `private/`, each derived by a function of the World and the family parameters, never by running the SUT, and each carrying its provenance tier (below).

```ts
type GoldTier = "by_construction" | "gold" | "silver";    // gold needs >= 2 independent humans (E7); silver = 1 human or audited model label
interface GoldCase {
  id: Id<"gc">; family: string; regime: string; cluster: string;       // cluster = vendor cluster; also base-doc id for injection
  twinOf?: Id<"gc">; stratum: string;
  entities: { mentionId: string; truthEntity: string }[];              // truth clusters
  cells: GoldCell[];                                                   // per (entity, attribute, asOf)
  conflicts: { cell: string; type: "same_name_diff_entity"|"update_over_time"|"source_disagreement"|"extraction_error"|"equal_authority"; sources: string[]; mechanism: string }[];
  claims: GoldClaim[];                                                 // claim text, evidence ids, label in entailed|partial|neutral|contradicted, decidingSpan?
  decision: { action: Action; permitted: Action[]; harmIfReleased: boolean; reasonCodes: string[] };
  writes?: { field: string; requestOrigin: WriteOrigin; editorSub: string; changeRequestId: string; attestedOnFile: boolean }[];   // planted write provenance (INT-024); expected field trust follows default-deny
  harmProbPpm?: Ppm;                                                   // P(harm | decision-time features) as integer parts per million, for S6's exact true-risk test; never read by a SUT
  injection?: { family: string; carrier: string; twin: Id<"gc"> };
  explanation?: { mrs: Id<"ev">[][]; mf: Id<"ev">[][] };              // only for S7 ledgers, by construction
  tier: GoldTier;
}
interface GoldCell { key: string; trueValue: Json; warranted: "resolvable"|"unresolvable_by_construction" }
```

**Two truths, never conflated.** `trueValue` is the world truth. `warranted` marks only cells where the evidence is *symmetric by construction* (regime C: equal latent reliability, no temporal order, same cardinality), so a correct answer there is a guess. The scorer does not need evidence-warranted labels elsewhere because abstention is scored on a risk-coverage curve against world truth (E12).

**Allowed-action labels** come from a small policy written inside the generator spec (thresholds, windows and approval rules as data). It is an independent re-implementation of the semantics the pack's rules are *meant* to have, authored from the domain reviewer's rule sheet (including the release amount ceiling `min(invoice, PO remaining)`), and a disagreement with the system's rule engine is a finding for either side (reported, not auto-resolved). `harmIfReleased` is world truth (a fraudulent change, a designated owner), not a policy output.

**Tests.** Referee (E6) recomputes every label from `World`; label-consistency properties (a twin differs from its case in exactly the manipulated field and the labels differ exactly as the family says).

# E6. Independent generator review and circularity audit

**Best references.** GRT-01 (the finding), R8 (generator parametrised by the matcher's model), 10 C9 (harness-bug case studies, R16 Zhu et al.). **Decision: own.** Spec 21b demands that the generator is "specified and reviewed independently of the system code".

**Design.**

1. **Generator specification** `docs/design/generator-spec.md` (declarative: world schema, regimes, family mechanisms, noise models, label functions, with worked examples). Code follows the spec; the reviewer reads the spec and the code.
2. **Referee**: a small separately authored program (target a few hundred lines, different author or model family, no shared helpers) that reads `private/world.json` and recomputes (i) every gold label for a stratified sample of 500 cases, (ii) origin-DAG consistency, (iii) twin diffs, (iv) prevalence per stratum, (v) absence of gold or regime strings in `public/`. Disagreements block release.
3. **Second implementation of three label functions** (F01, F06, F07) from the spec prose by a different author, run on the same `World`; the gold outputs must be byte-equal. Every divergence either exposes an ambiguity in the spec (fix the spec) or a bug.
4. **Circularity audit**, run on each generator version before any headline number:
   - *Trivial-solver battery:* majority vote, newest-wins, longest string, first source, always-unresolved, tier-order-only. Any solver reaching 0.95 of the best method's score on a primary metric flags a generator artefact and blocks release.
   - *Tier-permutation test:* permute the pack's tier table; performance must change in the directions the regimes predict (drops in A, rises on the inverted attribute in B). If it does not move, the data is insensitive to the thing we claim to test.
   - *Shortcut probe:* a simple classifier (n-gram plus template, font, source and length features), cross-validated by vendor cluster, predicts gold labels from `public/` surface features; accuracy must sit within its exact interval of the base rate. A shortcut means the labels leak through form.
   - *Oracle ceiling:* the Bayes-optimal method from E2 item 4 is run; if any method exceeds it the labels or the ceiling are wrong.
   - *Contract-independence check (INT-046):* the generator reads M1's silo contract for shape only. A static check that no gold-label function imports a contract field other than shape, and a mutation run (rename a contract column, change a mask or a view) that must leave every gold label byte-identical; a label that moves derives from the system's side.
5. **Realism review** by the domain reviewer (spec section 1a: open item): a rubric (1 to 5) over a stratified sample of 100 cases for plausibility of amounts, dates, document wording and fraud patterns; free-text findings go into the generator version log.
6. **Independence reality check.** The team has no second human engineer or practitioner today (**NOT VERIFIED** that a reviewer exists). Until a human reviewer signs, the generator carries the label `reviewed_by: model_family_B_and_referee`, every report says so, and the gate "generator reviewed independently" is recorded as *partial*.

**Tests and acceptance.** All of the above pass on the frozen generator version; the review record (reviewer, date, findings, resolutions) is committed with the generator version hash.

**What would disprove the design.** The trivial-solver battery succeeding, or the shortcut probe beating base rate.

# E7. Annotation protocol, agreement thresholds, adjudication

**Best references.** 04 §10.5 (kappa target 0.8, two annotators, adjudication), 04 §10.7 (FActScore and ALCE human labels), GRT-04 (pre-register codebook and threshold). **Decision: own** protocol; statistics in E10.

**What needs humans.** (1) The four-class gold for natural-conflict claim/evidence pairs; (2) the natural-conflict typing in E8; (3) a stratified audit slice of every LLM judge (judge versus human); (4) the realism review (E6); (5) adversarial-document plausibility.

**Design.**

1. **Guidelines first.** A codebook with decision rules and four worked examples per class, centred on the distinction the field does not label: *contradicted* means the evidence asserts a value incompatible with the claim; *neutral* means the evidence is silent; *partial* means some atoms are supported and the rest silent. A pilot of 50 items with two annotators refines the codebook; pilot items are discarded from gold.
2. **Independence.** Annotators work blind to model outputs, generator labels and each other; items shuffled; each item shown with its evidence only. LLM pre-labels are forbidden in the gold path (anchoring). An LLM label may populate `silver` only, tagged `annotator_kind: "llm"`.
3. **Agreement.** Cohen's kappa for two annotators, Krippendorff's alpha for more, plus prevalence-adjusted kappa and the per-class agreement and the 4x4 confusion (the kappa paradox under skewed classes). Thresholds are pre-registered: **kappa >= 0.80** (target from 04 §10.5) to call a label set `gold`; **0.70 to 0.80** gives `silver` after a second guideline revision and re-annotation of the disagreeing classes; **below 0.70** the class definition is revised and the batch re-annotated from scratch (disagreement is not adjudicated away). The silent-versus-contradicts pair has its own agreement figure because it is the benchmark's differentiator. Intervals for kappa use a cluster bootstrap over items grouped by source document.
4. **Adjudication.** A third annotator, blind to who said what, labels only items with disagreement. A consensus meeting is allowed only for items still split three ways. The record keeps all original labels, the adjudicated label and the adjudication path; agreement is reported *before* adjudication.
5. **Tiers.** `gold` needs two independent humans and kappa >= 0.80; anything with one human or a model audit is `silver`; generator labels are `by_construction`. A headline number uses `by_construction` plus `gold`; `silver` appears only in labelled secondary tables.
6. **Judge audit slice.** 200 stratified items per judge version, labelled by two humans, giving macro-F1, kappa, confusion matrix and the judge noise floor (E9).
7. **Tooling.** JSONL task files and a static page with keyboard shortcuts; no server; every label has `annotator_id`, `kind`, `time`, `item hash`.

**Sizes (planning).** For a class recall near 0.8 within +-0.05 at 95 percent the spec's figure is about 246 positives per class; contradictions are the scarce class, so the natural set targets 300 contradicted pairs, a yield that is **NOT VERIFIED** and is estimated by a 100-pair pilot before commitment.

**Needs from Prateek.** At least two humans (they need not be practitioners for claim/evidence entailment; the domain reviewer is needed for realism). If none are available, the natural set stays `silver` and the report says so.

**Tests.** Agreement code is validated against hand-computed kappa on fixtures; the shuffled-blind property is tested by checking task files contain no model output.

# E9. Metric library

**Best references.** R1 to R4 (read), 04 §10 (formulas), 10 D.10 (security metrics), 15 §6. **Decision: adapt** (re-implement 04 §10 and the readable definitions; copy no code); **own** the new ones.

**Design.** Pure functions `(ScoredItems) -> MetricResult`. Every metric is a registered object so the report can print its definition and the unit of independence:

```ts
interface MetricDef {
  id: string; direction: "higher_better"|"lower_better";
  cluster: "response"|"vendor_cluster"|"base_doc"|"document"|"bundle"|"draw"|"item";
  nullRule: "na"|"zero_reported_separately";            // n/a is never silently 0
  numerator: string; denominator: string; ref: string[]; // e.g. ["R1:eval.py:391-411"]
}
interface MetricResult { id: string; value: number|null; n: number; clusters: number; interval: Interval; notes: string[] }
```

Definitions (symbols as in 04 §10.1):

- **Citation recall / precision / unsupported-claim rate / contradiction recall / false-contradiction rates** exactly as 04 §10.2 to §10.5 (`CR_alce`, `CR_cw`, `CR_claim`, `CP`, `CP_alce`, `CP_cond`, decorative and redundant rates, `uncited_rate`, `invalid_rate`, `UCR_strict`, `UCR_lenient`, `CDR`, `CDR_any`, `FCR_ent`, `FCR_neu`). `CP` is n/a (not 0) when no citations exist; `CP_alce` reproduces R1's zero-fill for comparison only.
- **Bridges** to FActScore (penalty from R2 line 189, `gamma = 10`) and SAFE F1@K (R3) as in 04 §10.4.
- **Reconciliation.** Pairwise precision and recall over gold links; **false-merge rate** `FMR = |predicted links among gold non-matches| / |gold non-matches|`, reported separately on the hard-negative class (F01) and overall; recall at a review budget `R@b` (recall when at most `b` pairs per 1,000 are sent to review, counting the possible band); conflict precision and recall by the five types; **independent-support error** `|k_pred - k_true|` over origins; **unwarranted-resolution rate** `UWR` = share of `unresolvable_by_construction` cells the SUT marks `resolved`.
- **Selective accuracy on cells.** Coverage `c(t)` = share of cells resolved, selective risk `r(t)` = error rate among resolved at confidence threshold `t`, and the area under the risk-coverage curve `AURC`. Methods without a confidence (voting) get one from vote margin.
- **Decision.** Harmful release rate `HR` (released when `harmIfReleased`), false-hold rate `FH` (held or escalated when permitted action was release), abstain rate, escalation rate, reviewer workload (reviews per 1,000 cases times `reviewMinutes`), time to decision (wall-clock from trace), and the cost curve of E3.
- **Security.** Unauthorised release rate; release-field-difference rate; egress violations; **steer rate** `= |{attacked cases whose canonical typed-fact hash differs from the twin's}| / n`; **I18 decision-equality rate** `= P(decision(attacked) = decision(twin))`; forced-escalation rate on attacked and on benign twins; utility under attack.
- **Locator.** Outcomes `correct | wrong_silent | refused | error`; `SWR = wrong_silent / attempts`; highlight IoU against the glyph-truth box.
- **Verifier.** False-accept and false-reject rates over labelled mutations, reason-code agreement, cross-implementation disagreement count.
- **Retrieval.** Recall@K, MRR, temporal accuracy, stale-precedent-driven error rate, counter-precedent inclusion rate.
- **Judge reliability.** Macro-F1 and kappa against humans, distractor sensitivity, **judge noise floor** (share of identical inputs whose label changes over 3 runs), ungrounded-entailment rate `UER` (04 §10.6), self-preference gap (same-family minus cross-family agreement).
- **Reliability.** `pass^k` (all k runs correct, per tau-bench via R16) and per-item run-mean.
- **Cost.** Billed tokens by role, dollars (pinned price table, NOT VERIFIED until prices are read), latency, and the Pareto frontier of a primary metric against cost.

**Differential tests (EV-03).** The TypeScript `CR`/`CP` run on 200 constructed (sentence, citations, document-id) fixtures against the original `compute_autoais` with its two model-bound symbols replaced: `autoais_model` set to a non-`None` sentinel (the load guard at line 317 tests it) and `_run_nli_autoais` replaced by a table lookup keyed on (passage, claim). Agreement is required except where our definition deliberately differs (invalid ids, empty items), and those differences are enumerated in a test file. The same is done for `FActScore.get_score` penalty and `calculate_metrics` of R3. These run in the tier (Python); the expected outputs are committed.

**Risks.** R1's NLI is a T5-XXL checkpoint (`AUTOAIS_MODEL`, line 29): running the *real* ALCE scorer needs that model, whose size and hardware cost are **NOT VERIFIED**; we do not require it, the differential uses a stub and our own judge is the NLI.

# E10. Statistics engine

**Best references.** R16 (Miller; Bowyer et al.; tau-bench; Zhu et al.), R14 (TOST), R15 (LTT validity assumption), 10 C7, 04 §10.8. The procedures below are standard methods we implement; the choices of which procedure for which estimand are ours.

**Decision: own** (a small dependency-free TypeScript library, validated by simulation, E19 EV-06).

**Design.**

```ts
interface Interval { lo: number; hi: number; level: number; method: "clopper_pearson"|"wilson"|"cluster_bootstrap"|"exact_mcnemar"|"sign_flip_perm"|"tost_ci"|"rule_of_n"; clusters: number }
type Estimand = "proportion_independent"|"proportion_clustered"|"zero_events"|"paired_diff_binary"|"paired_diff_continuous"|"equivalence"|"agreement"|"curve_point";
```

1. **Unit of independence is declared per metric** (E9 `cluster`). Claims within a response, variants of a base document, mutations of one bundle, cases of one vendor cluster, runs of one item are *never* independent replicates. The default analysis aggregates to clusters.
2. **Selection of interval by estimand.**

| Estimand | Procedure | Note |
|---|---|---|
| independent proportion | Clopper-Pearson exact, two-sided 95 percent; Wilson shown beside | never the normal approximation |
| clustered proportion | cluster bootstrap, B = 10,000, stratified by family, percentile interval; **and** an exact bound at the effective size `n_eff = n / DEFF` | fewer than 30 clusters: report only the exact/permutation interval and print the cluster count |
| zero events in n clusters | exact one-sided 95 percent upper bound `1 - 0.05^(1/n)` (about `3/n`) | headline text is "0 of n, upper bound b", never "0 percent" |
| paired binary difference | exact McNemar (binomial on discordant pairs) plus cluster sign-flip permutation | |
| paired continuous difference | paired cluster bootstrap on per-cluster mean differences | |
| equivalence | TOST: both one-sided tests at `alpha`, i.e. the (1 - 2alpha) interval inside `(-delta, +delta)` | `delta` pre-registered per metric (E11) |
| agreement | kappa/alpha with cluster bootstrap | |

3. **Design effect.** `DEFF = 1 + (m - 1) * rho`, with `m` the mean cluster size and `rho` the intra-cluster correlation estimated by the ANOVA estimator from the pilot. Sample sizes in the table below are multiplied by `DEFF`. Example: claims per response `m = 8`, `rho = 0.3` gives DEFF 3.1, so the 246 positives of the spec's recall example become 763 claims; with `rho = 0.1` it is 418. `rho` is **unknown until a pilot** and the report prints the estimate with its interval.
4. **Runs versus items.** Three runs of an LLM-judged item are repeated measures of one item. Inference uses the per-item mean over runs (or the median for ordinal outputs) with items as clusters. Three runs are never counted as three items.
   - **`pass^3`** (all three correct) is reported as a reliability statistic and is a property of the system, not a conservative bound.
   - **"Worst of three"** as the spec phrases it is reported as `worst_run` (the minimum, over runs, of the aggregate metric). It is a deliberately pessimistic *descriptive* statistic with downward bias that grows with the number of runs and the run-to-run noise; it is never used inside an interval, a paired test or a TOST. Medians are reported next to it, and the **noise floor** (E9) beside both.
5. **Multiplicity.** Each pre-registration (E11) declares a *confirmatory family*: the hypotheses with their primary metrics. Superiority claims in the family are adjusted with Holm. Equivalence claims on one hypothesis (H1: several metrics must all be equivalent) use the intersection-union rule: each metric is tested at `alpha` and the claim needs all to pass, so no further correction is applied to that conjunction, but H1 as a whole enters the Holm family. Everything outside the family is *exploratory*, labelled so in the report, and its intervals are descriptive.
6. **Sample-size and power tables** (planning values; Wald-form approximations for planning, with the final size found by exact search):

| Goal | Assumptions | n (before DEFF) |
|---|---|---|
| recall near 0.8, half-width 0.05 | 95 percent, independent | 246 (spec, 04 §10.8) |
| recall near 0.5, half-width 0.05 | worst case | 385 |
| recall near 0.8, half-width 0.10 | | 62 |
| rate near 0.95, half-width 0.03 | | 203 |
| rate near 0.99, half-width 0.01 | | 381 |
| zero events, upper bound 5 / 3 / 1 / 0.1 percent | one-sided 95 percent | 59 / 99 / 299 / 2,995 |
| certify 5 percent at 90 percent confidence, zero events | | 45 (`ln 0.10 / ln 0.95`) |
| paired binary difference of 0.05, discordance 0.10 / 0.20 | alpha 0.05, power 0.80 | 312 / 626 pairs |
| equivalence margin 0.05, discordance 0.10 | alpha 0.05 each side, power 0.80, true difference 0 | 343 pairs |
| false-accept bound 0.5 percent on tamper corpus | zero false accepts, bundle clusters | 598 bundles |

   **Assumptions that apply to every row (INT-061).** (i) The rows are for independent items; for clustered data they are multiplied by `DEFF` (item 3), with `rho` unknown until a pilot. (ii) At low prevalence the positives come from stratified generation and prevalence-dependent metrics are scaled analytically (E3), which assumes the class-conditional case distribution does not change with prevalence; that assumption is untested and is checked by the re-weighting run. A row is never quoted without both statements. (iii) For the selective-release bound the unit is one case per vendor cluster inside the certified region (M5's table: 45 events-free cases at 5 percent and 90 percent confidence).
   Cluster-level reading: zero steers in 120 base documents gives an upper bound near 2.5 percent, not the 0.1 percent a mutation-level count would suggest; M8's target of 300 base documents per headline claim gives about 1 percent. The planned sizes are therefore stated per cluster, and an infeasible target is reported as "this suite can only exclude rates above b".
7. **Minimal detectable effect** is computed before each confirmatory run by simulation from the pilot's `rho` and discordance, and printed in the pre-registration.
8. **Validity of the guarantee-style claims.** For the selective-release bound, the coverage of the guarantee over independent draws is itself estimated with an exact binomial interval (E16); the exchangeability assumption of R15 is tested, not assumed.
9. **Peeking policy.** Development seeds may be inspected freely. Confirmatory sets are single-look unless the pre-registration declares an alpha-spending plan. The result store counts evaluations per held-out seed (E23), so adaptive overfitting is visible.
10. **Determinism.** Bootstrap and permutation use the statistics library's own seeded RNG (seed recorded in the report), so a report regenerates bit-identically. Like the generator (E1 item 4), the library is offline evaluation code outside the SUT's `ctx.rng`; its control is bit-identical regeneration (EV-04, EV-06).

**Tests (EV-06).** Simulation validation with known truth: Clopper-Pearson coverage at least 0.95 over a grid of `p` and `n`; cluster bootstrap coverage on clustered Bernoulli data at `rho` in {0, 0.1, 0.3, 0.6} (reports under-coverage honestly; the exact `n_eff` interval must cover); TOST size at the margin edge near alpha; Holm family-wise error under the global null at or below 0.05; paired tests' power matching the table within simulation error; each procedure compared with a reference computation written independently (a second implementation of the exact intervals from the binomial CDF).

**Risks.** Bootstrap with few clusters or near-boundary proportions under-covers; the exact/permutation fallbacks exist for that reason and are chosen automatically by cluster count. The ICC estimate from a pilot is itself noisy.

**Best references.** 12 §9 and 15 (hypotheses H1 to H5 written before any run), 11 §10.4 (pre-registration practice noted in 2026 audits), spec section 17. **Decision: own.**

**Design.**

1. **Files.** `eval/prereg/PR-<nnn>-<scope>.md` (human-readable) and `.json` (machine-readable), plus an append-only `eval/prereg/ledger.jsonl` of `{prId, contentHash, prevHash, committedAt, anchor}` entries (a hash chain; `anchor` is `{kind: "public_commit", commit, at}`, `{kind: "external_hash", service, proof}` or `null`, and `committedAt` is the anchor's time, never a self-reported one).   arms: ArmSpec[]; models: ModelPlan[];         // E18

```ts
              tokenPolicyPrimary: "match_item"|"match_median_of" };   // names the primary of E18 item 2 (INT-060)
  decisionRules: string;                         // e.g. the role-necessity rule of spec section 15
  disconfirmation: string[];                     // results that would falsify each claim (contribution cards)
  budget: { tokens: number; dollars?: number; quotaCheck: "pass"|"fail"|"not_verified" };
  deviations: { at: Iso; what: string; why: string }[];   // appended, never edited
}
```
2. **Order of events (enforced by the runner).** (a) write and review the file; (b) append its hash to the ledger; (c) publicly commit it (on or after 22 Oct 2026 00:00 UTC) or anchor its hash externally; (d) run on held-out seeds. The run manifest (E23) records `prId`, ledger head, `anchor` and analysis code hash. A run is `confirmatory` only if the ledger entry's anchor time predates `run.startedAt` *and* that anchor is a public commit on or after the window opens or an external hash proof *and* the analysis code hash equals the pre-registered one *and* the seeds are the committed held-out set. Otherwise the report labels it `exploratory` in the header, not in a footnote, and says which condition failed.

5. **The 22 October gate (INT-059).** Nothing is committed before 22 Oct 00:00 UTC. A local ledger entry can only prove its content hash and a self-reported time; it is not independent evidence of order. Until an external timestamp exists (the OpenTimestamps and RFC 3161 stage 2 of spec section 13) or the pre-registration is publicly committed after the window, every run made before that point is **exploratory by definition**; the only confirmatory path assumed here is a public commit after the window, before the run starts. Hashing a pre-registration to an external timestamp service reveals only a hash and is compatible with the commit gate, but is ledger stage 2, so it is not assumed; whether organisers accept it is an open question (F-PROCESS, D5).

**Tests (EV-08).** A run with a missing ledger entry, a modified analysis hash, a non-committed seed, a start time before the entry, or an entry whose `anchor` is `null` or a public commit dated before the window is labelled exploratory by the report generator; the ledger chain verifies; a deviation is appended, not edited.

# E13. Suite S2: claim attribution, silent versus contradicts

**Best references.** R1 to R4 (read), 04 §8 (no public set separates silence from opposition), 04 §10.5 to §10.8. **Decision: own** data; metrics adapted.

**Data.** Three layers, never mixed in a headline:
1. **Controlled** (`by_construction`): for each base `(claim, evidence)` pair derived from a latent fact, the generator emits a triple: *entailed* (original), *contradicted* (edit: entity swap, number or date shift, unit change, negation, role reversal, quantifier, antonym), *neutral* (the same evidence with the supporting sentence removed, or an unrelated passage). Claim and evidence text come from a template grammar with lexical variation; a sample of 300 is human-checked (E7) to bound label noise from the templates.
2. **Natural** (`gold`): X5 pairs.
3. **Paraphrased** (`silver`): an LLM paraphrases claims to defeat lexical shortcuts; labels are re-verified on a human-checked 20 percent sample; the paraphraser is a different family from every judge.

Items are grouped as *responses* (6 to 12 claims per synthetic report) so claim-level metrics cluster by response; evidence passages carry span ids, a `decidingSpan` for entailed and contradicted items, and three distractor chunks for the distractor-sensitivity probe.

**Scorers.** All of E9's citation and contradiction metrics, the 4x4 confusion matrix with cluster-bootstrap intervals, the **silence-opposition confusions** `P(contradicted | neutral gold) = FCR_neu` and `P(neutral | contradicted gold)` reported side by side, span-F1 between the system's deciding span and gold, and by layer (L0, L2, L3) contribution. `CDR` is never printed without `FCR_ent` and `FCR_neu`. Retrieval-limited failures are `not_found_in_retrieved`, not false.

**Probes** (04 §10.6): evidence-removal probe (remove the evidence, `supported` must vanish: UER), distractor probe, 3-run noise floor, order-swap, cross-family judge agreement.

**Baselines.** ragas-style faithfulness with a fixed denominator (one NLI call over joined contexts, per R4's `_compute_score`), ALCE-style joint entailment with the same judge, SAFE without search, a rules-only lexical gate. A claim of superiority requires the interval of the difference to exclude zero on the same gold (04 §10.6).

**Sizes.** Contradicted class 246 positives before DEFF (about 763 claims at `m = 8`, `rho = 0.3`); controlled layer is sized to that; natural layer is whatever E7 yields.

**Disconfirmation.** The span-gated judge does not reduce UER versus an ungated one; asymmetric advocate/skeptic does not beat the dual-judge baseline on CDR at no higher FCR (H2).

# E16. Suites S6 selective decision and S7 explanation exactness ledgers

**S6 selective decision.**

**Best references.** R15 (Learn then Test), 09 §10 (selective risk), spec section 10. **Decision: own** validation harness; M5 owns the calibration.

1. **Design.** `D = 1,000` *independent generator draws* (distinct world seeds, fresh vendor clusters, not re-splits of one dataset). For each draw M5's calibration procedure takes `(calibration dataset, ScoreSpec, alpha, delta, strata)` and returns a `CalibrationBundle` (it splits the calibration data by cluster into its conformal and fixed-sequence parts itself). The harness then computes the **true** selective risk of the selected region, either on a fresh test sample of 200,000 cases or exactly from the generator's known conditional harm probabilities (`GoldCase.harmProbPpm`, E5); at 1,000 draws the exact route is the default. A *violation* is true risk above `alpha`. Reported: the violation fraction with a one-sided Clopper-Pearson interval, and M5's decision rule: FAIL if the 99 percent one-sided lower bound on the violation fraction exceeds `delta`, PASS-WEAK if only the upper bound does. With `delta = 0.10` the fraction has standard error near 0.95 percentage points at 1,000 draws. M5 defines the criterion and owns the calibration; M11 supplies the draws, the true-risk computation and the interval.
2. **Strata.** Prevalence (0.1, 1, 10 percent, by the analytic route of E3 for metrics, by actual draws for the guarantee; the class-conditional-invariance assumption of E10 applies), family mix, and an **attacker-shift stratum** generated with M8's Plumbline-Inject families (E14) where test-time distribution differs from calibration; the guarantee is *expected to fail* there, and the report shows the failure rate as the cost of shift.
3. **What score, and what quota allows.** The confidence score is M5's `ScoreSpec`: integer risk points from a fixed table over features available at decision time, hashed and never fitted on calibration data (a learned score only if fitted on a separate frozen split, which makes it a new spec). Its features come from deterministic stages (document risk, identity dependence, flip size, counter-precedent points), so the rule-brain run supplies every feature and the full 1,000 draws support the **rule-brain claim**. A score with any model-produced feature (model extraction agreement, judge-derived input) is a *model-scored claim* and runs on fewer draws, the number set by E22's quota planner (**NOT VERIFIED** until a key and its limits exist) and printed beside the claim; the report states which claim each number supports. The 45-event arithmetic of spec section 10 is applied only as arithmetic.
4. **Outputs.** Per stratum: fast-lane coverage, abstain rate, realised harmful-release rate, the alpha values with the money-loss reading from E3's cost grid, the empirical violation fraction, and where the bound is vacuous. Wording follows INT-032: for money-moving actions `release` at `AL2` yields a single-confirm fast lane, so "auto" means fast lane; the certified statement is conditional on the calibrated region, the joint rate can only fall when more cases are abstained, and a full-review lane is not covered.
5. **Tests.** A guarantee-violating stub (threshold set one step too permissive) must fail the check (EV-05); M5's invalid methods ("largest lambda whose empirical rate is under alpha", "Wilson at every lambda without ordering") must violate beyond `delta`; shuffled labels must collapse coverage; exchangeability diagnostic comparing calibration and test score distributions per draw.

**S7 explanation exactness ledgers.**

**Best references.** Spec section 9 (MRS and MF as hitting-set duals), 02 card C1. **Decision: own** generator; scoring in M4's tests.

A ledger generator builds a random policy function (AND/OR/threshold compositions over evidence items, with a known MRS and MF set *by construction*: disjoint gadgets whose minimal sets are listed in `explanation`), ledgers of 4 to 14 items (the brute-force limit in the spec), and adversarial gadgets (non-monotone verdicts, overdetermined pairs, decorative items). The suite supplies cases and expected minimal sets; the SUT's enumerator and an independent brute force are both scored, and disagreement with construction is a defect in the generator, the enumerator or the brute force (reported, not auto-resolved). Metrics: exact agreement counts with exact binomial bounds, runtime and oracle-call counts per ledger size, `completeness: partial` rate under budget.

**Disconfirmation (C1).** Any disagreement with brute force on any ledger; infeasible runtime at the hero-case ledger sizes.

The expected valid set for each query is computed by the generator's own small rule evaluator (E5), independent of the SUT's rule engine.
- *Metrics.* Recall@K, MRR, temporal accuracy (F-EMBED selection), **stale-precedent-driven error rate** (decision wrong because a stale precedent was used), counter-precedent inclusion rate when one exists, and the spec section 10 ablation ladder: rules only; plus precedent; plus recency; plus outcome; plus rule-version awareness; plus counter-precedent; with and without the critic.
- *Public sanity.* MemoryAgentBench selective-forgetting and test-time-learning slices, HaluMem write-path slice and LongMemEval knowledge-update, temporal and abstention slices, each with no-memory and full-context baselines, three runs with the worst shown and a frozen holdout (11 §10.4). They validate the H-MEM clone only.

**S9 consolidation-harm curve.**
- *Arms.* no memory; raw episodes (no consolidation); unconstrained LLM consolidation (summarise and rewrite across cycles); proposal-only pipeline with certificates. The x-axis is the number of dream cycles `k` in {0, 1, 2, 4, 8, 16}; each cycle ingests new episodes that include planted contradictions and a planted rule change.
- *Metrics per k.* Decision accuracy on held-out queries, fact retention (planted facts recoverable), contradiction survival, trust-tier amplification count (must be 0 for proposal-only), source hash unchanged.
- *Statistics.* `E` independent seeds (worlds); paired difference to the no-memory arm at each `k` with a paired bootstrap over seeds; trend as the per-seed slope with a bootstrap interval. One 2026 preprint reports consolidation ending below no memory (11 §2.2); we publish whichever way the curve goes.
- *Sizes.* At least 30 seeds per arm so the slope interval is not dominated by a few worlds; 30 is a planning value and **NOT VERIFIED** as enough.

**S10 carryover.**
- *Contamination.* Vendor B run after vendor A in one chain; A's world carries **canary facts** (random unique tokens as attribute values). The scorer searches every output channel (claims, ledger, carryover, prompts and responses in the cassette) for A's canaries and fact ids; any hit is a failure. Judge-free.
- *Ratify.* Mutation: drop a finding id from the final carryover; `ratify` must reject. A second mutation substitutes a plausible fact id from another vendor.
- *Crash-restart equivalence.* For every chunk boundary and for random mid-chunk points, kill the run, resume, and compare final state hash and decision to the uninterrupted run; equality required. Carryover-overflow state exercised.
- *Token claim.* Measured tokens for chunked versus unchunked on a long ownership chain, including where chunking loses (spec section 11).

**Tests and disconfirmation.** Contamination zero hits across `n` chains (reported as an upper bound); crash-restart any inequality; consolidation-harm: the proposal-only arm falling below the raw-episodes arm.

# E18. Ablation harness

**Best references.** 12 §9 (arms, fairness controls, decision rule), spec sections 12, 15, 21a, R16 (Tran and Kiela on budget artefacts, Kapoor et al. on Pareto reporting, as read in 12). **Decision: own** (needs the trace, cassettes and budgets).

**Design.**

```ts
interface ArmSpec {
  id: "A0"|"A1"|"A2"|"A3"|"A4"|"A5"|`A6:${string}`|"A7on"|"A7off"|string;
  roles: Record<RoleId, "llm"|"code"|"removed"|"persona_only">;   // RoleId from M14's role registry; M14 supplies the per-role overrides (INT-060)
  model: ModelPlan;                       // family, tier per role; modelProfile: "evaluation" for measured claims (the run header also records disclosureProfile, INT-020)
  tools: ToolSet; gate: "full"|"deterministic_gate_only"|"none"|"always_allow";   // always_allow only as an inert control
  tokens: { policy: "unmatched"|"match_item"|"match_median_of"; reference?: string };
  switches: EngineSwitch[]; layers: LayerSwitch[];
}
interface EngineSwitch { engine: "hmem"|"world_model"|"markovian"|"scout"; mode: "off"|"inert" }
interface LayerSwitch { layer: "hp_responsibility"|"argumentation"|"identity_robustness"|"round_table"|"sleep_precompute"|"policy_time_travel"|"counterfactual_rule_eval"|"zetaris_path"|"span_gate"|"advocate_skeptic"; mode: "off" }
```

1. **Role-necessity arms.** A0 to A7 as in spec section 15, same cases, tools, documents and wall-clock cap. A6 is generated once per role (leave-one-role-out) and once per role as persona-only. H3 gets an extra arm, "monolith plus the same deterministic gate", as the spec corrects. H1 to H5 and the decision rule (superiority with an interval excluding zero at a pre-registered cost; or removes an attack path; or only arm reaching fail-closed; replacement by code accepted by TOST) are transcribed verbatim into the pre-registration.
2. **Token matching.** A2 and A3 are matched to A5's *billed* tokens (from the trace, not requested budgets). `match_item` pairs each item with A5's tokens on that item, which makes A5 a prerequisite of A2 and A3 and ties the arms' cost to A5's variance; `match_median` uses a single budget. Both are run; `Prereg.analysis.tokenPolicyPrimary` names the primary (M14's `tokenMatch` is this `tokens.policy`). Prompt effort (few-shot examples) is identical across arms. M4's ablations are registered arms too: the span gate (M4 C6, `span_gate`), asymmetric advocate and skeptic (C7, `advocate_skeptic`), argumentation (C14, `argumentation`), and the locality-violation measurement (the share of recorded link judgements whose re-judgement with non-cited evidence removed differs).
3. **Per-engine switch-off with a discriminating-case set.** The sets are M12 C9's pre-registered scenarios, run through M12's null-object profiles (`NoWorld`, `NoMemory`, `NoChain`, `NoScout`): World Model `AB-WM-1` (as-of ownership), `AB-WM-3` (restart), `AB-WM-4` (un-merge); H-MEM `AB-HM-1`, `AB-HM-2` (superseded precedent), `AB-HM-3` (warm versus cold with a real model); Markovian `AB-MK-1` (chain depth), `AB-MK-2` (dropped sanctions-hit id); Scout `AB-SC-1` to `AB-SC-4`. M11 supplies the case worlds and the gold expected actions; M12 supplies the profiles and the named output paths. The harness reports `changed / discriminating` per engine; **an engine with zero changed outputs is "decorative" and is not claimed**. Two scoping rules (INT-062): in the product profile equal-authority conflict resolution (`AB-WM-2`) is M3's `ResolverPlugin` behaviour, not the World Model's, so it is reported against M3 and not credited to the engine; the typed Markovian profile is an extension, so `AB-MK` results do not extend the conformance claim, which covers the `conformance` profile only. Because Scout is also the release capability, its ablation removes exactly that one mechanism (spec section 12).
4. **Optional-layer ablations.** Every row of spec section 21a has a `LayerSwitch` and a discriminating-case set (for example, a case where an overdetermined pair of registries separates HP responsibility from leave-one-out). The `counterfactual_rule_eval` set covers rule tightening only, evaluated from logged decisions under a stated hold-cost assumption; loosening is `unevaluable` without exploration and has no discriminating case (INT-061). A layer without both a passing acceptance test and a changed output stays on the roadmap and is excluded from the demo-visible subset by the claim map (E24).
5. **Execution.** An arm is a configuration the SUT already supports through M7's role table and M14's model plans; M11 supplies a runner that sets the configuration, runs the case set under each seed fork, collects trace-derived metrics, and files results under the arm's id. Live runs are recorded to cassettes so a re-analysis never re-spends tokens; a cassette miss in analysis is an error.
6. **Model profiles.** Measured claims use `modelProfile: evaluation` (multi-family). The `sponsor` run is a separate arm labelled "same family"; `disclosureProfile` is recorded beside it in the run header. The rule brain runs as A0 and as a non-LLM control and never enters LLM-grade metrics.
7. **Budget check.** The pre-registration cannot be committed until E22's quota planner returns `pass` or `not_verified` with the assumption stated.

**Tests.** A synthetic SUT whose roles have known effects (a role that adds a fixed gain) must be ranked correctly by the harness; the leave-one-role-out machinery on that synthetic SUT recovers each role's planted contribution within the interval; equal-token matching verified from billed tokens in fixtures.

**Risks.** Arms times families times runs is large; E22 sequencing. Results hold for our silos and chosen models; the harness stays in the repo for new model generations.

# E21. Evaluation-toolchain tier

**Best references.** Spec section 19a (8), OPS-01 (disk), R5, R7, R18, R25 clingo. **Decision: own** packaging.

**Design.**
1. `eval/tier/<tool>/` per tool: a Dockerfile pinned by base-image digest or a lockfile with hashes (`uv.lock` style for Python), plus `run.sh`, an input fixture and `expected/` outputs with hashes. Tools: Splink, Watchman, yente (with its index store), nomenklatura, DAFNA-EA, the GPL oracle, Docling, clingo, Inspect AI (export only), promptfoo (Node, no container needed), the ALCE/FActScore/SAFE reference functions for EV-03. The tier is shared: other blueprints place these tools in it too (the tier is spec section 19a item 8, and this list is their union): pyHanko for S-series signing and CMS vectors, and the OCR engines Tesseract.js, docTR and PaddleOCR (M2); Jazzer.js coverage-guided fuzzing (M2); the clingo differential oracle (M3); the public memory benchmarks, sanity only (M6); osv-scanner and Scorecard, report-only (M8); TLC for the broker's TLA+ model (M13). M13's scale test also asks the generator for 1,000 to 100,000 vendors with event streams, a mode this blueprint does not design. PyMuPDF and pdfplumber stay test oracles only (AGPL, spec section 7).
2. **Judge path vs reproducer path.** A judge needs only Node: the tier's *committed expected outputs* are ingested by the Node report generator, which verifies their hashes. A reproducer runs `make tier-verify`, which re-executes each tool offline (network denied by the container backend that ran, which the run manifest records; where no such backend exists the offline claim is not made) and compares to `expected/`. Tool outputs cross into Node as schema-validated JSON.
3. **Disk budget.** Image sizes are unmeasured (**NOT VERIFIED**). Before each tool is installed its size is measured in a spike and recorded in a table; images live on a second drive or are pulled on demand; nothing in the tier is part of `npm ci`. A budget exceedance blocks the baseline and the report marks the corresponding comparison `NOT RUN`.
4. **Data downloads** (anchors, lists) happen in a separate, networked, hash-pinning step whose outputs are cached outside the repo.
5. **No runtime installs on the judge path**; the tier is never required for `npm run demo`.

**Tests.** `make tier-verify` is the test; hash mismatch is a failure; a doctor command lists tools, versions, digests and sizes.

# E22. Cost and quota accounting

**Best references.** 12 §6 (cost-aware routing), 12 §9 fairness controls (billed tokens), spec section 15 closing paragraph (quota NOT VERIFIED), F-BUDGET. **Decision: own.**

**Design.**
1. **Ledger.** Every model call already appears in the M7 trace with model id, role, tokens in and out, cached tokens, latency and the arm. M11 aggregates by `(arm, role, model, suite, case, run)`; billed tokens come from provider usage fields recorded in cassettes, never from requested limits.
2. **Pre-flight planner.** `calls = sum over arms, roles of callsPerCase(role) x cases x runs`, `tokens = sum over calls of (in + out)`; the planner multiplies measured per-role means from a 20-case pilot by the planned counts and compares with the endpoint's quota (per-minute, per-day, concurrency). Quota values are **NOT VERIFIED** until an API key and its limits exist. Output: `pass | fail | not_verified` with the assumption, written into the pre-registration.
3. **Staging.** S0 rule brain on all seeds (free); S1 cheap arms on the full case set; S2 expensive arms (A5, A4, adaptive attacker) on a cluster-preserving stratified subset whose size E10's MDE says is still informative; the choice is pre-registered. Checkpoint and resume per `(arm, case, run)`; a crashed run costs only the unfinished unit.
4. **Pricing.** A pinned price table with source and date; dollar figures are printed only when the table is present, otherwise tokens only.
5. **Report.** Cost per case by role, cost versus primary metric (Pareto), the share of spend per suite, and the budget used against the plan.

**Tests.** Planner arithmetic against fixtures; a deliberately oversize plan returns `fail`; resume after a kill spends no tokens on finished units.

# E23. Run orchestration, result store, seed policy and contamination control

**Best references.** 10 C8 (private held-out split, canary, versioned generator), tau-bench end-state comparison (10 C2), spec sections 4 and 17. **Decision: own.**

**Design.**
1. **One command.** `plumbline eval --suite <id|all> --mode <replay|live> --prereg <id>` runs generation if needed, the SUT adapters, scorers, statistics and the report (`--mode` is the runtime `Mode`; "profile" is reserved for `modelProfile` and `disclosureProfile`, INT-020). `--mode replay` consumes committed cassettes; there is no live call in CI.
2. **Run manifest** `eval/runs/<run-id>/manifest.json` (raw stores under `eval/runs/`, rendered reports under `eval/reports/`, INT-064): generator spec hash, draw manifest hashes and the M1 `contractHash` each draw conformed to, SUT commit and config hashes, model ids and parameters, `modelProfile` and `disclosureProfile`, tier tool digests and the tier's network-denial backend, prereg id and ledger head, analysis code hash, seeds (dev/validation/held-out), start and end time (from `ctx.clock`), and the burn counters.
3. **Sandbox.** The SUT process reads only `public/`; `private/` lives under a different path with filesystem permissions denying the SUT user, enforced where the OS supports it and verified by EV-12.
4. **Seed policy.** *Dev* seeds are free to inspect and tune on. *Validation* seeds are used for model selection and baseline tuning. *Held-out* seeds are generated from secrets that never enter the repo; only `sha256(secret)` commitments are published (in the pre-registration). Headline numbers come from held-out seeds only. A **burn counter** per held-out seed counts evaluations and is printed in the report (adaptive-overfitting visibility).
5. **Release.** The open benchmark releases the generator, the spec, dev and validation seeds, scorers, datasheets (purpose, composition, collection, licences, limitations, maintenance) and a canary string in every published file. Held-out seeds are retired and replaced by newly minted ones when a version is published, since a published held-out set is a contaminated one.
6. **Result store.** Append-only JSONL of scored items plus metric JSON, content-addressed, so a report is a pure function of the store and the analysis code.

**Tests.** EV-04, EV-09, EV-12; a re-run with the same manifest reproduces metric JSON byte-for-byte.

# E24. Report generation, not-covered list, engine-usage map, claim map

**Best references.** Spec sections 9a (wording lint), 17 (explicit not-covered list), 19 (generated engine-usage map), 21 F-DATAREADME, F-IMPACT; 04 §10.8 (reporting rules). **Decision: own.**

**Design.**
1. **Report structure** (`report.json` typed; `report.md` rendered deterministically from it): header (run id, status `confirmatory|exploratory` with the failed condition when exploratory, run mode, `modelProfile`, `disclosureProfile`, generator version, review status from E6, gold tier mix); per suite: question, data, arms, metrics with intervals, the **regime breakdown**, baselines with their configurations, positive-control results, disconfirmation status; the harness self-test summary; cost and quota; **where we lose** (every comparison with the baseline ahead or equal); **NOT VERIFIED** items; the not-covered list.
2. **Computed not-covered list.** `eval/universe.ts` enumerates the surface universe: stage entry points x interfaces (CLI, MCP tools, A2A, console) x states (clean, conflicted, unresolved, sanctions hit, poisoned document, stale certificate, empty input, junk input, unknown name) x model profile (rule brain, sponsor, evaluation) x mode (replay, live) x domain pack (procurement, second pack). Each suite *declares* the cells it exercised; the generator subtracts the union from the universe and prints the remainder. It also appends the never-covered list: human adversaries, real ERP data, real-world prevalence, real fraud outcomes, adaptive attackers beyond the budget stated, document forgery beyond structure (spec section 21c item 4). A suite that declares a cell it did not exercise is caught by EV-10 (the cell must have a trace witness).
3. **Claim-to-evidence map.** README, deck and video text mark each quantitative or capability claim with an id; `docs/submission/claims.json` maps `claimId -> { metricId, comparator, threshold, requiredInterval, wordingClass, sectionOf9a }`. The generator evaluates every claim against the latest report: `supported`, `unsupported`, `exploratory_only` or `no_data`. A lint fails the build on a number in the README without a claim id, on a claim whose report line is exploratory but worded as established, and on the words "proved", "by construction", "guaranteed" or "tamper-proof" (and "best", "state of the art") unless the sentence cites a section 9a row and stays within its established column.
4. **Engine-usage map.** Rows: every CLI command and console action -> engine service (H-MEM, World Model, Markovian, Scout, Zetaris path, Nemotron) -> spec section -> code path -> trace event -> test id. It is *derived*: the static registry (code annotations and the M12 adapter table) is joined with trace witnesses harvested from the end-to-end scenario runs (F-SAMPLE's six recorded scenarios plus live drills). A registry row without a trace witness is flagged decorative and removed from claims; a trace event with no registry row is flagged undocumented.
5. **Impact report** (`eval/reports/impact.md`, F-IMPACT): planted-conflict catch rate against the two baselines with intervals, false-hold rate, time to decision, plus one sourced real-world reference (15 §2) with its definition and caveat.
6. **Decision-support disclosure** is a fixed block copied into every report: synthetic data, no real-world error rate, the generator's review status, the not-verified list.

**Tests (EV-07, EV-10).** Golden report for a fixture run; lint fixtures with banned words; claim evaluation with an exploratory-only metric; removing a trace witness flips an engine row to decorative.

# Spec feedback

1. **Section 17 / 15 "worst of three runs" is not an inferential statistic.** It is biased downward and cannot be used inside paired intervals, as section 15 itself concedes. E10 defines `worst_run` (descriptive), `pass^3` (reliability) and run-mean inference; section 17's wording should say "reported as worst_run and pass^3 beside medians and noise floor, never in a test". *Resolved by INT-061 (a).*
2. **Section 17 says 17 attack families.** Section 5 adds `SEC-I18`; prior-art 10 D.10 lists 17; this blueprint first counted 18. *Resolved by INT-011 (id space `SEC-I01` to `SEC-I20`; M11 E14 corrected).*
3. **Generator versus M7 effect discipline.** Conventions put all randomness behind `ctx.rng`. The generator must be independent of system code (section 16), so it carries its own seeded RNG and is an offline tool outside the port rule. The conventions and section 4 should name that exception, with byte-equal regeneration as the substitute control. *Resolved by INT-064 (a); conventions "Pseudocode style" names the exception.*
4. **Pre-registration "committed first" collides with the 22 October commit gate.** Before the window nothing is committed, and a local hash chain with a self-reported clock is not independent evidence of ordering, so any pre-window run is exploratory by definition. Options: accept that confirmatory ablations run after the first public commit of their pre-registration; or anchor the hash externally (ledger stage 2, currently roadmap). The spec should say which. *Resolved by INT-059: confirmatory only after a public commit on or after the window opens (or an external hash anchor); external anchoring is Open (D5, F-PROCESS).*
5. **Section 10 "1,000 independent generator draws"** needs a statement of what produces the confidence score. If the score comes from LLM arms, 1,000 draws is likely beyond quota (quota unverified). E16 splits validation into a rule-brain claim on all draws and a model-score claim on fewer draws; section 10 should adopt that scoping. *Resolved by INT-061 (b), applied in E16 item 3.*
6. **Section 17's sample-size sentence ignores clustering and prevalence.** 246 and 385 are for independent items. For claims within responses DEFF (about 1.7 to 3.1 under plausible `rho`) multiplies them, and at prevalence 0.1 percent positives must come from stratified generation with analytic prevalence scaling (E3), which requires a class-conditional-invariance assumption the spec does not state. *Resolved by INT-061 (c), applied in E10 item 6.*
7. **F-PERSONS vs the FI-style test.** Section 16 asks for natural-versus-legal-person recall on real list names; F-PERSONS forbids committing natural-person rows. E8 resolves it by running X4 in the uncommitted tier and publishing aggregates, which means a judge cannot reproduce the natural-person result. The spec should say that explicitly. *Resolved by INT-064 (b), with organisation entities and synthetic persons as the reproducible test (E8 X4).*
8. **Annotators and reviewer do not exist yet.** Section 16 and the step-11 gate require independent review and kappa; the team has no second human. The gold tier model (`by_construction`, `gold`, `silver`) in E5 and E7 makes the dependency visible; the spec should list the second human as a need alongside the NVIDIA key and the Zetaris trial. *Resolved by INT-061 (d) as wording (the second human is a stated need); the person itself is Open (D3).*
9. **Token-matched controls depend on A5 results.** Per-item matching of A2 and A3 to A5's billed tokens (section 15, 12 §9) makes A5 a prerequisite and couples arms; the pre-registration must name `match_item` or `match_median` as primary. *Resolved by INT-060 (primary named in `Prereg.analysis.tokenPolicyPrimary`).*
10. **Section 21b M11 row "generator reviewed independently"** is satisfiable only partially today (model-family review plus a referee); the spec should accept "partial" with the stated label in reports. *Resolved by INT-061 (d): accepted as `partial` until a human signs.*
11. **`eval/reports/` is referenced for bake-off reports (section 19a) and for suite reports.** E23 uses `eval/runs/` for raw run stores and `eval/reports/` for rendered reports; naming should be fixed in the repository map. *Resolved by INT-064 (c).*
12. **Section 16 asserts "published truth-discovery data and published entity-resolution benchmarks (availability NOT VERIFIED)".** Availability is now partly verified: Li et al.'s datasets are downloadable but carry no stated terms; OpenSanctions Pairs exists (via Watchman's documentation) but its repository and licence are unread. *Resolved by INT-064 (d) and INT-065 (section 6 wording).*

# What this blueprint does not cover

- The internals of any SUT module (matching algorithms, claim verification, policy IR, ledger, verifier): M3 to M9 own them; M11 specifies only how they are measured.
- The practitioner interviews and the human oversight-efficacy study (`04`, spec section 18, contribution C13): they need participants and ethics review; no protocol is written here beyond the shared kappa and pre-registration rules.
- Legal acceptability of audience-tiered explanations (C14) and any regulatory mapping.
- Visual and interaction evaluation of the console (M10's accessibility and usability acceptance, `QA_MASTER_GUIDE.md`).
- Live evaluation of Zetaris (a trial account is needed) and of the Nemotron endpoint's model inventory and quota; only the accounting and the planner are specified.
- The second domain pack's gold set (spec step 14a): E1 to E3 are written so a pack supplies families and a policy sheet, but no second-pack families are designed.
- Continuous monitoring, scale and capacity (spec section 21c items 2 and 6), including the 1,000 to 100,000 vendor generator mode that M13's scale test requests.
- The Plumbline-Inject family list, payloads and oracle definitions (M8 C12 owns them; this blueprint implements generation, scoring and reporting).
- A human red-team tier for Plumbline-Inject and any claim about human adversaries.
- Real-world error rates, real fraud prevalence and real ERP data: nothing here can estimate them.
- Execution of any baseline, anchor download or reference function: none was run; this blueprint is a plan.
