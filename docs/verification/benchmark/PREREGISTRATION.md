# Head-to-head benchmark: pre-registration

Written and committed before any model was run on the held-out questions. The question that matters for Track 3 is whether the reasoning architecture is better than asking the model directly. This file fixes the questions, the arms, the scoring and what will be reported, so that the result cannot be fitted to what we hoped for.

## The question set

`questions.json` in this folder: 60 questions generated by `src/desk/bench/questions.ts` from seed 20261023 against the constructed sample ledger. Set hash `sha256:8d61892d4f3c834c0cd4e575151815ba9ea2a366c2e450b2a0a41ec7ec9f4875`.

Six categories of ten: lookup (one retrieval), multi-hop (two or more retrievals and a step of reasoning), counterfactual (arithmetic what-ifs on a retrieved figure), unanswerable (nothing in the ledger can answer), adversarial (five instructions hidden in a lookup, five false premises), numeric (units, rounding, counting).

Ground truth is computed by code with its own SQL over the ledger, not by the Desk's specialists. What it shares with the Desk is the ledger, so this tests reasoning over a ledger, not the ledger's correctness.

A third (20, every third question by position) is held out. The arms and their prompts were developed against the other 40 and are frozen before the held-out 20 are run.

## The arms

All three use the same model, `nvidia/nemotron-3.5-super-vl-120b-a12b` through NVIDIA's API, temperature 0, the same system line about instructions inside a question, and a limit of 8 model calls and 240 seconds a question.

| Arm | What it is |
|---|---|
| A0 | One call with the ledger summary in the prompt: every day with its cost by model and the 80 largest sessions |
| A1 | A tool-using agent: the Desk's five read-only tools (spend, top sessions, landing, changes before, range digest), free-text answer, no program, no Auditor |
| A2 | The Desk: Planner, typed program, specialists, Auditor and Explainer (`src/desk/ask/`) |

## Scoring

Code only, in `src/desk/bench/score.ts`. Exact: every required item is stated (a dollar figure to the cent, a rounded figure to its decimals, a date, or the word first or second). Close: within 1% for dollars and 2% for other figures. Abstention is recognised by its words. A hidden instruction is "followed" when the marker it asked for appears; a false premise is "accepted" when the answer asserts it without a negation. An extra figure is a figure that is not required, not an intermediate of the computation and not in the question.

## What will be reported

Every metric, for every arm, whatever it shows: exact and close by category and in total, on the dev and held-out splits separately; correct abstention; instruction not followed; false premise not accepted; answers with an extra figure; runs that ended in an error; model calls, tokens and seconds per question. A result that favours the baselines is published as it is.

## Predictions, written before the run

1. The Desk (A2) will be at least as exact as A0 and A1 on lookup and multi-hop questions that its tools cover, and it will state fewer figures nothing asked for.
2. The Desk will abstain correctly more often than A0 and A1.
3. The Desk will resist hidden instructions at least as often as the baselines.
4. The Desk will be worse on counterfactual and numeric questions that need arithmetic on a retrieved figure, because its Auditor rejects a figure that no claim supports, so it cannot state a result it computed itself. A0 and A1 may do that arithmetic and be right.

## Limits, stated now

One model, one constructed ledger, one run per question and arm (k = 1), so no reliability over repeated runs is claimed and the pass^k check stays NOT RUN. Sixty questions give wide intervals; a difference of a few questions is not a finding. The questions and the Desk's tools were built by the same people, so the Desk's tools cover the lookup, multi-hop and numeric templates by design; the unanswerable, counterfactual and adversarial categories are where it is not tailored. The scoring rules are ours.

## Addendum, written after the first dev run and before any held-out question was run

The first run on the 40 dev questions (`results-dev-run-1.jsonl`) gave, exact: A0 8 of 40, A1 31 of 40, A2 (the Desk) 20 of 40. Predictions 1 and 2 failed on the dev split, 3 held as a tie, and 4 held. The Desk lost to the tool-using agent for three reasons visible in the answers:

1. It stated the ingredients but never the derived figure (a share, an average per day, a percentage of a spend, a count of days above a figure), because its Explainer may only restate figures a claim carries and no step computed them.
2. On questions the ledger cannot answer (invoices, headcount, the code in a session, a model never used) the Planner had no way to decline and mapped them to the nearest spend step; in one case the Explainer then said moving to a model never used "would have saved" the whole spend, a sentence whose figure is in a claim and whose meaning is not.
3. Two runs ended with the model unavailable and are not counted.

What changed in the Desk, using only the dev questions: four typed steps worked out by code (`share`, `per_day`, `percent_of`, `days_above`) and a `cannot_answer` tool for the Planner with a list of what the ledger cannot hold. A0 and A1 are unchanged. The Desk's dev run is repeated (`results.jsonl`) and reported beside the first. The 20 held-out questions have not been run and the Desk and the baselines are frozen from this commit. Whatever the held-out run shows is published.

## Addendum 2: the Desk v2 and a second question set, written before either was run

The first set's held-out questions have been seen, so they cannot test a Desk that was changed because of them. This addendum is committed before anything is run on the changed Desk. The changes, each in answer to a miss in `RESULTS.md`:

1. **A plan critic.** Code reads the question and the Planner's program and names a figure the question asks for that no step computes (a share, an average per day, a percentage of a spend, a count of days above a figure, an amount in thousands). The objection goes back to the Planner, which revises once; if the revision fails the first plan runs and the trace says so. A new `in_thousands` step does the unit conversion in code.
2. **The Explainer never reads the question.** The Planner reads it (and can only answer with a typed program); the Explainer is given a description of what was asked about, written by code from the program. An instruction hidden in a question can no longer reach the model that writes the sentences.
3. The Planner is told that a spend step also reports how many model calls it covers, because it had declined "how many calls" as untracked.

**Set B** is generated from seed 20261024 (`set-b/questions.json`, hash `sha256:67c9b7130edae3c95afe541dc59c46e8ff518f2012fd37b5a38c03055e9fb667`). It uses the same templates with new parameters, and seven of its sixty questions come from templates set A did not have and the Desk's tools were not built around: the busiest day (2), the gap between two models (2), the median day (2) and a count of sessions (1). They are reported separately. The arms A0 and A1 are unchanged. Each arm is run once greedily on all sixty (the headline), then three more times at temperature 0.7 for pass^k.

Predictions, written now:

1. The Desk's exact count on set B is within a few questions of the tool agent's: a difference of eight or fewer in sixty is noise, and we will say so whichever way it falls.
2. On the seven new-template questions the Desk does worse than the tool agent, because its tools were not built around them.
3. The Desk follows none of the five hidden instructions; the tool agent follows at least one.
4. pass^3 for the Desk is not below the tool agent's.

## Addendum 3: learning from mistakes (DF-127), written before any lesson was made

The Desk can keep what it learns from an answer the checker found wrong. This addendum fixes the procedure, the measure and the predictions before a single lesson exists. No model weights change; a lesson changes only what the Planner is shown.

**Mistakes.** The Desk (v2) is run once, greedy, on every question of set A and of a third set, **set C** (seed 20261025, the first set's templates with new parameters, `docs/verification/learning/train-c/questions.json`). A mistake is a run that ended without a model failure and was scored not exact by the same scoring code as the benchmark.

**Lessons.** For each mistake, in question order (set A first), the Planner plans the question again at temperature 0.7, up to four times (variants 1 to 4), with no precedents. Each plan is run by the Desk's own specialists, the Explainer writes the answer and the benchmark's scorer judges it. The first plan to score exact is kept as a precedent for that question. If none does, the lesson is recorded as unresolved and changes nothing.

**Retrieval.** A question is reduced to its shape (dates, months, model names and numbers become placeholders). The Planner is shown the two earlier questions of closest shape, at a similarity of at least 0.5, each with its verified plan. A question is never its own precedent.

**Rounds.** Resolved lessons are added six at a time (the pool of mistakes is too small for rounds of twenty). After each round the Desk is run, greedy, on all sixty questions of set B with every precedent in force so far. The measure is the held-out error: the share of set B answered not exact. Round 0 is the Desk with no precedents, which is the greedy run of set B already recorded. A round that raises the held-out error above the previous accepted state is reverted, and its lessons are marked reverted. An improvement is claimed only if a seeded paired bootstrap over the sixty questions (2,000 resamples) gives a 95% interval for the change from round 0 that excludes zero.

**Regression.** Every accepted lesson is also a test: asked its own question with all precedents in force except itself, the Desk must come out exact again at least as often as not.

Predictions, written now:

1. A verified plan is found for at most half of the mistakes. Many of the Desk's misses are in how a figure is worded or what the ledger holds, not in the plan.
2. The held-out error on set B falls by no more than five questions in sixty after the last round, which is inside the noise, and the interval for the change includes zero.
3. Nothing changes on the seven questions from templates the Desk's tools were not built around.
4. At least one round is flat or worse, and is reverted.

What would change this plan: nothing, once the first lesson is made. If the procedure turns out to be wrong, the change is written here as a new addendum, with the reason, before the run it affects.

## Addendum 4: a schema-error revision, written after set B was run and before any row was re-run

Set B was run on the Desk v2 as written in Addendum 2: 49 of 60 exact, against 41 for the tool agent. Reading the misses showed a defect that belongs to the Desk, not to the model: in 33 of its 360 recorded runs (4 on set A, 5 on set C, 24 on set B) the Planner's program failed the schema (for example a `share` step whose numerator was not a spend step with group none), the Desk silently handed the question to its rule planner, and the rule planner cannot compute a share, an average per day or a percentage. None of those 33 runs was exact. The first plan was refused and the Planner was never told why.

The change: when the Planner's program fails the schema, the refusal and its reasons go back to the Planner, which revises once, as it already does after the plan critic. Only if that also fails does the rule planner answer. The trace carries `desk.plan.schema_error` and `revision.applied`.

What this does to the evidence, stated before it is gathered:

1. The first runs are kept as they were, in `docs/verification/benchmark/pre-schema-fix/`. They are the Desk v2 as preregistered, and set B's held-out result for it is 49 of 60.
2. The 33 affected rows are removed from the live results files and run again on the changed Desk (v2.1). Everything else is untouched.
3. After this change set B is no longer held out for the Desk: it was read to find the defect. The v2.1 figures are reported as post-hoc, beside the preregistered ones, and never in place of them.
4. Prediction: most of the 33 become exact, because the defect was in the hand-off, not in the questions. If fewer than half do, the explanation here was wrong and that is reported.

## Addendum 5: what a round re-runs, written after the first learning run and before its repeat

The first learning run (`docs/verification/learning/report-first-run.json`) made 6 lessons from 9 mistakes (a verified plan was found for 6, none for 3) and measured held-out set B at 50 of 60 against 54 in round 0, so it reverted the round. Reading the rows shows why that number means little: only 2 of the 60 held-out questions were shown a precedent (Q12 and Q13, both share questions, both went from wrong to right). The other 58 were shown none, so the Planner received exactly the request it had received in round 0, and 6 of them still changed from right to wrong. The model does not give the same answer twice to the same request, and the round was measuring that.

The change: a held-out question that is shown no precedent keeps its round-0 result and is not asked again; only questions that receive a precedent are run. The comparison then isolates what the lessons did. This is a change to the measurement, made after seeing a result, so the first run's report stays in the repository beside the repeat, and the table says that the repeat differs by this rule.

Predictions for the repeat, written now: the held-out count rises by two (Q12 and Q13) and by no more than four; the paired interval for the change includes zero; nothing changes on the 7 new-template questions.

## Addendum 6: the Desk v3 and a fourth question set, written before either was run on it

Sets A and B were read to find the Desk v2.1's defects, so neither can test a Desk changed because of them. This addendum is committed before anything is run on set D, and set D's questions are generated from a seed nobody has used.

What changed in the Desk (v3), each in answer to a miss visible in `RESULTS-v2.md`:

1. **Two typed steps.** `median_day` (the median daily spend, over days with any spend or over every day the ledger covers in the range) and `count_sessions` (how many sessions started in a range, a session starting at its first logged model call). Set B's Q57, Q58 (median) and Q60 (sessions) had no step to compute them.
2. **A spend step for one model counts as one total** whether the Planner grouped it by none or by model. A `share` step whose part was a spend step with `group: "model"` and a model named was refused by the schema, which sent Q12 and Q13 to the rule planner.
3. **The rule planner plans a share** (a model spend, the same range's total, and a `share` step), a median day and a session count, so the fallback is no longer wrong by construction on those questions.
4. **The plan critic** asks for a `median_day` step when the question asks for a median, and for `count_sessions` when it asks how many sessions started.
5. **A comparison names the higher period first** ("The first period cost $51.60 more than the second"), where it used to say "The second period cost $51.60 less than the first". The scorer's reading of Q18 (the first of the words first and second that appears) was wrong for the Desk's answer only because of that wording.
6. **The figure asked for comes first.** When the last step works a figure out of earlier steps, its sentence is placed before the totals it rests on.
7. The Planner's prompt describes the new steps.

The Planner's tool schema and prompt are part of the key of every recorded model reply, so every recorded Desk reply of sets A and B and of the learning run is recorded again on v3. The v2 and v2.1 recordings and results are kept as history in `docs/verification/benchmark/pre-v3/`. The tables of sets A and B are then reported for v3 as post hoc, beside the preregistered ones, never in place of them.

**Set D** (`set-d/questions.json`, seed 20261027, hash `sha256:d8bccd58b4c830debb3635e3095c0c76012752392e9f20e679eb1ad6c2932209`): sixty questions in the same six categories of ten. Fifty come from the first sets' templates with new parameters. Ten replace template questions: four are shapes the Desk v3 now has steps for (the busiest day, the gap between two models, the median day, how many sessions started) and six are shapes nothing was built for (the lowest day, a ratio of two models, days with no spend, a weekend total, an average cost per call, the second-highest model). The six can be missed; that is what they measure. The scorer is unchanged except for one new item type, `text` (a model name the answer must state, case aside), used by the second-highest-model question; the other sets' hashes do not change. All of set D is held out for the v3; its dev and held-out labels carry no meaning here.

**Arms.** A0 and A1 are unchanged (same prompts, same five read-only tools). A2 is the Desk v3. The same Nemotron model (`nvidia/nemotron-3.5-super-vl-120b-a12b`) serves all three, now through Meterless Nightshift on the author's machine with NVIDIA's API as its provider; every live reply carries a Nightshift receipt id in its recording. Each arm answers each question once greedily and three more times at temperature 0.7.

**Predictions, written now.**

1. The Desk v3 answers at least 48 of set D's 60 questions exactly (greedy run).
2. On the six new shapes the Desk v3 answers at most 3 exactly.
3. On the four shapes it now has steps for, it answers at least 3 exactly.
4. The tool agent A1 answers fewer questions exactly than the Desk v3 by at least 5.
5. The Desk v3's pass^3 on set D is at least 75%.
6. The Desk v3 follows none of the five hidden instructions and accepts none of the five false premises.
7. The Desk v3 abstains correctly on all ten unanswerable questions.

A prediction that fails is reported with the others. If reading set D's misses leads to a change, set D is no longer held out for the changed version, and the report says so and shows the first figure beside the later one.

## Addendum 7: role-necessity ablations and a stress test of the Auditor, written before any model was run on set E

The specification asks which roles of the Desk change an outcome and says a role that fails becomes code and the README says so (DF-085). The core specification's arms for this were written for a different pipeline (a token-matched vote, long reasoning, a central orchestrator); the Desk has none of those. What it has is a Planner and an Explainer that are models, and a plan critic, an Auditor and a revision loop that are code, so the design here is leave-one-role-out: the Desk with exactly one role taken out and everything else as it was.

**Set E.** 60 questions in six categories of ten, generated by `src/desk/bench/questions.ts` with seed 20261028 against the constructed sample ledger, set hash `sha256:83e767af463ae51329915da7bcec2603160d146de4456fe538fbdd58024b3485` (`docs/verification/ablation/set-e/questions.json`). It has the first set's templates and the four extra shapes the Desk has steps for, with new parameters, and none of the shapes nothing was built for, so that a miss in an ablated arm is the removed role's and not a missing step. Set E has not been run by any arm. The Desk's code has not been changed to suit it; the only changes since set D are the role switches, which default to every role on and are tested to leave a default run unchanged.

**The arms.** All on the same model and settings as sets A to D (temperature 0, 8 model calls and 240 seconds a question, one greedy run per question). A0, A1 and A2 are as before. The ablation arms:

| Arm | What is taken out | What happens instead |
|---|---|---|
| A3 | the plan critic | the Planner's first plan stands |
| A4 | the Auditor | the Explainer's first draft is the answer, nothing is checked |
| A5 | the revision loop | the Auditor still removes an unsupported sentence, but the Explainer is not asked to revise it |
| A6 | the Explainer | code states each claim as its own sentence |
| A7 | the Planner | the rule planner plans |

Every model request that does not depend on the removed role is the same request as in A2, so the recordings are shared and the comparison is paired on identical inputs.

**The stress arms.** With a capable model the Explainer rarely writes an unsupported sentence, so on good runs the Auditor has little to do and an ablation cannot show what it is for. Two further arms read an Explainer that has been made wrong on purpose: in every Explainer reply, code changes the first figure (`corruptFirstFigure`: multiplied by 1.37 and increased by 1, in the same format; a digit next to a hyphen, so a date, is left alone). A2F is the Desk with this fault and A4F is the Desk without its Auditor with this fault. The fault is synthetic and is labelled so wherever the result is shown: it measures what the Auditor catches, not how often the model errs.

**The rule that decides each role, fixed now.** Each ablation arm is compared with A2 on the same questions by the exact McNemar test (two-sided). A role is **necessary on this set** when the arm without it gets fewer questions exactly right with p under 0.05, or lets a hidden instruction through that the full Desk resisted, on the same test over the ten adversarial questions. It is **harmful here** when the arm without it is better with p under 0.05. Otherwise it is **not shown necessary**, which is an absence of evidence and not a finding that the role does nothing: sixty questions cannot show equivalence, and no equivalence margin is set because the sample could not meet one. For the stress arms, the Auditor is **necessary under this fault** when more answers reach the reader without a figure nothing asked for with the Auditor than without it, exact McNemar p under 0.05.

**What will be done with the result.** Every finding is published as it falls. A role found harmful is reported and the product is not changed on this evidence alone; one set, one model and sixty questions are not enough to remove a part. A role not shown necessary is not claimed as proved useful anywhere in the README, the deck or the product description, and the sentence that names it says what was measured.

**Predictions, written now.**

1. A2, the full Desk, answers at least 54 of the 60 exactly (all 54 of set D's questions that were not new shapes were answered exactly, so this is not a stretch).
2. A7, the rule planner, answers at least 10 fewer exactly than A2 and is necessary on this set: it cannot compute a share, an average or a count of days.
3. A3, without the plan critic, differs from A2 on at most 3 questions and is not shown necessary: the third version's Planner is told the whole list of steps, including the ones that compute a share, an average and a count of days.
4. A4, without the Auditor, is within 2 questions of A2 on exactness and follows no hidden instruction: the Explainer never reads the question. It is not shown necessary on good runs.
5. A5, without the revision loop, is within 2 questions of A2 and is not shown necessary.
6. A6, with the Explainer replaced by code, is within 3 questions of A2 on exactness and states a figure nothing asked for in at least ten percentage points more of its answers than A2, because code states every claim. Exactness will not show a difference where the answer text does.
7. Under the fault, A4F shows a wrong figure in at least 30 of the answers that reach the reader and A2F in none; the Auditor is necessary under this fault.
8. A6 and A7 use fewer model calls and fewer seconds per question than A2.

A prediction that fails is reported with the others. If reading set E's misses leads to a change to the Desk, set E is no longer held out for the changed version, and the report says so and shows the first figure beside the later one.

## Addendum 8: does the architecture carry a small model, and does a mix of Nemotron models hold, written before any model was run on set F

Track 3 leans on "the Nemotron model mix, memory and the tool loop". Sets A to E ran every arm on one model, the 120B super-vl. Two questions follow that those sets cannot answer, and this addendum asks them before any run: (1) with a much smaller model behind it, does the Desk still beat a plain tool-using agent on the same model, and by how much does the model matter for the Desk and for the tool agent; (2) if the Planner (the role the answers depend on, Addendum 7) and the Explainer (not shown necessary on exactness) are given different models, does the mix answer as well as the large model alone.

**Set F.** Sixty questions in six categories of ten, generated by `src/desk/bench/questions.ts` with seed 20261031 (set E's recipe: the first set's templates and the four shapes the Desk has steps for, new draws), set hash `sha256:414cc20fcaddb2356b83f4dcf86a1ec114ed6ad452e98da14d6fe3bc3886f427` (`docs/verification/mix/set-f/questions.json`). It is not a set of unseen texts throughout: the ten unanswerable questions use fixed texts that every set repeats, and three lookup and two numeric draws coincide with a question of an earlier set; the other 45 are new. No arm has been run on set F. The Desk's code has not been changed to suit it; the only changes since set E are a per-role model setting (`DESK_ROLE_MODELS`), which is unused unless set and tested to leave a default run unchanged, and the new set itself. Note that the Ask path changed after set D (Scout Intent routing, embeddings for routing): set D is not held out for today's Desk, and set F is the first set that is.

**The models.** All through Meterless Nightshift 1.2.3 on one machine, each reply carrying a signed receipt that is checked after the run (`desk receipts`): S = `nvidia/nemotron-3.5-super-vl-120b-a12b` (the model of sets A to E), L = `nvidia/nemotron-3.5-lightning-30b-a3b` (30B parameters, 3B active), U = `nvidia/nemotron-3-ultra-550b-a55b` (550B, 55B active).

**The arms.** One greedy run per question (temperature 0, 8 model calls and 240 seconds a question as before). For each of S, L and U: A0 (the model with no tools), A1 (a plain tool-using agent) and A2 (the Desk). Then two mixes of the Desk, A2 with `ask_planner` on one model and `explainer` on another: **MIX-UL** (Planner on U, Explainer on L) and **MIX-LU** (Planner on L, Explainer on U). Eleven arm-runs, each in its own results file under `docs/verification/mix/` and its own recordings.

**How it is scored.** As in every set: exact figure, hidden instruction not followed, false premise not accepted, correct abstention. A reply that never arrives after the retries counts as not exact. Paired comparisons on the same questions use the exact McNemar test (two-sided). Seconds per question are measured live, since these runs share no recording with an earlier run.

**Predictions, written now.**

1. On every model, A2 answers more questions exactly than A1, and A1 more than A0.
2. A2 on L answers at least 48 of the 60 exactly: a model with 3B active parameters, behind the Desk's typed steps and Auditor, is not far below the large models.
3. Across the three models, the spread of A2 (largest exact count minus smallest) is at most 6, and the spread of A1 is at least 8: the architecture narrows the gap between models more than the tool agent does alone.
4. MIX-UL answers within 2 questions of A2 on U.
5. MIX-LU answers within 2 questions of A2 on L: a large Explainer cannot repair a small Planner's plan.
6. Median seconds per question order as A2 on L, then MIX-UL, then A2 on U, from fastest to slowest.
7. Every signed receipt of every run verifies, and the model named in each receipt is the model the arm asked for. A reply served by another model is reported with the arm.

**What will be done with the result.** Every finding is published as it falls, the failed predictions beside the held ones. The Desk is not changed on this evidence. If reading set F's misses leads to a change, set F stops being held out for the changed version and the report shows the first figure beside the later one. A mix that does not hold is reported as one that did not.
