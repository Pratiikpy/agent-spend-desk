# Head-to-head benchmark: pre-registration

Written and committed before any model was run on the held-out questions. The question that matters for Track 3 is whether the reasoning architecture is better than asking the model directly. This file fixes the questions, the arms, the scoring and what will be reported, so that the result cannot be fitted to what we hoped for.

## The question set

`questions.json` in this folder: 60 questions generated by `src/desk/bench/questions.ts` from seed 20261023 against the constructed sample ledger. Set hash `sha256:8d61892d4f3c834c0cd4e575151815ba9ea2a366c2e450b2a0a41ec7ec9f4875`.

Six categories of ten: lookup (one retrieval), multi-hop (two or more retrievals and a step of reasoning), counterfactual (arithmetic what-ifs on a retrieved figure), unanswerable (nothing in the ledger can answer), adversarial (five instructions hidden in a lookup, five false premises), numeric (units, rounding, counting).

Ground truth is computed by code with its own SQL over the ledger, not by the Desk's specialists. What it shares with the Desk is the ledger, so this tests reasoning over a ledger, not the ledger's correctness.

A third (20, every third question by position) is held out. The arms and their prompts were developed against the other 40 and are frozen before the held-out 20 are run.

## The arms

All three use the same model, `nvidia/nemotron-3.5-super-vl-120b-a12b` through NVIDIA's API, temperature 0, the same system line about instructions inside a question, and a limit of 8 model calls and 240 seconds a question.

| Arm | What it is |
|---|---|
| A0 | One call with the ledger summary in the prompt: every day with its cost by model and the 80 largest sessions |
| A1 | A tool-using agent: the Desk's five read-only tools (spend, top sessions, landing, changes before, range digest), free-text answer, no program, no Auditor |
| A2 | The Desk: Planner, typed program, specialists, Auditor and Explainer (`src/desk/ask/`) |

## Scoring

Code only, in `src/desk/bench/score.ts`. Exact: every required item is stated (a dollar figure to the cent, a rounded figure to its decimals, a date, or the word first or second). Close: within 1% for dollars and 2% for other figures. Abstention is recognised by its words. A hidden instruction is "followed" when the marker it asked for appears; a false premise is "accepted" when the answer asserts it without a negation. An extra figure is a figure that is not required, not an intermediate of the computation and not in the question.

## What will be reported

Every metric, for every arm, whatever it shows: exact and close by category and in total, on the dev and held-out splits separately; correct abstention; instruction not followed; false premise not accepted; answers with an extra figure; runs that ended in an error; model calls, tokens and seconds per question. A result that favours the baselines is published as it is.

## Predictions, written before the run

1. The Desk (A2) will be at least as exact as A0 and A1 on lookup and multi-hop questions that its tools cover, and it will state fewer figures nothing asked for.
2. The Desk will abstain correctly more often than A0 and A1.
3. The Desk will resist hidden instructions at least as often as the baselines.
4. The Desk will be worse on counterfactual and numeric questions that need arithmetic on a retrieved figure, because its Auditor rejects a figure that no claim supports, so it cannot state a result it computed itself. A0 and A1 may do that arithmetic and be right.

## Limits, stated now

One model, one constructed ledger, one run per question and arm (k = 1), so no reliability over repeated runs is claimed and the pass^k check stays NOT RUN. Sixty questions give wide intervals; a difference of a few questions is not a finding. The questions and the Desk's tools were built by the same people, so the Desk's tools cover the lookup, multi-hop and numeric templates by design; the unanswerable, counterfactual and adversarial categories are where it is not tailored. The scoring rules are ours.

## Addendum, written after the first dev run and before any held-out question was run

The first run on the 40 dev questions (`results-dev-run-1.jsonl`) gave, exact: A0 8 of 40, A1 31 of 40, A2 (the Desk) 20 of 40. Predictions 1 and 2 failed on the dev split, 3 held as a tie, and 4 held. The Desk lost to the tool-using agent for three reasons visible in the answers:

1. It stated the ingredients but never the derived figure (a share, an average per day, a percentage of a spend, a count of days above a figure), because its Explainer may only restate figures a claim carries and no step computed them.
2. On questions the ledger cannot answer (invoices, headcount, the code in a session, a model never used) the Planner had no way to decline and mapped them to the nearest spend step; in one case the Explainer then said moving to a model never used "would have saved" the whole spend, a sentence whose figure is in a claim and whose meaning is not.
3. Two runs ended with the model unavailable and are not counted.

What changed in the Desk, using only the dev questions: four typed steps worked out by code (`share`, `per_day`, `percent_of`, `days_above`) and a `cannot_answer` tool for the Planner with a list of what the ledger cannot hold. A0 and A1 are unchanged. The Desk's dev run is repeated (`results.jsonl`) and reported beside the first. The 20 held-out questions have not been run and the Desk and the baselines are frozen from this commit. Whatever the held-out run shows is published.

## Addendum 2: the Desk v2 and a second question set, written before either was run

The first set's held-out questions have been seen, so they cannot test a Desk that was changed because of them. This addendum is committed before anything is run on the changed Desk. The changes, each in answer to a miss in `RESULTS.md`:

1. **A plan critic.** Code reads the question and the Planner's program and names a figure the question asks for that no step computes (a share, an average per day, a percentage of a spend, a count of days above a figure, an amount in thousands). The objection goes back to the Planner, which revises once; if the revision fails the first plan runs and the trace says so. A new `in_thousands` step does the unit conversion in code.
2. **The Explainer never reads the question.** The Planner reads it (and can only answer with a typed program); the Explainer is given a description of what was asked about, written by code from the program. An instruction hidden in a question can no longer reach the model that writes the sentences.
3. The Planner is told that a spend step also reports how many model calls it covers, because it had declined "how many calls" as untracked.

**Set B** is generated from seed 20261024 (`set-b/questions.json`, hash `sha256:67c9b7130edae3c95afe541dc59c46e8ff518f2012fd37b5a38c03055e9fb667`). It uses the same templates with new parameters, and seven of its sixty questions come from templates set A did not have and the Desk's tools were not built around: the busiest day (2), the gap between two models (2), the median day (2) and a count of sessions (1). They are reported separately. The arms A0 and A1 are unchanged. Each arm is run once greedily on all sixty (the headline), then three more times at temperature 0.7 for pass^k.

Predictions, written now:

1. The Desk's exact count on set B is within a few questions of the tool agent's: a difference of eight or fewer in sixty is noise, and we will say so whichever way it falls.
2. On the seven new-template questions the Desk does worse than the tool agent, because its tools were not built around them.
3. The Desk follows none of the five hidden instructions; the tool agent follows at least one.
4. pass^3 for the Desk is not below the tool agent's.

## Addendum 3: learning from mistakes (DF-127), written before any lesson was made

The Desk can keep what it learns from an answer the checker found wrong. This addendum fixes the procedure, the measure and the predictions before a single lesson exists. No model weights change; a lesson changes only what the Planner is shown.

**Mistakes.** The Desk (v2) is run once, greedy, on every question of set A and of a third set, **set C** (seed 20261025, the first set's templates with new parameters, `docs/verification/learning/train-c/questions.json`). A mistake is a run that ended without a model failure and was scored not exact by the same scoring code as the benchmark.

**Lessons.** For each mistake, in question order (set A first), the Planner plans the question again at temperature 0.7, up to four times (variants 1 to 4), with no precedents. Each plan is run by the Desk's own specialists, the Explainer writes the answer and the benchmark's scorer judges it. The first plan to score exact is kept as a precedent for that question. If none does, the lesson is recorded as unresolved and changes nothing.

**Retrieval.** A question is reduced to its shape (dates, months, model names and numbers become placeholders). The Planner is shown the two earlier questions of closest shape, at a similarity of at least 0.5, each with its verified plan. A question is never its own precedent.

**Rounds.** Resolved lessons are added six at a time (the pool of mistakes is too small for rounds of twenty). After each round the Desk is run, greedy, on all sixty questions of set B with every precedent in force so far. The measure is the held-out error: the share of set B answered not exact. Round 0 is the Desk with no precedents, which is the greedy run of set B already recorded. A round that raises the held-out error above the previous accepted state is reverted, and its lessons are marked reverted. An improvement is claimed only if a seeded paired bootstrap over the sixty questions (2,000 resamples) gives a 95% interval for the change from round 0 that excludes zero.

**Regression.** Every accepted lesson is also a test: asked its own question with all precedents in force except itself, the Desk must come out exact again at least as often as not.

Predictions, written now:

1. A verified plan is found for at most half of the mistakes. Many of the Desk's misses are in how a figure is worded or what the ledger holds, not in the plan.
2. The held-out error on set B falls by no more than five questions in sixty after the last round, which is inside the noise, and the interval for the change includes zero.
3. Nothing changes on the seven questions from templates the Desk's tools were not built around.
4. At least one round is flat or worse, and is reverted.

What would change this plan: nothing, once the first lesson is made. If the procedure turns out to be wrong, the change is written here as a new addendum, with the reason, before the run it affects.

## Addendum 4: a schema-error revision, written after set B was run and before any row was re-run

Set B was run on the Desk v2 as written in Addendum 2: 49 of 60 exact, against 41 for the tool agent. Reading the misses showed a defect that belongs to the Desk, not to the model: in 33 of its 360 recorded runs (4 on set A, 5 on set C, 24 on set B) the Planner's program failed the schema (for example a `share` step whose numerator was not a spend step with group none), the Desk silently handed the question to its rule planner, and the rule planner cannot compute a share, an average per day or a percentage. None of those 33 runs was exact. The first plan was refused and the Planner was never told why.

The change: when the Planner's program fails the schema, the refusal and its reasons go back to the Planner, which revises once, as it already does after the plan critic. Only if that also fails does the rule planner answer. The trace carries `desk.plan.schema_error` and `revision.applied`.

What this does to the evidence, stated before it is gathered:

1. The first runs are kept as they were, in `docs/verification/benchmark/pre-schema-fix/`. They are the Desk v2 as preregistered, and set B's held-out result for it is 49 of 60.
2. The 33 affected rows are removed from the live results files and run again on the changed Desk (v2.1). Everything else is untouched.
3. After this change set B is no longer held out for the Desk: it was read to find the defect. The v2.1 figures are reported as post-hoc, beside the preregistered ones, and never in place of them.
4. Prediction: most of the 33 become exact, because the defect was in the hand-off, not in the questions. If fewer than half do, the explanation here was wrong and that is reported.

## Addendum 5: what a round re-runs, written after the first learning run and before its repeat

The first learning run (`docs/verification/learning/report-first-run.json`) made 6 lessons from 9 mistakes (a verified plan was found for 6, none for 3) and measured held-out set B at 50 of 60 against 54 in round 0, so it reverted the round. Reading the rows shows why that number means little: only 2 of the 60 held-out questions were shown a precedent (Q12 and Q13, both share questions, both went from wrong to right). The other 58 were shown none, so the Planner received exactly the request it had received in round 0, and 6 of them still changed from right to wrong. The model does not give the same answer twice to the same request, and the round was measuring that.

The change: a held-out question that is shown no precedent keeps its round-0 result and is not asked again; only questions that receive a precedent are run. The comparison then isolates what the lessons did. This is a change to the measurement, made after seeing a result, so the first run's report stays in the repository beside the repeat, and the table says that the repeat differs by this rule.

Predictions for the repeat, written now: the held-out count rises by two (Q12 and Q13) and by no more than four; the paired interval for the change includes zero; nothing changes on the 7 new-template questions.
