# Alerts (2026-10-24)

`desk alerts check` looks at the state of things and says so, once, when something needs a person. It is meant to run every fifteen minutes from the system's own scheduler (`desk alerts schedule` prints the command for Task Scheduler, launchd or cron and installs nothing).

## What it watches

| Rule | Unhealthy when |
|---|---|
| `cap:<person>:<day or month>` | the cap is used past its warn fraction or ask fraction (WARNING) or at 85% or reached (ALERT); the fractions are the lowest the policy sets, 50% and 80% where it says nothing; money held for calls in flight counts |
| `gate:paused:<person>` | the gate paused the person after a budget overshoot (ALERT) |
| `idle:agents` | idle or background work cost $2 (WARNING) or $10 (ALERT) in the last hour |
| `canary:verdict` | the canary says the agent regressed (ALERT) or that the harness or platform changed (WARNING) |
| `canary:running` | the canary has not run for three days (ALERT) |
| `reconciliation:<vendor>:<month>` | an imported invoice and the estimate are further apart than the tolerance (WARNING) |

Caps and pauses are read only when the gate is named (`--policy FILE`, and `--gate-db FILE` if it is not `data/desk/gate.db`); otherwise the output says they were not checked.

## When it speaks

The rules are the ones monitoring systems use to avoid crying wolf, and each is tested:

- A rule seen for the first time speaks only if it is unhealthy.
- It speaks when its state differs from the one it last spoke about; the same thing is never said twice, however often it is checked, and not on a later day either.
- WARNING to ALERT always speaks. Otherwise a suite (cap, idle, canary, reconciliation, gate) speaks at most once per UTC day. What was held back is recorded once, and speaks the next day if it is still true (a held-back alert does not count as spoken).
- NO_DATA never speaks. Getting better is recorded as `recovered`, not announced, and a rule that gets worse again after that speaks.
- A rule the owner paused (`desk alerts pause <key>`) is not evaluated and its state is not overwritten; that it was unhealthy is noted once a day.
- Every decision (fired, held back, paused, recovered), what was delivered and whether it worked, is in the ledger (`desk alerts history`).

## Where it goes

The terminal always. A desktop notification with `--desktop` (a balloon on Windows, `osascript` on macOS, `notify-send` elsewhere; the text goes through environment variables, not the command line, except `notify-send`, which gets it after `--`). A command of the owner's choosing with `--notify-command`, with the alert in `DESK_ALERT_*` variables. A webhook with `--webhook URL`, **off unless given**, which receives the title, body, state, evidence command, rule key and time and nothing else; a failure is retried twice with a growing wait, a client error is not retried, and failure is recorded and never thrown, so a dead webhook cannot hold anything up.

## What was run

31 tests (`tests/desk/alerts.test.ts`): the state machine in each case above, every rule at its thresholds, the delivery channels with stand-ins (including notify-send given a title that starts with a dash, a webhook that fails with 503, that recovers on a retry, that answers 404, that is down), a full check on a constructed ledger and canary file, the admin commands, and the real CLI in a subprocess. On this machine `desk alerts check` ran against the real ledger; it said the canary file holds a recorded scenario (below), and nothing else needed saying.

**A defect found by running it on real data.** This machine's canary file is the recorded 30-day scenario with assigned dates (up to 2026-10-29), and the first version of the rule called its verdict "the agent got worse" and raised an ALERT. A canary file whose newest date is still to come is a scenario, not daily runs; the rule now reports NO_DATA and says why, with a test.

## Not covered

A desktop notification was not shown on a real desktop (no alert was unhealthy enough, and a test cannot see a balloon); the Windows, macOS and Linux commands are as documented for each system and were exercised only through stand-ins. No webhook was posted to a real service. The gate's caps and pauses were exercised in unit tests of the rules and not through a live gate. The Sources screen of the UI does not show alert state, and there is no weekly page yet (DF-011).
