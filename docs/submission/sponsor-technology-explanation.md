# Sponsor technology explanation: desk.

Every sentence here can be checked in the repository, in a trace line, or by running `npm run desk -- prove` and `npm run desk -- demo`. Where a fact is not verified, it says so.

## Zetaris

- **What we used it for:** the organisational sources of an agent bill. Three synthetic silos of three kinds sit behind one local Zetaris instance: provider invoices as CSV files in an S3-compatible bucket, CI and pull requests in a Postgres database, and a team roster behind a REST endpoint. One statement joins them: spend per landed pull request by team, with seats. The same sources give the bill its `billed` class (invoice amounts against the ledger's list-price estimate) and give landing its CI fact (merged on green checks, or merged although checks were red).
- **Where in the code:** `src/sponsors/zetaris/silo-port.ts` (the port: live, recorded, or labelled fallback), `src/sponsors/zetaris/queries.ts` (the four statements), `src/desk/silo/` (parsing, reconciliation, seeding), `infra/silos/` (the three silos).
- **What changed in the output because of it:** with Zetaris, `desk silos` shows billed $6,123.23 covering the whole ledger (the invoice 1.2% below the list-price estimate), a three-team table of spend per landed pull request ($8.57 to $10.05), and CI facts for 644 landed sessions: 584 merged on green, 60 on red. Without it, nothing is billed, every dollar is an estimate, landing stops at what git shows, and the table is gone. `desk prove` checks this difference (`zetaris-role-changes-the-output`).
- **Fallback when unavailable:** the port returns a labelled fallback, never an exception and never partial rows. A real drill on 2026-10-22 stopped the Zetaris API container: `desk silos` answered in 3 seconds with all four silos `fallback` and the output above changed. In sample mode the four answers are replayed byte for byte from recordings of a live run.
- **Evidence:** trace line `desk.ingest {port:"silo", op:"zetaris.sql", servedFrom:"live"|"cassette"|"fallback", reqHash, respHash, rows}` on every statement; `docs/sponsors/zetaris-local-setup.md` records what was verified live, including the option names that register an S3-style file source (found in Zetaris's own metastore, then confirmed by registering a second table) and a join that overstated billed spend three-fold until each silo was aggregated first.
- **Not verified:** the Unified Semantic Layer, the AI data steward, JDBC from a SQL client.

## Meterless

- **What we used it for:** three of Meterless's open engines, run in our process (there is no Meterless API or key; the organisers confirmed this on 2026-10-17), Scout Intent as our own implementation of Meterless's published specification, and Nightshift as the route to Nemotron. The World Model holds the history of what shaped a bill: model ids, tool versions, plan settings, policy and price versions, with the day each first appeared. H-MEM holds the owner's own definitions and corrections and the precedent of each approved policy change. Markovian reads a range of three or more months one month at a time, carrying a fixed-size state. Scout Intent reads each request before anything is planned and refuses a request to change spend or policy that is phrased as a question. Nightshift serves the Nemotron calls and signs every reply.
- **Where in the code:** `src/engines/` (the engines), `src/desk/engines/` (the adapters), `src/desk/ask/` (the questions that use them), `src/scout-intent/` and `src/desk/scout/` (Scout Intent and the Desk's four-way routing), `src/desk/agents/model.ts` and `src/desk/agents/receipt-signature.ts` (the route through Nightshift and the check of each signed receipt), `vendor/meterless/` (Meterless's conformance suites, unchanged).
- **What it made possible:** "what changed before 15 October?" is answered from the World Model's event history: the tool version `vsample-2` first appeared on 14 October, and the model mix moved that week. A definition of "landed" stored in H-MEM changes the share of spend called landed (63% merged or kept; 67% once the owner says committed counts). Each engine's conformance count is read from a recorded run of Meterless's own runners: H-MEM 13/13, World Model 8/8, Markovian 8/8.
- **Fallback when unavailable:** the engines are code in this repository, so there is nothing to be unavailable; each can be switched off with `desk ask --ablate world_model|hmem|markovian`, and an answer then says so.
- **Evidence:** the trace line `desk.engine {engine, impl, conformance, ablated}` on every answer; `npm run desk -- prove` runs the question with each engine on and off and checks that the answer changes (`meterless-engines-change-answers`). While writing the test for H-MEM we found that the pattern that reads an owner's definition never matched, so the engine had no effect; it was fixed.
- **Scout Intent:** Meterless publishes a specification and an evaluation harness and no reference code, so nothing was copied. On 218 test questions written before tuning, Scout with the older word rules routed 96.3% to the right kind; 2.9% of 68 requests to change spend or policy reached the planner as questions (older rules alone: 76.6% and 61.8%). Against Meterless's own paraphrase gate it does not pass (with the embedding model, intent top-1 0.764 against a floor of 0.85); `docs/verification/scout-intent-2026-10-25.md` says so. `--ablate scout_intent` passes every question to the planner as a read.
- **Nightshift:** every reply carries an Ed25519-signed receipt naming the model; `desk receipts` checks the signature, refuses a changed number, and prints which Nemotron model answered which role. The Desk claims a reply as Nightshift's only if its signature verifies. 1,044 receipts of the model-mix runs and 11 of the first live run verify against one key (`docs/verification/mix/`, `docs/verification/nightshift-receipts/`). A valid signature shows that key signed the record, not that the key is Meterless's.
- **Not used:** Nightshift's overnight jobs and judges, and the engines' own embedder (the Desk's embedder acts beside H-MEM, whose vendored files are not edited).

## NVIDIA

- **Where NVIDIA technology contributes:** Nemotron, reached through Meterless Nightshift or NVIDIA's own OpenAI-compatible API, is the model behind every language role: the policy Drafter and Attacker, the Ask planner (which calls a `plan_answer` tool whose argument is a typed program), the Explainer, and the canary's runs. The code is identical for any OpenAI-compatible endpoint; only a URL, a key and a model id change.
- **Where in the code:** `src/desk/agents/model.ts` (`ModelPort`: live, recorded, none).
- **Which role ran on which model.** The recorded benchmark sets A to E ran every role on `nvidia/nemotron-3.5-super-vl-120b-a12b`. The first live run through Nightshift (11 signed calls) used Planner: Lightning 30B (3 calls) and Ultra 550B (1); Explainer: Lightning (2) and Ultra (1); Drafter: Lightning (3); Attacker: Lightning (1). The model-mix test (set F) ran the Desk on `nvidia/nemotron-3.5-lightning-30b-a3b`, the 120B model and `nvidia/nemotron-3-ultra-550b-a55b`, and two mixes with the Planner and the Explainer on different models (`DESK_ROLE_MODELS`). An embedding model, `nvidia/nemotron-3-embed-1b`, reads routing and the owner's notes by meaning when `DESK_EMBED=on`.
- **Evidence:** the served model id comes back on every reply and is on the trace; tool calling with a JSON-schema argument was exercised live on 2026-10-22; the recorded replies in `data/sample/cassettes/` came from live calls; `desk receipts` verifies the signed receipt of each call and names the model. The canary's 2,340 real runs use two Nemotron models (120B, 30B) and read the served model id from the reply to see a switch. Each benchmark set runs one model on all three of its arms, so a difference is a difference in architecture and not in model.
- **Limits measured:** latency from 0.4 s to 56 s for the same small request, HTTP 500 on about one call in four under rapid use and HTTP 429 on some models under concurrency. The code retries, caps retries, times out, falls back to a rule brain, and says so on the trace.

## What is unique about our use

Four things a typical entry would not do, each with proof. The architecture is measured against a plain call and against a tool-using agent on the same model, on 60 questions whose predictions were written before the run (set D: one call 12, tool agent 45, the Desk 55 exact, seven of seven predictions held), and the result is published as it is, with its earlier first run (49 on set B), its five misses, and a margin the sample size cannot make certain beside it. Each role was taken out in turn on 60 more questions (only the Planner is shown necessary), and the Desk was run on three Nemotron models and two role mixes, with the two predictions that failed published. The sponsor components change outputs a reviewer can see when they are switched off, and the repository checks that they do. The language roles are checked by code: a policy a model drafts is replayed on a month it was not drafted from, and the report leads with the 5 of 333 landed sessions it would have blocked rather than the savings. A result is not a claim: a dossier carries the rows its figures come from and a verifier that runs on plain Node recomputes them; change one byte and it names the row.
